# Lecția 2.2: SPDX și alegerea formatului

[[SPDX]] este celălalt format care îndeplinește cerința din articolul 13(5) al CRA pentru un SBOM "utilizat în mod curent, care poate fi citit de mașini". Această lecție explică ce este SPDX, în ce privințe diferă de CycloneDX și cum decizi ce format să folosești.

## Ce este SPDX

Software Package Data Exchange (SPDX) a fost creat la Linux Foundation în 2010. A devenit standard ISO în 2021: ISO/IEC 5962:2021. Versiunea 2.3 este cea curentă pentru standardul ISO. Versiunea 3.0 a fost lansată în 2024, cu un nou model de date și un sistem de profiluri.

SPDX a fost conceput pentru a rezolva problema conformității cu licențele open-source. Când livrezi un produs care include componente open-source, ai obligații legale: atribuire, includerea textului licenței, dezvăluirea codului sursă pentru licențele copyleft. SPDX îți oferă o modalitate care poate fi citită de mașini pentru a exprima ce licențe se aplică căror componente și ce obligații ai acceptat.

A devenit standard SBOM în timp și acoperă acum și câmpurile de inventar al componentelor necesare pentru gestionarea vulnerabilităților. Dar intenția sa inițială de proiectare, conformitatea cu licențele, este încă vizibilă în modelul de date.

## Structura unui document SPDX

Un document SPDX 2.3 în format JSON conține:

- **Informații despre crearea documentului**, echivalentul metadatelor din CycloneDX: creator, marcaj temporal de creare, spațiul de nume al documentului, versiunea SPDX
- **Pachete (Packages)**, inventarul componentelor. Fiecare pachet are: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` sau `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (unde se află [[PURL]])
- **Relații (Relationships)**, modul în care pachetele se raportează unele la altele. Relația `DESCRIBES` identifică produsul de nivel superior. `DEPENDS_ON` și `DEPENDENCY_OF` cartografiază graful de dependențe.
- **Fișiere (Files)** (opțional), inventar la nivel de fișier cu hash-uri, dacă ai nevoie de granularitate la nivel de fișier
- **Fragmente (Snippets)** (opțional), la nivel de fragment de cod, pentru cod copiat care nu provine dintr-un pachet

Câmpul PURL din SPDX 2.3 se află în interiorul tabloului `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Acest lucru este mai prolix decât câmpul `purl` de prim rang din CycloneDX, dar rămâne lizibil de mașini și poate fi analizat de scanerele de vulnerabilități.

## Unde SPDX are un avantaj

**Standardizarea ISO.** ISO/IEC 5962:2021 înseamnă că SPDX este singurul format SBOM care este standard internațional. Pentru organizațiile care cer formate certificate ISO în achizițiile sau contractele cu furnizorii, acest lucru contează.

**Fluxuri de lucru pentru conformitatea cu licențele.** Dacă principalul tău caz de utilizare al SBOM este conformitatea cu licențele open-source, urmărirea obligațiilor de atribuire, identificarea codului contaminat cu GPL, generarea notificărilor pentru terți, atunci modelul bogat de licențe din SPDX este mai potrivit. SPDX acceptă identificatorii de licență SPDX, `LicenseInfoInFile` pentru detectarea licențelor la nivel de fișier și `licenseComments` pentru situații complexe.

**Integrarea cu graful de dependențe GitHub.** Graful de dependențe al GitHub exportă nativ SPDX 2.3 în format JSON. Dacă depozitul tău este pe GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` îți oferă un SBOM SPDX fără să rulezi niciun instrument local. Pentru multe echipe, acesta este cel mai simplu punct de plecare.

**Mai multe formate de ieșire.** SPDX acceptă JSON, YAML, RDF/XML și un format text tip tag-value. Formatul tag-value poate fi citit de oameni (spre deosebire de JSON sau XML), ceea ce poate fi util pentru revizuire.

## Unde CycloneDX are un avantaj

**Gestionarea vulnerabilităților.** CycloneDX are suport nativ pentru [[VEX]]. SPDX 3.0 a adăugat un profil de securitate cu capabilități VEX, dar suportul din ecosistem pentru VEX în SPDX este încă în curs de maturizare. Pentru fluxurile de lucru de conformitate cu articolul 14, VEX din CycloneDX este mai matur și mai bine susținut de instrumente.

**Dependency-Track.** Cea mai importantă platformă open-source de gestionare a SBOM, OWASP Dependency-Track, a fost construită pentru CycloneDX. Acceptă intrări SPDX, dar funcțiile sale native, potrivirea vulnerabilităților, gestionarea VEX, evaluarea politicilor, sunt cele mai complete pentru CycloneDX.

**Maturitatea instrumentelor.** Majoritatea instrumentelor SBOM, Syft, cdxgen, trivy, grype, tratează CycloneDX ca format principal de ieșire și SPDX ca format secundar.

## Ambele formate sunt valabile pentru conformitatea cu CRA

CRA cere un format "utilizat în mod curent, care poate fi citit de mașini". Atât CycloneDX, cât și SPDX sunt folosite de sute de organizații. Ambele pot fi citite de mașini. Ambele pot transporta câmpurile de inventar al componentelor cerute de articolul 13(5). Nu vei pica un audit CRA pentru că ai ales SPDX în loc de CycloneDX sau invers.

Ghidul Comisiei Europene și documentul ENISA privind bunele practici pentru SBOM fac referire ambele la cele două formate. Niciun ghid oficial al UE nu a desemnat un format ca fiind preferat în detrimentul celuilalt.

## Cum alegi

Folosește acest cadru de decizie:

| Întrebare | CycloneDX | SPDX |
|---|---|---|
| Cazul principal de utilizare este gestionarea vulnerabilităților și conformitatea cu articolul 14 | ✓ | ✗ |
| Cazul principal de utilizare este conformitatea cu licențele open-source | ✗ | ✓ |
| Folosești Dependency-Track | ✓ | ✗ |
| Achizițiile tale cer formate certificate ISO | ✗ | ✓ |
| Pornești de la exportul grafului de dependențe GitHub | ✗ | ✓ |
| Echipa ta folosește Syft sau cdxgen | ✓ | ✗ |
| Ai nevoie de instrumente VEX mature | ✓ | ✗ |

Dacă gestionarea vulnerabilităților este preocuparea ta principală, alege CycloneDX. Dacă ai deja un flux de lucru SPDX pentru conformitatea cu licențele, este rezonabil să îl extinzi pentru a acoperi și gestionarea vulnerabilităților. Trebuie doar să fii conștient că instrumentele VEX sunt mai puțin mature.

Multe organizații produc ambele: CycloneDX pentru operațiunile de securitate, SPDX pentru aspectele juridice și de achiziții. Instrumentele susțin acest lucru. Syft poate produce ambele dintr-o singură scanare.

## Concluzii cheie

1. SPDX (ISO/IEC 5962:2021) este formatul SBOM standard ISO. Versiunea curentă este 2.3 pentru standardul ISO și 3.0 pentru noul model de date. A fost conceput pentru conformitatea cu licențele open-source.
2. Atât [[CycloneDX]], cât și SPDX se califică drept formate "utilizate în mod curent, care pot fi citite de mașini" conform articolului 13(5) al CRA. Niciunul nu este preferat oficial de ghidurile UE.
3. Avantajele SPDX: statutul ISO, model de licențe mai bogat, export nativ din graful de dependențe GitHub, mai multe formate de ieșire.
4. Avantajele CycloneDX: suport nativ pentru [[VEX]], integrare cu Dependency-Track, ecosistem de instrumente de vulnerabilitate mai matur.
5. Dacă raportarea vulnerabilităților conform articolului 14 al CRA este principalul tău motiv, CycloneDX este alegerea mai naturală. Producerea ambelor formate dintr-o singură scanare Syft este o strategie validă.
