# Lesson 2.2: SPDX and Choosing Your Format

[[SPDX]] is the other format that satisfies the CRA Annex I, Part II, point (1) requirement for a "commonly used and machine-readable" SBOM. This lesson covers what SPDX is, where it differs from CycloneDX, and how to decide which format to use.

## What SPDX is

Software Package Data Exchange (SPDX) was created at the Linux Foundation in 2010. It became an ISO standard in 2021: ISO/IEC 5962:2021. Version 2.3 is current for the ISO standard. Version 3.0 was released in 2024 with a new data model and profile system.

SPDX was designed to solve the open-source license compliance problem. When you ship a product that includes open-source components, you have legal obligations: attribution, license text inclusion, source code disclosure for copyleft licenses. SPDX gives you a machine-readable way to express what licenses apply to which components and what obligations you have accepted.

It became an SBOM standard over time, and now covers the component inventory fields needed for vulnerability management as well. But its original design intent (license compliance) is still visible in the data model.

## SPDX document structure

A SPDX 2.3 JSON document has:

- **Document creation information**: equivalent to CycloneDX metadata: creator, created timestamp, document namespace, SPDX version
- **Packages**: the component inventory. Each package has: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` or `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (where [[PURL]] goes)
- **Relationships**: how packages relate to each other. The `DESCRIBES` relationship identifies the top-level product. `DEPENDS_ON` and `DEPENDENCY_OF` map the dependency graph.
- **Files** (optional): file-level inventory with hashes, if you need file-level granularity
- **Snippets** (optional): code snippet level, for copied code that does not come from a package

The SPDX 2.3 PURL field lives inside the `externalRefs` array:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

This is more verbose than CycloneDX's first-class `purl` field, but it is still machine-readable and parseable by vulnerability scanners.

## Where SPDX has an advantage

**ISO standardisation.** ISO/IEC 5962:2021 means SPDX is the only SBOM format that is an international standard. For organisations that require ISO-certified formats in their procurement or supplier contracts, this matters.

**License compliance workflows.** If your primary SBOM use case is open-source license compliance, tracking attribution obligations, identifying GPL-contaminated code, generating third-party notices, SPDX's rich license model is better suited. SPDX supports SPDX License Identifiers, `LicenseInfoInFile` for file-level license detection, and `licenseComments` for complex situations.

**GitHub dependency graph integration.** GitHub's dependency graph natively exports SPDX 2.3 JSON. If your repository is on GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` gives you an SPDX SBOM without running any local tooling. For many teams this is the easiest starting point.

**Multiple output formats.** SPDX supports JSON, YAML, RDF/XML, and a tag-value text format. The tag-value format is human-readable (unlike JSON or XML) which can be useful for review.

## Where CycloneDX has an advantage

**Vulnerability management.** CycloneDX has native [[VEX]] support. SPDX 3.0 added a security profile with VEX capabilities, but the ecosystem support for SPDX VEX is still maturing. For Article 14 compliance workflows, CycloneDX VEX is more mature and better supported by tooling.

**Dependency-Track.** The leading open-source SBOM management platform, OWASP Dependency-Track, was built for CycloneDX. It accepts SPDX input but its native features (vulnerability matching, VEX management, policy evaluation) are most complete for CycloneDX.

**Tooling maturity.** The majority of SBOM tools, Syft, cdxgen, trivy, grype, treat CycloneDX as their primary output format and SPDX as secondary.

## Both formats qualify for CRA compliance

The CRA requires "commonly used, machine-readable." Both CycloneDX and SPDX are used by hundreds of organisations. Both are machine-readable. Both can carry the component inventory fields required by Annex I, Part II, point (1). You will not fail a CRA audit because you chose SPDX over CycloneDX or vice versa.

The European Commission's guidance and ENISA's SBOM good practices document both reference both formats. No official EU guidance has designated one format as preferred over the other.

## How to choose

Use this decision framework:

| Question | CycloneDX | SPDX |
|---|---|---|
| Primary use case is vulnerability management and Article 14 compliance | ✓ | - |
| Primary use case is open-source license compliance | - | ✓ |
| You use Dependency-Track | ✓ | - |
| Your procurement requires ISO-certified formats | - | ✓ |
| You are starting from GitHub's dependency graph export | - | ✓ |
| Your team uses Syft or cdxgen | ✓ | - |
| You need mature VEX tooling | ✓ | - |

If vulnerability management is your primary concern, choose CycloneDX. If you already have an SPDX workflow for license compliance, extending it to cover vulnerability management is reasonable. Just be aware the VEX tooling is less mature.

Many organisations produce both: CycloneDX for security operations, SPDX for legal and procurement. The tools support this. Syft can output both from the same scan.

## Key takeaways

1. SPDX (ISO/IEC 5962:2021) is the ISO standard SBOM format. Current version is 2.3 for the ISO standard, 3.0 for the new data model. It was designed for open-source license compliance.
2. Both [[CycloneDX]] and SPDX qualify as "commonly used and machine-readable" formats under CRA Annex I, Part II, point (1). Neither is officially preferred by EU guidance.
3. SPDX advantages: ISO status, richer license model, GitHub dependency graph native export, multiple output formats.
4. CycloneDX advantages: native [[VEX]] support, Dependency-Track integration, more mature vulnerability tooling ecosystem.
5. If CRA Article 14 vulnerability reporting is your primary driver, CycloneDX is the more natural fit. Producing both formats from a single Syft scan is a valid strategy.
