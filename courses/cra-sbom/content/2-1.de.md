# Lektion 2.1: CycloneDX: Das sicherheitsfokussierte SBOM-Format

Die CRA erfordert ein „häufig verwendetes, maschinenlesbares“ Format. Zwei Formate erfüllen die Anforderung: [[CycloneDX]] und [[SPDX]]. Diese Lektion behandelt CycloneDX: was es ist, was es sicherheitsfokussiert macht und warum es gut zum CRA Artikel 14 Vulnerability-Reporting-Workflow passt.

## Was CycloneDX ist

CycloneDX ist ein OWASP-Projekt. Das Open Web Application Security Project (OWASP) pflegt es als Standard für Sicherheitsanwendungsfälle. Die aktuelle Version ist 1.6. Sie steht in JSON und XML zur Verfügung.

CycloneDX wurde entwickelt, um Vulnerability-Management-Workflows zu unterstützen. Sein Kern-Datenmodell baut auf der Frage auf: „Gegeben diese Liste von Komponenten, welche weisen bekannte Schwachstellen auf, und kann ich darauf reagieren?“ Jede wesentliche Funktion des Formats dient der Beantwortung dieser Frage.

## Aufbau eines CycloneDX-SBOM

Ein CycloneDX-Dokument enthält vier Hauptabschnitte:

### Metadata

Angaben zum SBOM-Dokument selbst und zum beschriebenen Produkt:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Der Zeitstempel zeigt dem Prüfer, wann das SBOM erstellt wurde. Das Tool zeigt, wie. Der Komponentenblock identifiziert, was das SBOM beschreibt.

### Components

Die Liste der Softwarekomponenten. Jede Komponente enthält:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` oder `operating-system`
- `name`: der kanonische Paketname
- `version`: exakte Versionszeichenfolge
- `supplier`: wer sie veröffentlicht
- `purl`: die eindeutige [[PURL]]-Kennung
- `hashes`: SHA-256 oder ein anderer Hash der Komponentendatei
- `licenses`: SPDX-Lizenzausdrücke

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX 1.4+ enthält einen Abschnitt `dependencies`, der abbildet, welche Komponente von welcher abhängt. Dies ist die maschinenlesbare Darstellung des Abhängigkeitsgraphen. Damit kann ein Tool Komponenten der obersten Ebene von transitiven Komponenten unterscheiden, ohne das Build-Tool erneut auszuführen.

### Vulnerabilities

CycloneDX kann Vulnerability-Daten direkt im SBOM einbetten. Jeder Vulnerability-Eintrag verweist auf eine [[CVE]] und die betroffene Komponente. Dies eignet sich für punktuelle Dokumentation, ist jedoch in der Praxis weniger verbreitet. Die meisten Teams führen das SBOM und die Vulnerability-Scan-Ausgabe als separate Artefakte.

## VEX: das Merkmal, das CycloneDX auszeichnet

[[VEX]], Vulnerability Exploitability eXchange, ist das markanteste CycloneDX-Merkmal für die CRA-Konformität. Eine VEX-Erklärung ist eine maschinenlesbare Erklärung, die die Beziehung zwischen einer bekannten Schwachstelle und dem konkreten Produkt dokumentiert.

CycloneDX-VEX unterstützt vier Statuswerte:

- **not_affected**: die Komponente ist vorhanden, die Schwachstelle kann in diesem Produkt jedoch nicht ausgenutzt werden
- **affected**: die Schwachstelle kann ausgenutzt werden und ist noch nicht behoben
- **fixed**: die Schwachstelle war vorhanden und wurde behoben
- **under_investigation**: die Bewertung läuft noch

Jede `not_affected`-Erklärung erfordert eine Begründung:

- `code_not_present`: der verwundbare Codepfad existiert in der verwendeten Version nicht
- `code_not_reachable`: der verwundbare Code existiert, ist jedoch im Ausführungskontext nicht erreichbar
- `requires_configuration`: die Ausnutzung erfordert eine Konfiguration, die in der eigenen Bereitstellung nicht verwendet wird
- `requires_environment`: die Ausnutzung erfordert eine Umgebungsbedingung, die nicht zutrifft
- `protected_by_mitigating_control`: eine ausgleichende Kontrolle ist vorhanden
- `protected_at_perimeter`: die betroffene Komponente ist von außerhalb der eigenen Umgebung nicht erreichbar

Eine VEX-Erklärung `not_affected` mit der Begründung `code_not_reachable`, datiert und signiert, stellt im Rahmen einer Prüfung nach Artikel 14 belastbares Nachweismaterial dar, dass die Schwachstelle bewertet und festgestellt wurde, dass sie keine Meldepflicht auslöst.

## Warum CycloneDX für die CRA-Konformität bevorzugt wird

Die Verpflichtung nach CRA Artikel 14 lautet:

1. Auf aktiv ausgenutzte Schwachstellen in den Komponenten des Produkts überwachen
2. Bei aktiver Ausnutzung die als Koordinator benannte CSIRT und ENISA über die einheitliche Meldeplattform benachrichtigen: eine Frühwarnung innerhalb von 24 Stunden, eine vollständigere Meldung innerhalb von 72 Stunden und einen Abschlussbericht innerhalb von 14 Tagen nach Verfügbarkeit einer Behebung

Das Design von CycloneDX stimmt damit überein:

- Die PURL-basierte Komponentenidentifikation lässt sich direkt auf Vulnerability-Datenbankabfragen abbilden
- VEX-Erklärungen bieten eine maschinenlesbare Möglichkeit, Überwachungsentscheidungen zu dokumentieren
- Tools wie [[Grype]] verarbeiten CycloneDX-SBOMs nativ und erzeugen CycloneDX-Vulnerability-Scan-Ergebnisse
- Die CycloneDX-BOM-Seriennummer (`serialNumber`) ermöglicht die Nachverfolgung von SBOM-Versionen über die Zeit

SPDX kann Vulnerability-Management abbilden, wurde jedoch primär für Lizenzkonformität entwickelt. CycloneDX wurde für Sicherheitsoperationen entwickelt. Wenn der primäre Anwendungsfall die Konformität mit Artikel 14 ist, ist CycloneDX die passendere Wahl.

## Erzeugen eines CycloneDX-SBOM

[[Syft]] von Anchore erzeugt standardmäßig CycloneDX 1.6 JSON:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` ist eine weitere Option, insbesondere für sprachspezifische Builds, bei denen der Dateisystemscan von Syft Anwendungsabhängigkeiten möglicherweise nicht erfasst:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Beide Tools erzeugen gültige CycloneDX 1.6-Ausgaben, die die Schemavalidierung bestehen und von nachgelagerten Tools einschließlich Grype, Dependency-Track und den meisten Vulnerability-Management-Plattformen akzeptiert werden.

## Wichtige Erkenntnisse

1. CycloneDX ist ein OWASP-Standard, der in JSON und XML verfügbar ist. Die aktuelle Version ist 1.6.
2. Die vier Hauptabschnitte sind: Metadata (zum SBOM), Components (das Inventar), Dependencies (der Graph) und optional Vulnerabilities.
3. VEX-Erklärungen ermöglichen die formale Dokumentation, ob eine bekannte [[CVE]] im konkreten Produktkontext ausnutzbar ist. Dies ist entscheidend für Nachweise im Rahmen von Artikel 14.
4. CycloneDX ist das bevorzugte Format für die CRA-Konformität, weil es für Vulnerability-Management-Workflows und nicht für Lizenzkonformität entwickelt wurde.
5. Sowohl Syft als auch cdxgen erzeugen CycloneDX 1.6-Ausgaben. Die meisten SBOM-Tools zielen primär auf CycloneDX als Ausgabeformat ab.
