# Lição 3.1: Construção do seu SBOM: Ferramentas e Integração em Pipelines

Saber o que um SBOM deve conter é uma coisa. Gerá-lo de forma fiável, como parte do seu processo de compilação, para cada lançamento, é outra. Esta lição aborda as ferramentas que geram SBOMs e a forma de integrar a geração de SBOMs num pipeline de CI/CD para que o resultado esteja sempre atualizado.

## As duas categorias de geração de SBOM

### Análise em tempo de origem

As ferramentas em tempo de origem leem os ficheiros de manifesto de dependências do seu código, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, e produzem um SBOM a partir das dependências declaradas. Estas ferramentas compreendem os ficheiros de bloqueio dos gestores de pacotes e podem produzir grafos completos de dependências transitivas a partir deles.

**cdxgen** (CycloneDX Generator) é a ferramenta em tempo de origem mais capaz. Suporta mais de 30 ecossistemas de linguagens: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP e outros. Lê o ficheiro de bloqueio do ecossistema e produz CycloneDX JSON.

```bash
# Projeto Node.js
cdxgen -t npm -o sbom.cdx.json .

# Projeto Python
cdxgen -t python -o sbom.cdx.json .

# Projeto Java Maven
cdxgen -t maven -o sbom.cdx.json .
```

A análise em tempo de origem é precisa para dependências de aplicação, mas omite pacotes do sistema operativo e bibliotecas de sistema que não constam dos manifestos específicos da linguagem.

### Digitalização de imagem/sistema de ficheiros

Os digitalizadores de imagem examinam um artefacto compilado, uma imagem de contentor, um diretório do sistema de ficheiros, um binário compilado, e identificam pacotes a partir das bases de dados de pacotes presentes. [[Syft]] da Anchore é a ferramenta principal para esta finalidade.

```bash
# Digitalizar uma imagem de contentor
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Digitalizar um diretório
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Digitalizar um tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifica pacotes ao ler:
- Bases de dados de pacotes do SO (dpkg para Debian/Ubuntu, rpm para RHEL/Fedora, apk para Alpine)
- Manifestos e ficheiros de bloqueio específicos da linguagem incorporados na imagem
- Assinaturas binárias de pacotes que foram compilados e instalados sem gestor de pacotes

A vantagem da digitalização de imagem: vê exatamente o que existe no artefacto que será implementado. A desvantagem: se um pacote foi instalado sem gestor de pacotes (comum em sistemas de compilação legados), o Syft pode não o detetar.

## Boa prática: combinar ambas as abordagens

Execute cdxgen sobre o seu código-fonte para as dependências de aplicação e Syft sobre a imagem de contentor para os pacotes do SO e de runtime. Una os dois SBOMs com uma ferramenta de união. O CycloneDX fornece uma operação de união que combina listas de componentes e remove duplicados.

O SBOM unido cobre:
- Dependências de aplicação (de cdxgen, grafo transitivo completo)
- Pacotes do SO (de Syft)
- Dependências de runtime (runtime Node.js, interpretador Python, JVM)

Esta é a imagem completa que o CRA e a monitorização do Artigo 14 exigem.

## Integração da geração de SBOM em CI/CD

O SBOM deve ser gerado automaticamente como parte do seu pipeline de compilação. A geração manual de SBOMs cria o risco de um SBOM desatualizado ou em falta quando for necessário para uma auditoria ou resposta a incidente.

### Exemplo em GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Anexe o SBOM ao artefacto de lançamento. Cada lançamento recebe um SBOM. O nome de ficheiro com a etiqueta SHA cria o registo de auditoria que liga cada SBOM à compilação correspondente.

### Exemplo em GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garante que o GitLab não elimina o artefacto. Combinado com a etiquetagem de lançamentos, isto fornece histórico de SBOM para todos os lançamentos durante o tempo necessário.

## Validação do seu SBOM

Antes de armazenar ou submeter um SBOM, valide-o:

```bash
# Validar o esquema CycloneDX
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

A CLI do CycloneDX está disponível em `@cyclonedx/cyclonedx-cli`. A validação do esquema deteta campos obrigatórios em falta, tipos incorretos e PURLs malformados antes de o SBOM entrar nos seus registos de documentação.

## Assinatura do seu SBOM

Um SBOM assinado constitui prova mais forte numa auditoria do que um não assinado. Se conseguir demonstrar que o SBOM foi gerado num momento específico e não foi alterado desde então, dispõe de uma cadeia de custódia mais robusta.

O Cosign (do projeto Sigstore) pode assinar e verificar ficheiros SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

O ficheiro de assinatura prova que o SBOM foi produzido pelo seu sistema de compilação e não foi alterado. Armazene a assinatura junto com o SBOM.

## Pontos-chave

1. As ferramentas em tempo de origem (cdxgen) leem manifestos de pacotes e produzem grafos completos de dependências transitivas. Os digitalizadores de imagem (Syft) examinam artefactos compilados e localizam pacotes do SO e de runtime.
2. A boa prática combina ambas: cdxgen para dependências de aplicação, Syft para pacotes do SO e de runtime, unidos num único SBOM.
3. A geração de SBOM deve ser integrada em CI/CD. A geração manual cria SBOMs desatualizados ou em falta sob pressão.
4. Anexe o SBOM a cada artefacto de lançamento, etiquetado com o SHA da compilação ou a versão. Isto cria o registo de auditoria exigido pela regra de retenção de 10 anos.
5. Valide com a CLI do CycloneDX antes do armazenamento. Assine com Cosign para criar uma cadeia de custódia.
