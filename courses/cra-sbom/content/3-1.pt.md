# Lição 3.1: Construir o seu SBOM: ferramentas e integração no pipeline

Saber o que um SBOM deve conter é uma coisa. Consegui-lo gerar de forma fiável, como parte do seu processo de build, para cada versão, é outra. Esta lição aborda as ferramentas que geram SBOM e como integrar a geração de SBOM num pipeline de CI/CD, para que o resultado esteja sempre atualizado.

## As duas categorias de geração de SBOM

### Análise em tempo de código-fonte

As ferramentas de tempo de código-fonte leem os ficheiros de manifesto de dependências do seu código, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, e produzem um SBOM a partir das dependências declaradas. Estas ferramentas compreendem os ficheiros de bloqueio dos gestores de pacotes e conseguem produzir grafos completos de dependências transitivas a partir deles.

**cdxgen** (CycloneDX Generator) é a ferramenta de tempo de código-fonte mais capaz. Suporta mais de 30 ecossistemas de linguagens: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP, entre outros. Lê o ficheiro de bloqueio do ecossistema e produz CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

A análise em tempo de código-fonte é exata para as dependências da aplicação, mas falha os pacotes do sistema operativo e as bibliotecas de sistema que não constam dos manifestos específicos da linguagem.

### Análise de imagem/sistema de ficheiros

Os analisadores de imagem examinam um artefacto construído, uma imagem de contentor, um diretório de sistema de ficheiros, um binário compilado, e identificam pacotes a partir das bases de dados de pacotes presentes. O [[Syft|Syft]] da Anchore é a ferramenta de referência para isto.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

O Syft identifica pacotes lendo:
- Bases de dados de pacotes do SO (dpkg para Debian/Ubuntu, rpm para RHEL/Fedora, apk para Alpine)
- Manifestos e ficheiros de bloqueio específicos da linguagem incorporados na imagem
- Assinaturas binárias de pacotes que foram compilados e instalados sem um gestor de pacotes

A vantagem da análise de imagem: vê exatamente o que está no artefacto que vai ser implementado. A desvantagem: se um pacote foi instalado sem um gestor de pacotes (algo comum em sistemas de build antigos), o Syft pode não o detetar.

## Boa prática: combinar as duas abordagens

Execute o cdxgen sobre o seu código-fonte para as dependências da aplicação, e o Syft sobre a sua imagem de contentor para os pacotes do SO e de runtime. Combine os dois SBOM utilizando uma ferramenta de fusão. O CycloneDX disponibiliza uma operação de fusão que junta as listas de componentes e elimina duplicados.

O SBOM combinado abrange:
- Dependências da aplicação (do cdxgen, grafo transitivo completo)
- Pacotes do SO (do Syft)
- Dependências de runtime (runtime Node.js, interpretador Python, JVM)

Este é o panorama completo que o CRA e a monitorização do Artigo 14 exigem.

## Integrar a geração de SBOM no CI/CD

O SBOM deve ser gerado automaticamente como parte do seu pipeline de build. A geração manual de SBOM cria o risco de um SBOM desatualizado ou em falta no momento em que precisa dele para uma auditoria ou resposta a incidentes.

### Exemplo com GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Anexe o SBOM ao artefacto da versão. Cada versão recebe um SBOM. O nome de ficheiro etiquetado com o SHA cria o registo de auditoria que liga cada SBOM ao respetivo build.

### Exemplo com GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garante que o GitLab não elimina o artefacto. Combinado com a sua etiquetagem de versões, isto dá-lhe o histórico de SBOM de cada versão, recuando tanto quanto precisar.

## Validar o seu SBOM

Antes de armazenar ou submeter um SBOM, valide-o:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

A CLI do CycloneDX está disponível em `@cyclonedx/cyclonedx-cli`. A validação de esquema deteta campos obrigatórios em falta, tipos incorretos e PURL malformados antes de o SBOM entrar nos seus registos de documentação.

## Assinar o seu SBOM

Um SBOM assinado é uma prova mais forte numa auditoria do que um não assinado. Se conseguir demonstrar que o SBOM foi gerado num momento específico no tempo e não foi modificado desde então, tem uma cadeia de custódia mais sólida.

O Cosign (do projeto Sigstore) consegue assinar e verificar ficheiros SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

O ficheiro de assinatura prova que o SBOM foi produzido pelo seu sistema de build e não foi alterado. Guarde a assinatura junto do SBOM.

## Pontos-chave

1. As ferramentas de tempo de código-fonte (cdxgen) leem os manifestos de pacotes e produzem grafos completos de dependências transitivas. Os analisadores de imagem (Syft) examinam artefactos construídos e encontram pacotes do SO e de runtime.
2. A boa prática combina ambos: cdxgen para as dependências da aplicação, Syft para os pacotes do SO e de runtime, fundidos num único SBOM.
3. A geração de SBOM tem de estar integrada no CI/CD. A geração manual cria SBOM desatualizados ou em falta sob pressão.
4. Anexe o SBOM a cada artefacto de versão, etiquetado com o SHA do build ou a versão. Isto cria o registo de auditoria que a regra de retenção de 10 anos exige.
5. Valide com a CLI do CycloneDX antes do armazenamento. Assine com o Cosign para criar uma cadeia de custódia.
