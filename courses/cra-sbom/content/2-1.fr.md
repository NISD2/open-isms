# Leçon 2.1 : CycloneDX : le format SBOM axé sur la sécurité

Le CRA exige un format « couramment utilisé et lisible par machine ». Deux formats répondent à cette exigence : [[CycloneDX]] et [[SPDX]]. Cette leçon porte sur CycloneDX : sa nature, les raisons de son orientation sécurité et son adéquation avec le flux de travail de notification des vulnérabilités de l'article 14 du CRA.

## Nature de CycloneDX

CycloneDX est un projet de l'OWASP. L'Open Web Application Security Project (OWASP) le maintient comme norme pour les cas d'usage liés à la sécurité. La version actuelle est la 1.6. Il est disponible en JSON et en XML.

CycloneDX a été conçu pour les flux de travail de gestion des vulnérabilités. Son modèle de données central repose sur la question suivante : « Compte tenu de cette liste de composants, lesquels présentent des vulnérabilités connues et puis-je y remédier ? » Chaque fonctionnalité majeure du format existe pour répondre à cette question.

## Structure d'un SBOM CycloneDX

Un document CycloneDX comporte quatre sections principales :

### Métadonnées

Informations sur le document SBOM lui-même et sur le produit qu'il décrit :

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

L'horodatage indique à l'auditeur la date de génération du SBOM. L'outil lui indique la méthode employée. Le bloc composant identifie l'objet décrit par le SBOM.

### Composants

La liste des composants logiciels. Chaque composant comprend :

- `type` : `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` ou `operating-system`
- `name` : le nom canonique du paquet
- `version` : la chaîne de version exacte
- `supplier` : l'éditeur
- `purl` : l'identifiant unique [[PURL]]
- `hashes` : le hachage SHA-256 ou autre du fichier composant
- `licenses` : les expressions de licence SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dépendances

CycloneDX 1.4+ inclut une section `dependencies` qui indique quel composant dépend de quel autre. Il s'agit de la représentation lisible par machine du graphe de dépendances. Elle permet à un outil de distinguer les composants de premier niveau des composants transitifs sans relancer l'outil de build.

### Vulnérabilités

CycloneDX peut intégrer directement des données de vulnérabilité dans le SBOM. Chaque entrée de vulnérabilité référence un [[CVE]] et le composant concerné. Cette fonctionnalité est utile pour une documentation ponctuelle, mais elle reste peu utilisée en pratique. La plupart des équipes conservent le SBOM et les résultats de l'analyse de vulnérabilités comme artefacts distincts.

## VEX : la fonctionnalité qui distingue CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, constitue la fonctionnalité CycloneDX la plus distinctive pour la conformité au CRA. Une déclaration VEX est une déclaration lisible par machine qui documente la relation entre une vulnérabilité connue et votre produit spécifique.

VEX dans CycloneDX prend en charge quatre valeurs d'état :

- **not_affected** : le composant est présent, mais la vulnérabilité ne peut pas être exploitée dans ce produit
- **affected** : la vulnérabilité peut être exploitée et vous ne l'avez pas encore atténuée
- **fixed** : la vulnérabilité était présente et vous l'avez corrigée
- **under_investigation** : vous êtes encore en train d'évaluer

Chaque déclaration `not_affected` exige une justification :

- `code_not_present` : le chemin de code vulnérable n'existe pas dans la version utilisée
- `code_not_reachable` : le code vulnérable existe, mais il n'est pas accessible dans votre contexte d'exécution
- `requires_configuration` : l'exploitation exige une configuration que votre déploiement n'utilise pas
- `requires_environment` : l'exploitation exige une condition d'environnement qui ne s'applique pas
- `protected_by_mitigating_control` : vous avez mis en place un contrôle compensatoire
- `protected_at_perimeter` : le composant concerné n'est pas accessible depuis l'extérieur de votre environnement

Une déclaration VEX `not_affected` assortie d'une justification `code_not_reachable`, datée et signée, constitue une preuve solide lors d'un audit au titre de l'article 14 que vous avez évalué la vulnérabilité et conclu qu'elle ne déclenchait pas l'obligation de notification.

## Pourquoi CycloneDX est préféré pour la conformité au CRA

L'obligation de l'article 14 du CRA est la suivante :

1. Surveiller les vulnérabilités activement exploitées dans les composants de votre produit
2. En cas d'exploitation active, notifier le CSIRT désigné comme coordinateur et ENISA via la plateforme de notification unique : un avertissement précoce dans les 24 heures, une notification plus complète dans les 72 heures et un rapport final dans les 14 jours suivant la disponibilité d'un correctif

La conception de CycloneDX s'aligne sur ces exigences :

- L'identification des composants par PURL correspond directement aux recherches dans les bases de données de vulnérabilités
- Les déclarations VEX offrent un moyen lisible par machine de documenter les décisions de surveillance
- Des outils tels que [[Grype]] consomment nativement les SBOM CycloneDX et produisent des résultats d'analyse de vulnérabilités au format CycloneDX
- Le numéro de série du BOM CycloneDX (`serialNumber`) permet de suivre les versions du SBOM au fil du temps

SPDX peut gérer les vulnérabilités, mais il a été conçu principalement pour la conformité des licences. CycloneDX a été conçu pour les opérations de sécurité. Si votre cas d'usage principal est la conformité à l'article 14, CycloneDX constitue le choix le plus naturel.

## Génération d'un SBOM CycloneDX

[[Syft]] d'Anchore produit par défaut du CycloneDX 1.6 JSON :

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` constitue une autre option, en particulier pour les builds spécifiques à un langage où l'analyse du système de fichiers par Syft peut omettre des dépendances applicatives :

```bash
cdxgen -t java -o sbom.cdx.json .
```

Les deux outils produisent une sortie CycloneDX 1.6 valide qui passe la validation du schéma et est acceptée par les outils en aval, notamment Grype, Dependency-Track et la plupart des plateformes de gestion des vulnérabilités.

## Points clés à retenir

1. CycloneDX est une norme de l'OWASP disponible en JSON et en XML. La version actuelle est la 1.6.
2. Les quatre sections principales sont : metadata (sur le SBOM), components (l'inventaire), dependencies (le graphe) et, en option, vulnerabilities.
3. Les déclarations VEX permettent de documenter formellement si un [[CVE]] connu est exploitable dans le contexte spécifique de votre produit. Elles sont essentielles pour les preuves d'audit au titre de l'article 14.
4. CycloneDX est le format préféré pour la conformité au CRA car il a été conçu pour les flux de travail de gestion des vulnérabilités, et non pour la conformité des licences.
5. Syft et cdxgen produisent tous deux une sortie CycloneDX 1.6. La plupart des outils SBOM ciblent CycloneDX comme format de sortie principal.
