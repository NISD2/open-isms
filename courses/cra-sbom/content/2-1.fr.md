# Leçon 2.1 : CycloneDX : le format SBOM axé sur la sécurité

Le CRA exige un format « couramment utilisé et lisible par machine ». Deux formats satisfont à cette exigence : [[CycloneDX]] et [[SPDX]]. Cette leçon traite de CycloneDX, ce qu'il est, ce qui le rend axé sur la sécurité, et pourquoi il correspond bien au flux de signalement des vulnérabilités de l'article 14 du CRA.

## Ce qu'est CycloneDX

CycloneDX est un projet de l'OWASP. L'Open Web Application Security Project (OWASP) le maintient comme standard pour les cas d'usage de sécurité. La version actuelle est la 1.6. Il est disponible en JSON et XML.

CycloneDX a été conçu pour servir les flux de gestion des vulnérabilités. Son modèle de données fondamental est construit autour de la question : « Étant donné cette liste de composants, lesquels ont des vulnérabilités connues, et puis-je agir dessus ? » Chaque fonctionnalité majeure du format existe pour répondre à cette question.

## Structure d'un SBOM CycloneDX

Un document CycloneDX comporte quatre sections majeures :

### Métadonnées

Information sur le document SBOM lui-même et le produit qu'il décrit :

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

L'horodatage indique à l'auditeur quand le SBOM a été généré. L'outil lui indique comment. Le bloc component identifie ce que le SBOM décrit.

### Composants

La liste des composants logiciels. Chaque composant a :

- `type` : `library`, `framework`, `application`, `container`, `device`, `firmware`, `file`, ou `operating-system`
- `name` : le nom canonique du paquet
- `version` : la chaîne de version exacte
- `supplier` : qui le publie
- `purl` : l'identifiant unique [[PURL]]
- `hashes` : SHA-256 ou autre empreinte du fichier de composant
- `licenses` : expressions de licence SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dépendances

CycloneDX 1.4+ inclut une section `dependencies` qui cartographie quel composant dépend de quel autre. C'est la représentation lisible par machine du graphe de dépendances, c'est ce qui permet à un outil de distinguer les composants de premier niveau des transitifs sans réexécuter l'outil de build.

### Vulnérabilités

CycloneDX peut intégrer des données de vulnérabilité directement dans le SBOM. Chaque entrée de vulnérabilité référence une [[CVE]] et le composant qu'elle affecte. C'est utile pour une documentation à un instant donné, mais moins courant en pratique, la plupart des équipes gardent le SBOM et la sortie d'analyse des vulnérabilités comme des artefacts distincts.

## VEX : la fonctionnalité qui distingue CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, est la fonctionnalité CycloneDX la plus distinctive pour la conformité au CRA. Une déclaration VEX est une déclaration lisible par machine qui documente la relation entre une vulnérabilité connue et votre produit précis.

VEX dans CycloneDX prend en charge quatre valeurs de statut :

- **not_affected** : le composant est présent mais la vulnérabilité ne peut pas être exploitée dans ce produit
- **affected** : la vulnérabilité peut être exploitée et vous ne l'avez pas encore atténuée
- **fixed** : la vulnérabilité était présente et vous l'avez corrigée
- **under_investigation** : vous êtes encore en cours d'évaluation

Chaque déclaration `not_affected` requiert une justification :

- `code_not_present` : le chemin de code vulnérable n'existe pas dans la version que vous utilisez
- `code_not_reachable` : le code vulnérable existe mais ne peut pas être atteint dans votre contexte d'exécution
- `requires_configuration` : l'exploitation requiert une configuration que votre déploiement n'utilise pas
- `requires_environment` : l'exploitation requiert une condition d'environnement qui ne s'applique pas
- `protected_by_mitigating_control` : vous avez une mesure compensatoire en place
- `protected_at_perimeter` : le composant affecté n'est pas atteignable depuis l'extérieur de votre environnement

Une déclaration VEX de `not_affected` avec une justification `code_not_reachable`, datée et signée, est une preuve solide lors d'un audit au titre de l'article 14 que vous avez évalué la vulnérabilité et conclu qu'elle ne déclenchait pas l'obligation de signalement.

## Pourquoi CycloneDX est privilégié pour la conformité au CRA

L'obligation de l'article 14 du CRA est de :

1. Surveiller les vulnérabilités activement exploitées dans les composants de votre produit
2. Signaler à l'ENISA via la plateforme de signalement unique dans un délai de 24 heures si l'une d'elles est activement exploitée

La conception de CycloneDX s'aligne sur cela :

- L'identification des composants par PURL correspond directement aux recherches dans les bases de données de vulnérabilités
- Les déclarations VEX vous donnent une manière lisible par machine de documenter les décisions de surveillance
- Des outils comme [[Grype]] consomment nativement les SBOM CycloneDX et produisent des résultats d'analyse de vulnérabilités CycloneDX
- Le numéro de série de BOM CycloneDX (`serialNumber`) vous permet de suivre les versions du SBOM dans le temps

SPDX peut faire de la gestion des vulnérabilités, mais il a été conçu principalement pour la conformité des licences. CycloneDX a été conçu pour les opérations de sécurité. Si votre cas d'usage principal est la conformité à l'article 14, CycloneDX est le choix le plus naturel.

## Générer un SBOM CycloneDX

[[Syft]] d'Anchore produit du CycloneDX 1.6 JSON par défaut :

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` est une autre option, en particulier pour les builds spécifiques à un langage où l'analyse du système de fichiers de Syft peut manquer les dépendances applicatives :

```bash
cdxgen -t java -o sbom.cdx.json .
```

Les deux outils produisent une sortie CycloneDX 1.6 valide qui passe la validation de schéma et est acceptée par les outils en aval, dont Grype, Dependency-Track et la plupart des plateformes de gestion des vulnérabilités.

## Points clés à retenir

1. CycloneDX est un standard de l'OWASP disponible en JSON et XML. La version actuelle est la 1.6.
2. Les quatre sections principales sont : metadata (à propos du SBOM), components (l'inventaire), dependencies (le graphe), et facultativement vulnerabilities.
3. Les déclarations VEX vous permettent de documenter formellement si une [[CVE]] connue est exploitable dans le contexte précis de votre produit : essentiel comme preuve d'audit au titre de l'article 14.
4. CycloneDX est le format privilégié pour la conformité au CRA, car il a été conçu pour les flux de gestion des vulnérabilités, pas pour la conformité des licences.
5. Syft et cdxgen produisent tous deux une sortie CycloneDX 1.6. La plupart des outils SBOM visent CycloneDX comme format de sortie principal.
