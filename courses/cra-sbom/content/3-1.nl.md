# Les 3.1: Uw SBOM opbouwen: Tools en pipeline-integratie

Weten wat een SBOM moet bevatten is één ding. Het betrouwbaar genereren ervan als onderdeel van uw bouwproces, voor elke release, is iets anders. Deze les behandelt de tools die SBOMs genereren en hoe u SBOM-generatie integreert in een CI/CD-pipeline zodat de output altijd actueel is.

## De twee categorieën van SBOM-generatie

### Analyse op broncode-niveau

Tools voor broncode-niveau lezen de manifestbestanden van uw afhankelijkheden, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, en produceren een SBOM op basis van de opgegeven afhankelijkheden. Deze tools begrijpen de lockbestanden van package managers en kunnen volledige transitieve afhankelijkheidsgrafieken opstellen.

**cdxgen** (CycloneDX Generator) is de meest capabele tool voor broncode-niveau. Het ondersteunt meer dan 30 taale ecosystemen: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP en meer. Het leest het lockbestand voor het ecosysteem en produceert CycloneDX JSON.

```bash
# Node.js-project
cdxgen -t npm -o sbom.cdx.json .

# Python-project
cdxgen -t python -o sbom.cdx.json .

# Java Maven-project
cdxgen -t maven -o sbom.cdx.json .
```

Analyse op broncode-niveau is nauwkeurig voor toepassingsafhankelijkheden, maar mist besturingssysteem-pakketten en systeembibliotheken die niet in de taalspecifieke manifests voorkomen.

### Scannen van images en bestandssystemen

Image-scanners onderzoeken een gebouwd artefact, een container-image, een bestandssysteemmap of een gecompileerde binary en identificeren pakketten uit de aanwezige packagedatabases. [[Syft]] van Anchore is de toonaangevende tool hiervoor.

```bash
# Een container-image scannen
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Een map scannen
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Een tarball scannen
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identificeert pakketten door het lezen van:
- OS-packagedatabases (dpkg voor Debian/Ubuntu, rpm voor RHEL/Fedora, apk voor Alpine)
- Taalspecifieke package-manifests en lockbestanden die in de image zijn opgenomen
- Binaire handtekeningen voor pakketten die zonder package manager zijn gecompileerd en geïnstalleerd

Het voordeel van image-scanning: u ziet precies wat zich in het artefact bevindt dat wordt uitgerold. Het nadeel: als een pakket zonder package manager is geïnstalleerd (vaak voorkomend in legacy-bouwsystemen), kan Syft het missen.

## Beste praktijk: beide benaderingen combineren

Voer cdxgen uit op uw broncode voor toepassingsafhankelijkheden en Syft op uw container-image voor OS- en runtime-pakketten. Voeg de twee SBOMs samen met een merge-tool. CycloneDX biedt een merge-operatie die componentenlijsten combineert en duplicaten verwijdert.

De samengevoegde SBOM dekt:
- Toepassingsafhankelijkheden (van cdxgen, volledige transitieve grafiek)
- OS-pakketten (van Syft)
- Runtime-afhankelijkheden (Node.js-runtime, Python-interpreter, JVM)

Dit is het volledige beeld dat de CRA en Artikel 14-monitoring vereisen.

## SBOM-generatie integreren in CI/CD

De SBOM moet automatisch als onderdeel van uw build-pipeline worden gegenereerd. Handmatige SBOM-generatie brengt het risico met zich mee dat een verouderde of ontbrekende SBOM ontstaat wanneer u die nodig hebt voor een audit of incidentrespons.

### GitHub Actions-voorbeeld

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Voeg de SBOM toe als release-artefact. Elke release krijgt een SBOM. De met SHA gelabelde bestandsnaam creëert het audittrail dat elke SBOM koppelt aan de bijbehorende build.

### GitLab CI-voorbeeld

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` zorgt ervoor dat GitLab het artefact niet verwijdert. In combinatie met uw release-tagging levert dit SBOM-geschiedenis op voor elke release, zo ver terug als nodig.

## Uw SBOM valideren

Valideer de SBOM voordat u deze opslaat of indient:

```bash
# CycloneDX-schema valideren
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

De CycloneDX CLI is beschikbaar via `@cyclonedx/cyclonedx-cli`. Schemavalidatie detecteert ontbrekende verplichte velden, onjuiste typen en onjuist gevormde PURLs voordat de SBOM in uw documentatierecords terechtkomt.

## Uw SBOM ondertekenen

Een ondertekende SBOM vormt sterker bewijs bij een audit dan een niet-ondertekende. Als u kunt aantonen dat de SBOM op een specifiek tijdstip is gegenereerd en sindsdien niet is gewijzigd, beschikt u over een sterkere bewijsketen.

Cosign (van het Sigstore-project) kan SBOM-bestanden ondertekenen en verifiëren:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Het handtekeningsbestand bewijst dat de SBOM door uw buildsysteem is geproduceerd en niet is gewijzigd. Bewaar de handtekening samen met de SBOM.

## Belangrijkste aandachtspunten

1. Tools voor broncode-niveau (cdxgen) lezen package-manifests en produceren volledige transitieve afhankelijkheidsgrafieken. Image-scanners (Syft) onderzoeken gebouwde artefacten en vinden OS- en runtime-pakketten.
2. De beste praktijk combineert beide: cdxgen voor toepassingsafhankelijkheden, Syft voor OS- en runtime-pakketten, samengevoegd tot één SBOM.
3. SBOM-generatie moet in CI/CD worden geïntegreerd. Handmatige generatie leidt tot verouderde of ontbrekende SBOMs onder druk.
4. Voeg de SBOM toe aan elk release-artefact, gelabeld met de build-SHA of versie. Dit creëert het audittrail dat de 10-jarige bewaartermijnregel vereist.
5. Valideer met de CycloneDX CLI vóór opslag. Onderteken met Cosign om een bewijsketen te creëren.
