# Lektion 3.2: SBOM aktuell halten und auf Schwachstellen überwachen

Ein SBOM, das einmal erzeugt und danach nicht mehr aktualisiert wird, verfehlt seinen eigentlichen Zweck. Das Komponenteninventar ändert sich bei jeder Abhängigkeitsaktualisierung, jedem Betriebssystem-Patch oder jeder Änderung der Build-Toolchain. Gleichzeitig werden kontinuierlich Schwachstellen in diesen Komponenten veröffentlicht. Diese Lektion erläutert, wie der SBOM aktuell gehalten wird und wie er als Überwachungsinstrument nach Artikel 14 eingesetzt werden kann.

## Warum der SBOM veraltet

Ein SBOM gibt den Zustand des Produkts zu einem bestimmten Zeitpunkt wieder. Sobald ein Pull-Request mit einer aktualisierten Abhängigkeit zusammengeführt wird, ist der SBOM veraltet. Sobald eine neue [[CVE]] für eine Komponente im SBOM veröffentlicht wird, hat sich die Schwachstellenexposition geändert, der SBOM jedoch nicht.

Zwei Ursachen führen zu SBOM-Drift:

1. **Komponentenänderungen**: Abhängigkeitsaktualisierungen, Betriebssystem-Patches, Aktualisierungen von Build-Tools, Änderungen bei der Auflösung transitiver Abhängigkeiten, wenn eine Top-Level-Version festgelegt wird und sich die Unterabhängigkeiten verschieben.
2. **Veröffentlichung von Schwachstellen**: Eine CVE für eine Komponente, die gestern noch sicher war, kann heute veröffentlicht werden.

Die Antwort auf Drift-Typ 1 ist die automatisierte Neuerzeugung. Die Antwort auf Drift-Typ 2 ist das automatisierte Scannen.

## Automatisierte SBOM-Neuerzeugung

Lösen Sie die SBOM-Erzeugung bei jedem Build aus, der ein Release-Artefakt erzeugt. Erzeugen Sie den SBOM nicht nach einem Zeitplan, sondern als Teil des Builds aus demselben Artefakt, das der Build erzeugt.

Die Regel lautet: ein SBOM pro Release-Artefakt, erzeugt zur Build-Zeit und zusammen mit dem Artefakt gespeichert.

Versendet das Produkt Patches zwischen Minor-Versionen, was zur Erfüllung der Anforderungen an Sicherheitsaktualisierungen nach Anhang I Teil I CRA erforderlich ist, erhält jedes Patch-Release einen eigenen SBOM. Dieser SBOM bildet das Komponenteninventar dieses Patches ab. Wird eine Schwachstelle für eine Komponente offengelegt, die in Patch 2.4.1 behoben, in 2.4.0 jedoch nicht behoben wurde, benötigen Sie den SBOM für 2.4.0, um festzustellen, dass diese Version betroffen war.

## Die Schwachstellenüberwachungsschleife

[[Grype]] von Anchore ist das Standardwerkzeug für die Überwachungsschleife. Es nimmt einen CycloneDX-SBOM als Eingabe entgegen, gleicht jede Komponente mit mehreren Schwachstellen-Feeds ab und gibt einen Bericht aus:

```bash
grype sbom:sbom.cdx.json
```

Ausgabeformat-Optionen:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

Die CycloneDX-Ausgabe von Grype kann als Schwachstellen-Ergänzung in den SBOM zurückgeführt werden. Dadurch entsteht ein einzelnes Dokument, das sowohl das Komponenteninventar als auch den aktuellen Schwachstellenstatus enthält.

Grype bezieht Daten aus:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Sicherheitsempfehlungen von Red Hat, Debian, Ubuntu, Alpine
- Empfehlungsdatenbanken von Amazon, Oracle, SUSE
- Sprachspezifische Empfehlungs-Feeds (PyPI, npm, Go, Maven, NuGet, Ruby)

## Automatisierung der Überwachungsschleife

Planen Sie Grype so ein, dass es die produktiven SBOMs in einem Rhythmus scannt, der der Überwachungspflicht nach Artikel 14 entspricht:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

Ein fehlgeschlagener Exit-Code löst eine Benachrichtigung an das Team aus. Der Benachrichtigungsfluss sollte an die Stelle geleitet werden, die für die Berichtsentscheidung nach Artikel 14 verantwortlich ist.

## Schweregrad-Schwellenwerte und der Auslöser nach Artikel 14

Nicht jede Schwachstelle erfordert einen Bericht nach Artikel 14. Die Pflicht wird durch eine [[actively exploited vulnerability|aktiv ausgenutzte Schwachstelle]] ausgelöst, also eine Schwachstelle, die ein böswilliger Akteur derzeit ohne Berechtigung gegen reale Systeme einsetzt.

Der Schweregrad einer CVE (CVSS-Score) ist ein Indikator, nicht der Auslöser. Eine CVSS-9.8-Schwachstelle, für die kein öffentlicher Exploit-Code vorliegt und die nicht in Angriffen genutzt wird, löst keine Pflicht nach Artikel 14 aus. Eine CVSS-6.5-Schwachstelle, die im CISA Known Exploited Vulnerabilities (KEV) Katalog steht und in Ransomware-Kampagnen aktiv genutzt wird, hingegen schon.

Der Überwachungsprozess sollte:

1. **Alle Schweregrade oberhalb eines Schwellenwerts erfassen**: Mindestens Critical und High
2. **KEV prüfen**: Der CISA-KEV-Katalog listet derzeit ausgenutzte Schwachstellen. Grype markiert KEV-Einträge. CISA veröffentlicht den KEV als JSON-Feed unter `kev.cisa.gov/api/v1/catalog`.
3. **Anwendbarkeit bewerten**: Ist die betroffene Komponente im Produkt tatsächlich erreichbar? Wird der verwundbare Code-Pfad ausgeführt? Dokumentieren Sie diese Bewertung.
4. **Bei aktiver Ausnutzung eskalieren**: Befindet sich eine Komponente im SBOM, für die eine CVE im KEV-Katalog steht und die im Produkt erreichbar ist, erfolgt sofortige Eskalation für die 24-Stunden-Berichtsentscheidung nach Artikel 14.
5. **Entscheidung dokumentieren**: Ob berichtet wird oder festgestellt wird, dass keine Betroffenheit vorliegt: die Entscheidung und die Begründung sind zu dokumentieren. Nutzen Sie eine [[VEX]]-Aussage, um „nicht betroffen“-Entscheidungen in maschinenlesbarer Form festzuhalten.

## Einsatz von Dependency-Track für die kontinuierliche Überwachung

Für Organisationen mit mehreren Produkten bietet OWASP Dependency-Track ein zentrales Dashboard. SBOMs werden in Dependency-Track hochgeladen, das kontinuierlich die Schwachstellen-Feeds überwacht und bei einer neuen CVE, die eine Komponente in einem der hochgeladenen SBOMs betrifft, benachrichtigt.

Dependency-Track integriert sich mit:
- JIRA (erstellt Tickets für neue kritische Befunde)
- Slack und Teams (versendet Benachrichtigungen)
- REST-API (Abfrage des Schwachstellenstatus programmatisch)

Bei einem Hersteller mit fünf oder mehr vom CRA erfassten Produkten reduziert Dependency-Track den betrieblichen Aufwand der Überwachungsschleife nach Artikel 14 von einem manuellen täglichen Prozess auf ein automatisiertes Benachrichtigungssystem.

## Wichtige Erkenntnisse

1. SBOMs altern, wenn sich Komponenten ändern und wenn neue CVEs veröffentlicht werden. Erzeugen Sie sie automatisch zur Build-Zeit, einen SBOM pro Release-Artefakt.
2. [[Grype]] scannt einen SBOM gegen mehrere Schwachstellen-Feeds und meldet Treffer. Führen Sie es täglich oder bei jeder Bereitstellung aus.
3. Der Auslöser nach Artikel 14 ist eine aktiv ausgenutzte Schwachstelle, nicht allein der CVSS-Score. Prüfen Sie den CISA-KEV-Katalog, um festzustellen, welche CVEs derzeit in Angriffen genutzt werden.
4. Dokumentieren Sie jede Bewertung: ob berichtet wird oder keine Betroffenheit festgestellt wird. Nutzen Sie [[VEX]]-Aussagen für die maschinenlesbare Dokumentation von „nicht betroffen“.
5. Für Portfolios mit mehreren Produkten bietet OWASP Dependency-Track eine zentrale kontinuierliche Überwachung, die die tägliche Scanschleife in ein automatisiertes Benachrichtigungssystem überführt.
