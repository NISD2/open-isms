# Lezione 3.2: Mantenere aggiornato l'SBOM e monitorare le vulnerabilità

Un SBOM generato una sola volta e mai più aggiornato non adempie al suo scopo principale. L'inventario dei componenti cambia a ogni aggiornamento di dipendenza, patch del sistema operativo o modifica della toolchain di build. Le vulnerabilità in tali componenti vengono pubblicate in modo continuo. Questa lezione illustra come mantenere l'SBOM aggiornato e come utilizzarlo come strumento di monitoraggio ai sensi dell'Articolo 14.

## Perché l'SBOM diventa obsoleto

Un SBOM riflette lo stato del prodotto in un momento specifico. Nel momento in cui si unisce una pull request che aggiorna una dipendenza, l'SBOM è obsoleto. Nel momento in cui viene pubblicato un nuovo [[CVE]] per un componente presente nell'SBOM, l'esposizione alle vulnerabilità è cambiata, ma l'SBOM no.

Due fattori causano la deriva dell'SBOM:

1. **Modifiche ai componenti**: aggiornamenti delle dipendenze, patch del sistema operativo, aggiornamenti degli strumenti di build, modifiche alla risoluzione delle dipendenze transitive quando si blocca una versione di primo livello e le sue sotto-dipendenze variano.
2. **Pubblicazione di vulnerabilità**: un CVE relativo a un componente che era sicuro ieri può essere pubblicato oggi.

La risposta alla deriva di tipo 1 è la rigenerazione automatizzata. La risposta alla deriva di tipo 2 è la scansione automatizzata.

## Rigenerazione automatizzata dell'SBOM

Attivare la generazione dell'SBOM come parte di ogni build che produce un artefatto di release. Non generare l'SBOM secondo una pianificazione, ma come parte della build, a partire dallo stesso artefatto prodotto dalla build.

La regola è: un SBOM per artefatto di release, generato al momento della build e archiviato insieme all'artefatto.

Se il prodotto distribuisce patch tra versioni minori, come dovrebbe fare per soddisfare i requisiti di aggiornamento della sicurezza previsti dal CRA Allegato I Parte I, ogni release di patch riceve il proprio SBOM. Tale SBOM riflette l'inventario dei componenti di quella patch. Quando viene divulgata una vulnerabilità per un componente corretto nella patch 2.4.1 ma non nella 2.4.0, è necessario l'SBOM della 2.4.0 per sapere che quella versione era interessata.

## Il ciclo di monitoraggio delle vulnerabilità

[[Grype]] di Anchore è lo strumento standard per il ciclo di monitoraggio. Accetta in input un SBOM CycloneDX, confronta ogni componente con più feed di vulnerabilità e produce un report:

```bash
grype sbom:sbom.cdx.json
```

Opzioni di formato di output:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

L'output CycloneDX di Grype può essere reintegrato nell'SBOM come arricchimento delle vulnerabilità, ottenendo un unico documento che contiene sia l'inventario dei componenti sia lo stato attuale delle vulnerabilità.

Grype attinge da:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- advisory di sicurezza di Red Hat, Debian, Ubuntu, Alpine
- database di advisory di Amazon, Oracle, SUSE
- feed di advisory specifici per linguaggio (PyPI, npm, Go, Maven, NuGet, Ruby)

## Esecuzione automatica del ciclo di monitoraggio

Pianificare l'esecuzione di Grype sui SBOM di produzione con una cadenza coerente con l'obbligo di monitoraggio previsto dall'Articolo 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

Il fallimento del codice di uscita attiva una notifica al team. Il flusso di notifica deve essere instradato verso il responsabile della decisione di segnalazione ai sensi dell'Articolo 14.

## Soglie di gravità e attivazione dell'Articolo 14

Non ogni vulnerabilità richiede una segnalazione ai sensi dell'Articolo 14. L'obbligo si attiva in presenza di una [[actively exploited vulnerability|vulnerabilità attivamente sfruttata]], ovvero una vulnerabilità che un attore malevolo sta attualmente utilizzando contro sistemi reali senza autorizzazione.

La gravità del CVE (punteggio CVSS) è un segnale, non l'attivatore. Una vulnerabilità con CVSS 9.8 priva di codice di exploit pubblico e non utilizzata in attacchi non attiva l'Articolo 14. Una vulnerabilità con CVSS 6.5 presente nel catalogo Known Exploited Vulnerabilities (KEV) di CISA e attualmente utilizzata in campagne ransomware sì.

Il processo di monitoraggio deve:

1. **Rilevare tutte le gravità superiori a una soglia**: almeno Critical e High
2. **Verificare il KEV**: il catalogo CISA KEV elenca le vulnerabilità attualmente sfruttate. Grype segnala le voci KEV. CISA pubblica il KEV come feed JSON all'indirizzo `kev.cisa.gov/api/v1/catalog`.
3. **Valutare l'applicabilità**: il componente vulnerabile è effettivamente raggiungibile nel prodotto? Il percorso di codice vulnerabile viene eseguito? Documentare questa valutazione.
4. **Escalare in caso di sfruttamento attivo**: se un componente presente nell'SBOM ha un CVE incluso nel catalogo KEV e il componente è raggiungibile nel prodotto, escalare immediatamente per la decisione di segnalazione entro 24 ore prevista dall'Articolo 14.
5. **Documentare la decisione**: sia che si proceda alla segnalazione sia che si concluda per l'assenza di impatto, documentare la decisione e la motivazione. Utilizzare un'istruzione [[VEX]] per registrare le decisioni di "non interessato" in forma leggibile da macchina.

## Utilizzo di Dependency-Track per il monitoraggio continuo

Per le organizzazioni che gestiscono più prodotti, OWASP Dependency-Track fornisce una dashboard centralizzata. Si caricano gli SBOM su Dependency-Track, che monitora continuamente i feed di vulnerabilità e invia avvisi quando un nuovo CVE interessa un componente in qualsiasi SBOM caricato.

Dependency-Track si integra con:
- JIRA (crea ticket per i nuovi risultati critici)
- Slack e Teams (invia avvisi)
- REST API (consente di interrogare programmaticamente lo stato delle vulnerabilità)

Per un produttore con cinque o più prodotti soggetti al CRA, Dependency-Track riduce il carico operativo del ciclo di monitoraggio dell'Articolo 14 da un processo manuale quotidiano a un sistema di avvisi automatizzato.

## Punti chiave

1. Gli SBOM invecchiano quando cambiano i componenti e quando vengono pubblicati nuovi CVE. Rigenerarli automaticamente al momento della build, un SBOM per artefatto di release.
2. [[Grype]] analizza un SBOM rispetto a più feed di vulnerabilità e segnala le corrispondenze. Eseguirlo quotidianamente o a ogni deployment.
3. L'attivatore dell'Articolo 14 è una vulnerabilità attivamente sfruttata, non il solo punteggio CVSS. Consultare il catalogo CISA KEV per identificare quali CVE sono attualmente utilizzati in attacchi.
4. Documentare ogni valutazione: sia che si proceda alla segnalazione sia che si concluda per l'assenza di impatto. Utilizzare istruzioni [[VEX]] per la documentazione leggibile da macchina delle decisioni di non interessato.
5. Per portafogli multi-prodotto, OWASP Dependency-Track fornisce un monitoraggio continuo centralizzato che trasforma il ciclo di scansione quotidiano in un sistema di avvisi automatizzato.
