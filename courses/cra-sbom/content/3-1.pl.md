# Lekcja 3.1: Tworzenie SBOM: narzędzia i integracja z potokiem

Znajomość wymagań dotyczących zawartości SBOM to jedno. Zapewnienie jego niezawodnego generowania w ramach procesu budowania dla każdego wydania to drugie. Lekcja omawia narzędzia generujące SBOM oraz sposób integracji generowania SBOM z potokiem CI/CD, aby wynik był zawsze aktualny.

## Dwie kategorie generowania SBOM

### Analiza w czasie źródła

Narzędzia działające w czasie źródła odczytują pliki manifestów zależności kodu, takie jak `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, i tworzą SBOM na podstawie zadeklarowanych zależności. Narzędzia te rozumieją pliki blokady menedżerów pakietów i potrafią wygenerować pełne grafy zależności przechodnich.

**cdxgen** (CycloneDX Generator) jest najbardziej zaawansowanym narzędziem działającym w czasie źródła. Obsługuje ponad 30 ekosystemów językowych: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP i inne. Odczytuje plik blokady dla danego ekosystemu i generuje CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Analiza w czasie źródła zapewnia dokładność w zakresie zależności aplikacji, lecz pomija pakiety systemu operacyjnego oraz biblioteki systemowe niewymienione w manifestach specyficznych dla języka.

### Skanowanie obrazu lub systemu plików

Skanery obrazów analizują zbudowany artefakt, obraz kontenera, katalog systemu plików lub skompilowany plik binarny i identyfikują pakiety na podstawie baz pakietów obecnych w systemie. [[Syft]] firmy Anchore jest wiodącym narzędziem w tej kategorii.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identyfikuje pakiety poprzez odczyt:
- baz pakietów systemu operacyjnego (dpkg dla Debian/Ubuntu, rpm dla RHEL/Fedora, apk dla Alpine)
- manifestów pakietów i plików blokady specyficznych dla języka osadzonych w obrazie
- sygnatur binarnych pakietów zainstalowanych bez użycia menedżera pakietów

Zaletą skanowania obrazu jest możliwość zobaczenia dokładnie tego, co znajduje się w artefakcie przeznaczonym do wdrożenia. Wadą jest ryzyko pominięcia pakietu zainstalowanego bez menedżera pakietów (częste w starszych systemach budowania).

## Najlepsza praktyka: połączenie obu podejść

Uruchom cdxgen na kodzie źródłowym w celu uzyskania zależności aplikacji oraz Syft na obrazie kontenera w celu uzyskania pakietów systemu operacyjnego i środowiska uruchomieniowego. Połącz oba SBOM za pomocą narzędzia do scalania. CycloneDX udostępnia operację scalania łączącą listy komponentów i usuwającą duplikaty.

Scalony SBOM obejmuje:
- zależności aplikacji (z cdxgen, pełny graf przechodni)
- pakiety systemu operacyjnego (z Syft)
- zależności środowiska uruchomieniowego (środowisko Node.js, interpreter Python, JVM)

Daje to pełny obraz wymagany przez CRA oraz monitorowanie na podstawie Artykuł 14.

## Integracja generowania SBOM z CI/CD

SBOM powinien być generowany automatycznie w ramach potoku budowania. Ręczne generowanie SBOM niesie ryzyko powstania nieaktualnego lub brakującego dokumentu w momencie audytu lub reakcji na incydent.

### Przykład GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Dołącz SBOM do artefaktu wydania. Każde wydanie otrzymuje SBOM. Nazwa pliku zawierająca skrót SHA tworzy ścieżkę audytu łączącą każdy SBOM z odpowiadającym mu buildem.

### Przykład GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` zapewnia, że GitLab nie usunie artefaktu. W połączeniu z tagowaniem wydań zapewnia historię SBOM dla każdego wydania, sięgającą tak daleko wstecz, jak jest to potrzebne.

## Walidacja SBOM

Przed zapisaniem lub przekazaniem SBOM należy go zwalidować:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

CLI CycloneDX jest dostępne w pakiecie `@cyclonedx/cyclonedx-cli`. Walidacja schematu wykrywa brakujące pola wymagane, niepoprawne typy oraz zniekształcone PURL przed wprowadzeniem SBOM do dokumentacji.

## Podpisywanie SBOM

Podpisany SBOM stanowi silniejszy dowód podczas audytu niż dokument niepodpisany. Możliwość wykazania, że SBOM został wygenerowany w określonym momencie i nie uległ modyfikacji od tego czasu, wzmacnia łańcuch kontroli.

Cosign (z projektu Sigstore) umożliwia podpisywanie i weryfikację plików SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Plik podpisu potwierdza, że SBOM został wyprodukowany przez system budowania i nie został zmieniony. Przechowuj podpis razem z SBOM.

## Kluczowe wnioski

1. Narzędzia działające w czasie źródła (cdxgen) odczytują manifesty pakietów i tworzą pełne grafy zależności przechodnich. Skanery obrazów (Syft) analizują zbudowane artefakty i wykrywają pakiety systemu operacyjnego oraz środowiska uruchomieniowego.
2. Najlepsza praktyka łączy oba podejścia: cdxgen dla zależności aplikacji, Syft dla pakietów systemu operacyjnego i środowiska uruchomieniowego, scalone w jeden SBOM.
3. Generowanie SBOM musi być zintegrowane z CI/CD. Ręczne generowanie prowadzi do nieaktualnych lub brakujących SBOM w sytuacjach presji czasowej.
4. Dołącz SBOM do każdego artefaktu wydania, oznaczając go skrótem SHA builda lub wersją. Tworzy to ścieżkę audytu wymaganą przez zasadę przechowywania przez 10 lat.
5. Waliduj za pomocą CLI CycloneDX przed zapisaniem. Podpisuj za pomocą Cosign w celu utworzenia łańcucha kontroli.
