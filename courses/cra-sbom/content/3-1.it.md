# Lezione 3.1: Creazione del proprio SBOM: Strumenti e Integrazione nella Pipeline

Sapere cosa deve contenere un SBOM è una cosa. Generarlo in modo affidabile, come parte del processo di build, per ogni release, è un'altra. Questa lezione illustra gli strumenti che generano SBOM e come integrare la generazione di SBOM in una pipeline CI/CD affinché l'output sia sempre aggiornato.

## Le due categorie di generazione di SBOM

### Analisi a tempo di sorgente

Gli strumenti a tempo di sorgente leggono i file manifest delle dipendenze del codice, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, e producono un SBOM dalle dipendenze dichiarate. Questi strumenti comprendono i file di lock dei gestori di pacchetti e possono produrre grafi completi delle dipendenze transitive a partire da essi.

**cdxgen** (CycloneDX Generator) è lo strumento a tempo di sorgente più capace. Supporta oltre 30 ecosistemi linguistici: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP e altri. Legge il file di lock per l'ecosistema e genera CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

L'analisi a tempo di sorgente è accurata per le dipendenze dell'applicazione ma non rileva i pacchetti del sistema operativo e le librerie di sistema che non sono presenti nei manifest specifici del linguaggio.

### Scansione di immagini e filesystem

Gli scanner di immagini esaminano un artefatto compilato, un'immagine container, una directory del filesystem, un binario compilato e identificano i pacchetti dalle basi di dati dei pacchetti presenti. [[Syft]] di Anchore è lo strumento principale per questa attività.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifica i pacchetti leggendo:
- le basi di dati dei pacchetti del sistema operativo (dpkg per Debian/Ubuntu, rpm per RHEL/Fedora, apk per Alpine)
- i manifest e i file di lock dei pacchetti specifici del linguaggio incorporati nell'immagine
- le firme binarie per i pacchetti compilati e installati senza un gestore di pacchetti

Il vantaggio della scansione delle immagini è che si vede esattamente cosa è presente nell'artefatto che verrà distribuito. Lo svantaggio è che, se un pacchetto è stato installato senza un gestore di pacchetti (caso comune nei sistemi di build legacy), Syft potrebbe non rilevarlo.

## Best practice: combinare entrambi gli approcci

Eseguire cdxgen sul codice sorgente per le dipendenze dell'applicazione e Syft sull'immagine container per i pacchetti del sistema operativo e del runtime. Unire i due SBOM con uno strumento di merge. CycloneDX fornisce un'operazione di merge che combina gli elenchi di componenti ed elimina i duplicati.

Lo SBOM unificato copre:
- le dipendenze dell'applicazione (da cdxgen, grafo transitivo completo)
- i pacchetti del sistema operativo (da Syft)
- le dipendenze di runtime (runtime Node.js, interprete Python, JVM)

Questa è l'immagine completa richiesta dal CRA e dal monitoraggio ai sensi dell'articolo 14.

## Integrazione della generazione di SBOM nella pipeline CI/CD

Lo SBOM deve essere generato automaticamente come parte della pipeline di build. La generazione manuale di SBOM crea il rischio di uno SBOM obsoleto o assente quando serve per un audit o una risposta a un incidente.

### Esempio GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Associare lo SBOM all'artefatto della release. Ogni release ottiene un SBOM. Il nome del file con tag SHA crea la traccia di audit che collega ogni SBOM alla build corrispondente.

### Esempio GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantisce che GitLab non elimini l'artefatto. Combinato con il tagging delle release, fornisce la cronologia degli SBOM per ogni release per il periodo necessario.

## Convalida dello SBOM

Prima di archiviare o inviare uno SBOM, convalidarlo:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

La CLI di CycloneDX è disponibile da `@cyclonedx/cyclonedx-cli`. La convalida dello schema rileva i campi obbligatori mancanti, i tipi errati e i PURL malformati prima che lo SBOM entri nei registri della documentazione.

## Firma dello SBOM

Uno SBOM firmato costituisce una prova più solida in un audit rispetto a uno non firmato. Se si può dimostrare che lo SBOM è stato generato in un momento specifico e non è stato modificato da allora, si dispone di una catena di custodia più robusta.

Cosign (dal progetto Sigstore) può firmare e verificare i file SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Il file della firma dimostra che lo SBOM è stato prodotto dal sistema di build e non è stato alterato. Archiviare la firma insieme allo SBOM.

## Punti chiave

1. Gli strumenti a tempo di sorgente (cdxgen) leggono i manifest dei pacchetti e producono grafi completi delle dipendenze transitive. Gli scanner di immagini (Syft) esaminano gli artefatti compilati e individuano i pacchetti del sistema operativo e del runtime.
2. La best practice combina entrambi gli approcci: cdxgen per le dipendenze dell'applicazione, Syft per i pacchetti del sistema operativo e del runtime, uniti in un unico SBOM.
3. La generazione di SBOM deve essere integrata nella pipeline CI/CD. La generazione manuale crea SBOM obsoleti o assenti sotto pressione.
4. Associare lo SBOM a ogni artefatto di release, con tag SHA della build o versione. Questo crea la traccia di audit richiesta dalla regola di conservazione di 10 anni.
5. Convalidare con la CLI di CycloneDX prima dell'archiviazione. Firmare con Cosign per creare una catena di custodia.
