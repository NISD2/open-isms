# Lezione 3.1: Costruire il tuo SBOM: strumenti e integrazione nella pipeline

Sapere cosa dovrebbe contenere un SBOM è una cosa. Farlo generare in modo affidabile, come parte del tuo processo di build, per ogni rilascio, è un'altra. Questa lezione copre gli strumenti che generano gli SBOM e come integrare la generazione dell'SBOM in una pipeline CI/CD affinché l'output sia sempre aggiornato.

## Le due categorie di generazione dell'SBOM

### Analisi al momento del sorgente

Gli strumenti di analisi al momento del sorgente leggono i file di manifesto delle dipendenze del tuo codice, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, e producono un SBOM dalle dipendenze dichiarate. Questi strumenti comprendono i file di lock dei gestori di pacchetti e possono produrre da essi grafi completi delle dipendenze transitive.

**cdxgen** (CycloneDX Generator) è lo strumento di analisi al momento del sorgente più capace. Supporta oltre 30 ecosistemi di linguaggi: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP e altri. Legge il file di lock dell'ecosistema e produce CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

L'analisi al momento del sorgente è accurata per le dipendenze applicative ma non rileva i pacchetti del sistema operativo e le librerie di sistema che non sono nei manifesti specifici del linguaggio.

### Scansione di immagini/filesystem

Gli scanner di immagini esaminano un artefatto già costruito, un'immagine di container, una directory del filesystem, un binario compilato, e identificano i pacchetti dai database dei pacchetti presenti. [[Syft]] di Anchore è lo strumento principale per questo.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifica i pacchetti leggendo:
- I database dei pacchetti del sistema operativo (dpkg per Debian/Ubuntu, rpm per RHEL/Fedora, apk per Alpine)
- I manifesti e i file di lock dei pacchetti specifici del linguaggio incorporati nell'immagine
- Le firme dei binari per i pacchetti che sono stati compilati e installati senza un gestore di pacchetti

Il vantaggio della scansione delle immagini: vedi esattamente cosa c'è nell'artefatto che verrà distribuito. Lo svantaggio: se un pacchetto è stato installato senza un gestore di pacchetti (cosa comune nei sistemi di build legacy), Syft potrebbe non rilevarlo.

## Buona prassi: combinare entrambi gli approcci

Esegui cdxgen sul tuo codice sorgente per le dipendenze applicative, e Syft sulla tua immagine di container per i pacchetti del sistema operativo e di runtime. Unisci i due SBOM usando uno strumento di merge. CycloneDX fornisce un'operazione di merge che combina gli elenchi di componenti ed elimina i duplicati.

L'SBOM unito copre:
- Le dipendenze applicative (da cdxgen, grafo transitivo completo)
- I pacchetti del sistema operativo (da Syft)
- Le dipendenze di runtime (runtime Node.js, interprete Python, JVM)

Questo è il quadro completo che il CRA e il monitoraggio dell'Articolo 14 richiedono.

## Integrare la generazione dell'SBOM in CI/CD

L'SBOM dovrebbe essere generato automaticamente come parte della tua pipeline di build. La generazione manuale dell'SBOM crea il rischio di un SBOM obsoleto o mancante quando ne hai bisogno per un audit o per la risposta a un incidente.

### Esempio con GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Allega l'SBOM all'artefatto di rilascio. Ogni rilascio ottiene un SBOM. Il nome del file contrassegnato con lo SHA crea la pista di controllo che collega ogni SBOM alla build corrispondente.

### Esempio con GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantisce che GitLab non elimini l'artefatto. Combinato con il tuo tagging dei rilasci, questo ti fornisce la cronologia degli SBOM per ogni rilascio, indietro nel tempo quanto necessario.

## Convalidare il tuo SBOM

Prima di conservare o inviare un SBOM, convalidalo:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

La CLI di CycloneDX è disponibile da `@cyclonedx/cyclonedx-cli`. La convalida dello schema individua campi obbligatori mancanti, tipi errati e PURL malformati prima che l'SBOM entri nei registri della tua documentazione.

## Firmare il tuo SBOM

Un SBOM firmato è una prova più solida in un audit rispetto a uno non firmato. Se puoi dimostrare che l'SBOM è stato generato in un momento specifico e non è stato modificato da allora, hai una catena di custodia più solida.

Cosign (del progetto Sigstore) può firmare e verificare i file SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Il file di firma dimostra che l'SBOM è stato prodotto dal tuo sistema di build e non è stato alterato. Conserva la firma insieme all'SBOM.

## Punti chiave

1. Gli strumenti al momento del sorgente (cdxgen) leggono i manifesti dei pacchetti e producono grafi completi delle dipendenze transitive. Gli scanner di immagini (Syft) esaminano gli artefatti costruiti e trovano i pacchetti del sistema operativo e di runtime.
2. La buona prassi combina entrambi: cdxgen per le dipendenze applicative, Syft per i pacchetti del sistema operativo e di runtime, uniti in un unico SBOM.
3. La generazione dell'SBOM deve essere integrata in CI/CD. La generazione manuale crea SBOM obsoleti o mancanti sotto pressione.
4. Allega l'SBOM a ogni artefatto di rilascio, contrassegnato con lo SHA o la versione di build. Questo crea la pista di controllo che la regola di conservazione decennale richiede.
5. Convalida con la CLI di CycloneDX prima della conservazione. Firma con Cosign per creare una catena di custodia.
