# Lecția 1.1: Ce include un SBOM: componente, versiuni și identificatori

Anexa I, Partea II, punctul (1) din CRA vă spune să creați un SBOM. Nu precizează fiecare câmp care trebuie inclus. Formatele [[CycloneDX]] și [[SPDX]] completează acest aspect. Această lecție acoperă câmpurile pe care SBOM-ul trebuie să le conțină pentru a fi util în practică: pentru un scaner de vulnerabilități, pentru un auditor și pentru dumneavoastră atunci când apare o problemă la ora 2 noaptea.

## Minimul impus de CRA

Minimului CRA prevede: „componentele conținute în produsele cu elemente digitale ... cel puțin dependențele de nivel superior”. În practică, fiecare intrare de componentă trebuie să conțină suficiente informații pentru a răspunde la:

- Ce este această componentă?
- Cine a creat-o?
- Ce versiune are?
- Cum o caut într-o bază de date de vulnerabilități?

Aceste patru întrebări corespund direct câmpurilor esențiale pe care atât CycloneDX, cât și SPDX le impun.

## Câmpurile esențiale

### Nume

Numele componentei așa cum îl publică responsabilul pachetului. Nu aliasul intern. Numele exact așa cum apare în registrul de pachete. Pentru npm: `@angular/core`. Pentru Maven: `org.springframework.boot:spring-boot`. Pentru Python: `requests`.

Numele exacte contează deoarece bazele de date de vulnerabilități indexează după numele canonic al pachetului. O diferență minoră de ortografie întrerupe căutarea.

### Versiune

Șirul de versiune exact. Pentru pachetele npm: `17.0.0`. Pentru bibliotecile de sistem: `2.38.1-5+deb12u1`. Intervalele de tip `>=2.0` nu sunt acceptabile. Ele nu indică scanerului ce binar rulează efectiv.

Versiunea contează deoarece o [[CVE]] afectează de obicei un interval de versiuni și este corectată într-o versiune specifică. Fără versiunea exactă, nu puteți determina dacă componenta este afectată.

### Furnizor

Organizația care publică sau întreține componenta. Pentru pachetele npm: autorul sau organizația menționată în manifestul pachetului. Pentru pachetele de sistem de operare: responsabilul distribuției. Pentru bibliotecile comerciale: furnizorul.

Furnizorul contează pentru imaginea de risc [[supply chain attack|atac la lanțul de aprovizionare]]. Dacă un furnizor este compromis, cunoașterea componentelor provenite de la acesta indică unde să căutați mai întâi.

### Identificator unic: PURL

Un [[PURL]] (Package URL) este modul standard de a identifica unic o componentă în registre și baze de date. Formatul este:

```
pkg:type/namespace/name@version
```

Exemple:

- `pkg:npm/%40angular/core@17.0.0`: Angular Core 17.0.0 din npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0`: Spring Boot 3.2.0 din Maven Central
- `pkg:pypi/requests@2.31.0`: requests 2.31.0 din PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3`: libc6 din Debian Bookworm

Atât CycloneDX, cât și SPDX tratează PURL ca identificator unic recomandat. Bazele de date de vulnerabilități îl folosesc pentru a lega înregistrările CVE de componente specifice. Când scanerul compară un SBOM cu un flux de vulnerabilități, compară PURL-uri.

### Hash

Un [[hash|hash]] este o amprentă de lungime fixă a fișierului componentei. SHA-256 este standard. Includerea unui hash în fiecare intrare SBOM permite verificarea faptului că componenta nu s-a modificat de la generarea SBOM-ului. Este, de asemenea, singura modalitate de a confirma că două echipe vorbesc despre același binar, nu doar despre același șir de versiune.

CycloneDX și SPDX acceptă ambele hash-uri per componentă. Adăugați-le ori de câte ori instrumentele le generează.

### Licență

Nu este impusă de minimul CRA, dar este cerută de majoritatea fluxurilor SPDX și utilă în practică. Identificatorul de licență SPDX (de exemplu `Apache-2.0`, `MIT`, `GPL-2.0-only`) trimite la textul complet al licenței.

Dacă sunteți o întreprindere care utilizează componente open-source, informațiile de licență din SBOM constituie baza programului de conformitate cu licențele open-source.

## Metadatele SBOM

Pe lângă lista de componente, un SBOM valid include metadate despre documentul SBOM în sine:

- **Marcaj temporal**: momentul generării SBOM-ului
- **Versiunea SBOM**: o versiune sau un identificator pentru acest document SBOM specific
- **Informații despre instrument**: ce instrument a generat SBOM-ul și la ce versiune
- **Descrie**: ce produs sau componentă descrie acest SBOM (pachetul de nivel superior)

CycloneDX numește acest obiect `metadata`. SPDX îl numește secțiunea de informații privind crearea documentului. Auditorii verifică aici mai întâi prospețimea.

## Ce înseamnă „lizibil automat” în practică

CRA impune un format „lizibil automat”. Aceasta înseamnă că un scaner de vulnerabilități trebuie să poată analiza SBOM-ul fără intervenție umană. JSON și XML îndeplinesc această cerință. Un tabel sau un PDF nu.

Un SBOM lizibil automat permite automatizarea buclei de monitorizare din Articolul 14: publicarea unei noi CVE → scanerul compară SBOM-ul → alertă declanșată → echipă evaluează → raport depus dacă este necesar.

Dacă SBOM-ul este un PDF, niciuna dintre aceste automatizări nu funcționează.

## Concluzii cheie

1. Fiecare intrare de componentă din SBOM necesită minimum: nume, versiune, furnizor și un identificator unic. [[PURL]] este identificatorul unic standard.
2. Sunt necesare șiruri de versiune exacte. Intervalele întrerup scanarea vulnerabilităților.
3. Un hash per componentă permite verificarea faptului că SBOM-ul nu a deviat de la binarul implementat efectiv.
4. Metadatele SBOM (marcaj temporal, instrument, descrie) sunt primul element verificat de un auditor.
5. „Lizibil automat” înseamnă JSON sau XML: formate pe care un scaner de vulnerabilități le poate analiza automat. Un tabel sau un PDF nu se califică.
