# Leçon 3.1 : Création de votre SBOM : Outils et intégration dans le pipeline

Savoir ce qu'un SBOM doit contenir est une chose. Obtenir sa génération de manière fiable, dans le cadre de votre processus de build, pour chaque version, en est une autre. Cette leçon présente les outils qui génèrent des SBOM et la façon d'intégrer cette génération dans un pipeline CI/CD afin que le résultat soit toujours à jour.

## Les deux catégories de génération de SBOM

### Analyse au moment de la source

Les outils d'analyse au moment de la source lisent les fichiers manifestes de dépendances de votre code, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, et produisent un SBOM à partir des dépendances déclarées. Ces outils comprennent les fichiers de verrouillage des gestionnaires de paquets et peuvent produire des graphes complets de dépendances transitives à partir de ces fichiers.

**cdxgen** (CycloneDX Generator) est l'outil source-time le plus performant. Il prend en charge plus de 30 écosystèmes linguistiques : Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP, et d'autres. Il lit le fichier de verrouillage de l'écosystème et produit un CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

L'analyse au moment de la source est précise pour les dépendances applicatives mais omet les paquets du système d'exploitation et les bibliothèques système absents des manifestes spécifiques au langage.

### Analyse d'image ou de système de fichiers

Les scanners d'images examinent un artefact compilé, une image de conteneur, un répertoire de système de fichiers, un binaire compilé, et identifient les paquets à partir des bases de données de paquets présentes. [[Syft]] d'Anchore est l'outil de référence pour cette tâche.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifie les paquets en lisant :
- les bases de données de paquets du système d'exploitation (dpkg pour Debian/Ubuntu, rpm pour RHEL/Fedora, apk pour Alpine)
- les manifestes et fichiers de verrouillage spécifiques aux langages intégrés dans l'image
- les signatures binaires des paquets compilés et installés sans gestionnaire de paquets

L'avantage de l'analyse d'image : vous voyez exactement ce qui se trouve dans l'artefact qui sera déployé. L'inconvénient : si un paquet a été installé sans gestionnaire de paquets (cas fréquent dans les systèmes de build legacy), Syft peut l'omettre.

## Bonne pratique : combiner les deux approches

Exécutez cdxgen sur votre code source pour les dépendances applicatives, et Syft sur votre image de conteneur pour les paquets du système d'exploitation et de l'environnement d'exécution. Fusionnez les deux SBOM à l'aide d'un outil de fusion. CycloneDX propose une opération de fusion qui combine les listes de composants et supprime les doublons.

Le SBOM fusionné couvre :
- les dépendances applicatives (issues de cdxgen, graphe transitif complet)
- les paquets du système d'exploitation (issues de Syft)
- les dépendances d'exécution (environnement Node.js, interpréteur Python, JVM)

Il s'agit de la vue complète exigée par le CRA et par la surveillance prévue à l'article 14.

## Intégration de la génération de SBOM dans le pipeline CI/CD

Le SBOM doit être généré automatiquement dans le cadre de votre pipeline de build. Une génération manuelle crée le risque d'obtenir un SBOM obsolète ou absent lorsque vous en avez besoin pour un audit ou une réponse à incident.

### Exemple GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Joignez le SBOM à l'artefact de release. Chaque version reçoit un SBOM. Le nom de fichier incluant le SHA crée la piste d'audit reliant chaque SBOM à son build correspondant.

### Exemple GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantit que GitLab ne supprime pas l'artefact. Combiné à votre étiquetage de release, cela fournit l'historique des SBOM pour chaque version, aussi loin que nécessaire.

## Validation de votre SBOM

Avant de stocker ou de soumettre un SBOM, validez-le :

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

La CLI CycloneDX est disponible via `@cyclonedx/cyclonedx-cli`. La validation de schéma détecte les champs obligatoires manquants, les types incorrects et les PURL mal formés avant que le SBOM n'entre dans vos registres de documentation.

## Signature de votre SBOM

Un SBOM signé constitue une preuve plus solide lors d'un audit qu'un SBOM non signé. Si vous pouvez démontrer que le SBOM a été généré à un moment précis et n'a pas été modifié depuis, vous disposez d'une chaîne de conservation plus robuste.

Cosign (issu du projet Sigstore) permet de signer et de vérifier les fichiers SBOM :

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Le fichier de signature prouve que le SBOM a été produit par votre système de build et n'a pas été altéré. Conservez la signature aux côtés du SBOM.

## Points clés à retenir

1. Les outils source-time (cdxgen) lisent les manifestes de paquets et produisent des graphes complets de dépendances transitives. Les scanners d'images (Syft) examinent les artefacts compilés et détectent les paquets du système d'exploitation et de l'environnement d'exécution.
2. La bonne pratique consiste à combiner les deux approches : cdxgen pour les dépendances applicatives, Syft pour les paquets du système d'exploitation et de l'environnement d'exécution, le tout fusionné dans un seul SBOM.
3. La génération de SBOM doit être intégrée au pipeline CI/CD. Une génération manuelle produit des SBOM obsolètes ou absents en situation de contrainte.
4. Joignez le SBOM à chaque artefact de release, étiqueté avec le SHA du build ou la version. Cela crée la piste d'audit requise par la règle de conservation sur 10 ans.
5. Validez avec la CLI CycloneDX avant le stockage. Signez avec Cosign pour établir une chaîne de conservation.
