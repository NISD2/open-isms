# Leçon 3.1 : Constituer votre SBOM : outils et intégration au pipeline

Savoir ce qu'un SBOM devrait contenir est une chose. Le faire générer de manière fiable, dans le cadre de votre processus de build, à chaque publication, en est une autre. Cette leçon traite des outils qui génèrent des SBOM et de comment intégrer la génération de SBOM dans un pipeline CI/CD pour que la sortie soit toujours à jour.

## Les deux catégories de génération de SBOM

### Analyse au moment de la source

Les outils au moment de la source lisent les fichiers de manifeste de dépendances de votre code, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, et produisent un SBOM à partir des dépendances déclarées. Ces outils comprennent les fichiers de verrouillage des gestionnaires de paquets et peuvent en produire des graphes de dépendances transitives complets.

**cdxgen** (CycloneDX Generator) est l'outil au moment de la source le plus capable. Il prend en charge plus de 30 écosystèmes de langages : Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP, et d'autres. Il lit le fichier de verrouillage de l'écosystème et produit du CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

L'analyse au moment de la source est précise pour les dépendances applicatives, mais manque les paquets du système d'exploitation et les bibliothèques système qui ne figurent pas dans les manifestes spécifiques au langage.

### Analyse d'image/de système de fichiers

Les scanners d'image examinent un artefact construit, une image de conteneur, un répertoire de système de fichiers, un binaire compilé, et identifient les paquets à partir des bases de données de paquets présentes. [[Syft]] d'Anchore est l'outil de référence pour cela.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifie les paquets en lisant :
- Les bases de données de paquets du système d'exploitation (dpkg pour Debian/Ubuntu, rpm pour RHEL/Fedora, apk pour Alpine)
- Les manifestes et fichiers de verrouillage de paquets spécifiques au langage intégrés dans l'image
- Les signatures binaires des paquets qui ont été compilés et installés sans gestionnaire de paquets

L'avantage de l'analyse d'image : vous voyez exactement ce qui se trouve dans l'artefact qui sera déployé. L'inconvénient : si un paquet a été installé sans gestionnaire de paquets (courant dans les anciens systèmes de build), Syft peut le manquer.

## Bonne pratique : combiner les deux approches

Lancez cdxgen sur votre code source pour les dépendances applicatives, et Syft sur votre image de conteneur pour les paquets du système d'exploitation et du runtime. Fusionnez les deux SBOM à l'aide d'un outil de fusion. CycloneDX fournit une opération de fusion qui combine les listes de composants et déduplique.

Le SBOM fusionné couvre :
- Les dépendances applicatives (depuis cdxgen, graphe transitif complet)
- Les paquets du système d'exploitation (depuis Syft)
- Les dépendances de runtime (runtime Node.js, interpréteur Python, JVM)

C'est le tableau complet qu'exigent le CRA et la surveillance de l'article 14.

## Intégrer la génération de SBOM dans la CI/CD

Le SBOM devrait être généré automatiquement dans le cadre de votre pipeline de build. La génération manuelle de SBOM crée le risque d'un SBOM périmé ou manquant au moment où vous en avez besoin pour un audit ou une réponse à incident.

### Exemple GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Attachez le SBOM à l'artefact de publication. Chaque publication obtient un SBOM. Le nom de fichier étiqueté par SHA crée la piste d'audit reliant chaque SBOM à son build correspondant.

### Exemple GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantit que GitLab ne supprime pas l'artefact. Combiné à votre étiquetage des publications, cela vous donne un historique de SBOM pour chaque publication remontant aussi loin que nécessaire.

## Valider votre SBOM

Avant de stocker ou de soumettre un SBOM, validez-le :

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

Le CLI CycloneDX est disponible depuis `@cyclonedx/cyclonedx-cli`. La validation de schéma détecte les champs requis manquants, les types incorrects et les PURL malformés avant que le SBOM n'entre dans vos archives de documentation.

## Signer votre SBOM

Un SBOM signé est une preuve plus solide lors d'un audit qu'un SBOM non signé. Si vous pouvez démontrer que le SBOM a été généré à un moment précis et n'a pas été modifié depuis, vous disposez d'une chaîne de traçabilité plus solide.

Cosign (du projet Sigstore) peut signer et vérifier les fichiers SBOM :

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Le fichier de signature prouve que le SBOM a été produit par votre système de build et n'a pas été altéré. Stockez la signature aux côtés du SBOM.

## Points clés à retenir

1. Les outils au moment de la source (cdxgen) lisent les manifestes de paquets et produisent des graphes de dépendances transitives complets. Les scanners d'image (Syft) examinent les artefacts construits et trouvent les paquets du système d'exploitation et du runtime.
2. La bonne pratique combine les deux : cdxgen pour les dépendances applicatives, Syft pour les paquets du système d'exploitation et du runtime, fusionnés en un seul SBOM.
3. La génération de SBOM doit être intégrée à la CI/CD. La génération manuelle crée des SBOM périmés ou manquants sous pression.
4. Attachez le SBOM à chaque artefact de publication, étiqueté avec le SHA du build ou la version. Cela crée la piste d'audit qu'exige la règle de conservation de 10 ans.
5. Validez avec le CLI CycloneDX avant le stockage. Signez avec Cosign pour créer une chaîne de traçabilité.
