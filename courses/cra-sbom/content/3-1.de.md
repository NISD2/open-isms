# Lektion 3.1: Erstellen Ihrer SBOM: Tools und Pipeline-Integration

Zu wissen, was eine SBOM enthalten soll, ist das eine. Sie zuverlässig als Teil Ihres Build-Prozesses für jedes Release zu erzeugen, ist etwas anderes. Diese Lektion behandelt die Tools, die SBOMs erzeugen, und wie Sie die SBOM-Erzeugung in eine CI/CD-Pipeline integrieren, damit die Ausgabe stets aktuell ist.

## Die zwei Kategorien der SBOM-Erzeugung

### Quellzeit-Analyse

Quellzeit-Tools lesen die Abhängigkeits-Manifestdateien Ihres Codes, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, und erzeugen daraus eine SBOM. Diese Tools verstehen die Lock-Dateien der Paketmanager und können vollständige transitive Abhängigkeitsgraphen daraus ableiten.

**cdxgen** (CycloneDX Generator) ist das leistungsfähigste Quellzeit-Tool. Es unterstützt über 30 Sprachökosysteme: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP und weitere. Es liest die Lock-Datei des jeweiligen Ökosystems und gibt CycloneDX-JSON aus.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Die Quellzeit-Analyse ist für Anwendungsabhängigkeiten genau, übersieht jedoch Betriebssystempakete und Systembibliotheken, die nicht in den sprachspezifischen Manifesten stehen.

### Image/Dateisystem-Scan

Image-Scanner untersuchen ein gebautes Artefakt, ein Container-Image, ein Dateisystemverzeichnis oder eine kompilierte Binärdatei und identifizieren Pakete aus den vorhandenen Paketdatenbanken. [[Syft|Syft]] von Anchore ist das führende Tool dafür.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifiziert Pakete durch Lesen von:
- OS-Paketdatenbanken (dpkg für Debian/Ubuntu, rpm für RHEL/Fedora, apk für Alpine)
- Sprachspezifischen Paketmanifesten und Lock-Dateien, die im Image eingebettet sind
- Binärsignaturen für Pakete, die ohne Paketmanager kompiliert und installiert wurden

Der Vorteil des Image-Scans: Sie sehen genau, was in dem Artefakt enthalten ist, das ausgerollt wird. Der Nachteil: Wurde ein Paket ohne Paketmanager installiert (häufig in Legacy-Build-Systemen), kann Syft es übersehen.

## Bewährte Praxis: beide Ansätze kombinieren

Führen Sie cdxgen gegen Ihren Quellcode für Anwendungsabhängigkeiten aus und Syft gegen Ihr Container-Image für OS- und Laufzeitpakete. Führen Sie die beiden SBOMs mit einem Merge-Tool zusammen. CycloneDX stellt eine Merge-Operation bereit, die Komponentenlisten vereint und Duplikate entfernt.

Die zusammengeführte SBOM deckt ab:
- Anwendungsabhängigkeiten (von cdxgen, vollständiger transitiver Graph)
- OS-Pakete (von Syft)
- Laufzeitabhängigkeiten (Node.js-Laufzeitumgebung, Python-Interpreter, JVM)

Dies ist das vollständige Bild, das die CRA und die Überwachung nach Artikel 14 verlangen.

## SBOM-Erzeugung in CI/CD integrieren

Die SBOM sollte automatisch als Teil Ihrer Build-Pipeline erzeugt werden. Manuelle SBOM-Erzeugung birgt das Risiko einer veralteten oder fehlenden SBOM, wenn Sie sie für ein Audit oder eine Incident Response benötigen.

### GitHub Actions-Beispiel

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Hängen Sie die SBOM als Release-Artefakt an. Jedes Release erhält eine SBOM. Der mit dem SHA gekennzeichnete Dateiname erzeugt die Audit-Spur, die jede SBOM mit dem zugehörigen Build verknüpft.

### GitLab CI-Beispiel

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` stellt sicher, dass GitLab das Artefakt nicht löscht. In Kombination mit Ihrem Release-Tagging erhalten Sie so die SBOM-Historie für jedes Release, so weit zurück wie erforderlich.

## Validierung Ihrer SBOM

Validieren Sie die SBOM vor der Speicherung oder Übermittlung:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

Die CycloneDX-CLI ist über `@cyclonedx/cyclonedx-cli` verfügbar. Die Schema-Validierung erkennt fehlende Pflichtfelder, falsche Typen und fehlerhafte PURLs, bevor die SBOM in Ihre Dokumentationsbestände aufgenommen wird.

## Signieren Ihrer SBOM

Eine signierte SBOM ist in einem Audit stärkeres Beweismaterial als eine unsignierte. Wenn Sie nachweisen können, dass die SBOM zu einem bestimmten Zeitpunkt erzeugt und seither nicht verändert wurde, verfügen Sie über eine stärkere Chain of Custody.

Cosign (aus dem Sigstore-Projekt) kann SBOM-Dateien signieren und verifizieren:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Die Signaturdatei beweist, dass die SBOM von Ihrem Build-System erzeugt wurde und nicht verändert wurde. Speichern Sie die Signatur zusammen mit der SBOM.

## Wichtige Erkenntnisse

1. Quellzeit-Tools (cdxgen) lesen Paketmanifeste und erzeugen vollständige transitive Abhängigkeitsgraphen. Image-Scanner (Syft) untersuchen gebaute Artefakte und finden OS- und Laufzeitpakete.
2. Die bewährte Praxis kombiniert beide Ansätze: cdxgen für Anwendungsabhängigkeiten, Syft für OS- und Laufzeitpakete, zusammengeführt zu einer SBOM.
3. Die SBOM-Erzeugung muss in die CI/CD-Pipeline integriert werden. Manuelle Erzeugung führt unter Druck zu veralteten oder fehlenden SBOMs.
4. Hängen Sie die SBOM an jedes Release-Artefakt an, gekennzeichnet mit dem Build-SHA oder der Version. Dies erzeugt die Audit-Spur, die die 10-Jahres-Aufbewahrungsregel erfordert.
5. Validieren Sie mit der CycloneDX-CLI vor der Speicherung. Signieren Sie mit Cosign, um eine Chain of Custody zu schaffen.
