# Lección 2.2: SPDX y la elección de tu formato

[[SPDX]] es el otro formato que cumple el requisito del Artículo 13(5) CRA de un SBOM "de uso común y legible por máquina". Esta lección trata qué es SPDX, en qué se diferencia de CycloneDX, y cómo decidir qué formato usar.

## Qué es SPDX

Software Package Data Exchange (SPDX) se creó en la Linux Foundation en 2010. Se convirtió en un estándar ISO en 2021: ISO/IEC 5962:2021. La versión 2.3 es la actual para el estándar ISO. La versión 3.0 se publicó en 2024 con un nuevo modelo de datos y un sistema de perfiles.

SPDX se diseñó para resolver el problema del cumplimiento de licencias de código abierto. Cuando entregas un producto que incluye componentes de código abierto, tienes obligaciones legales: atribución, inclusión del texto de la licencia, divulgación del código fuente para licencias copyleft. SPDX te da una forma legible por máquina de expresar qué licencias se aplican a qué componentes y qué obligaciones has aceptado.

Con el tiempo se convirtió en un estándar de SBOM, y ahora cubre también los campos del inventario de componentes necesarios para la gestión de vulnerabilidades. Pero su intención de diseño original, el cumplimiento de licencias, sigue siendo visible en el modelo de datos.

## Estructura de un documento SPDX

Un documento SPDX 2.3 JSON tiene:

- **Información de creación del documento**: equivalente a los metadatos de CycloneDX: creador, marca de tiempo de creación, espacio de nombres del documento, versión de SPDX
- **Paquetes**: el inventario de componentes. Cada paquete tiene: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` o `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (donde va el [[PURL]])
- **Relaciones**: cómo se relacionan los paquetes entre sí. La relación `DESCRIBES` identifica el producto de nivel superior. `DEPENDS_ON` y `DEPENDENCY_OF` asignan el grafo de dependencias.
- **Archivos** (opcional): inventario a nivel de archivo con hashes, si necesitas granularidad de archivo
- **Fragmentos** (opcional): a nivel de fragmento de código, para código copiado que no procede de un paquete

El campo PURL de SPDX 2.3 vive dentro del array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Esto es más verboso que el campo `purl` de primera clase de CycloneDX, pero sigue siendo legible por máquina y analizable por los escáneres de vulnerabilidades.

## Dónde tiene ventaja SPDX

**Normalización ISO.** ISO/IEC 5962:2021 significa que SPDX es el único formato de SBOM que es un estándar internacional. Para las organizaciones que exigen formatos certificados por ISO en sus compras o contratos con proveedores, esto importa.

**Flujos de trabajo de cumplimiento de licencias.** Si tu caso de uso principal del SBOM es el cumplimiento de licencias de código abierto, el seguimiento de obligaciones de atribución, la identificación de código contaminado por GPL, la generación de avisos de terceros, el rico modelo de licencias de SPDX se adapta mejor. SPDX admite SPDX License Identifiers, `LicenseInfoInFile` para la detección de licencias a nivel de archivo, y `licenseComments` para situaciones complejas.

**Integración con el grafo de dependencias de GitHub.** El grafo de dependencias de GitHub exporta de forma nativa SPDX 2.3 JSON. Si tu repositorio está en GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` te da un SBOM SPDX sin ejecutar ninguna herramienta local. Para muchos equipos este es el punto de partida más sencillo.

**Múltiples formatos de salida.** SPDX admite JSON, YAML, RDF/XML y un formato de texto tag-value. El formato tag-value es legible por humanos (a diferencia de JSON o XML), lo que puede ser útil para la revisión.

## Dónde tiene ventaja CycloneDX

**Gestión de vulnerabilidades.** CycloneDX tiene soporte nativo de [[VEX]]. SPDX 3.0 añadió un perfil de seguridad con capacidades VEX, pero el soporte del ecosistema para SPDX VEX todavía está madurando. Para los flujos de trabajo de cumplimiento del Artículo 14, CycloneDX VEX es más maduro y está mejor soportado por las herramientas.

**Dependency-Track.** La principal plataforma de código abierto de gestión de SBOM, OWASP Dependency-Track, se construyó para CycloneDX. Acepta entrada SPDX, pero sus características nativas, el cotejo de vulnerabilidades, la gestión de VEX, la evaluación de políticas, son más completas para CycloneDX.

**Madurez de las herramientas.** La mayoría de las herramientas de SBOM, Syft, cdxgen, trivy, grype, tratan CycloneDX como su formato de salida principal y SPDX como secundario.

## Ambos formatos cumplen para el CRA

El CRA exige "de uso común y legible por máquina". Tanto CycloneDX como SPDX son utilizados por cientos de organizaciones. Ambos son legibles por máquina. Ambos pueden contener los campos del inventario de componentes exigidos por el Artículo 13(5). No suspenderás una auditoría del CRA por haber elegido SPDX en vez de CycloneDX o viceversa.

La orientación de la Comisión Europea y el documento de buenas prácticas de SBOM de ENISA hacen referencia ambos a los dos formatos. Ninguna orientación oficial de la UE ha designado un formato como preferido frente al otro.

## Cómo elegir

Usa este marco de decisión:

| Pregunta | CycloneDX | SPDX |
|---|---|---|
| El caso de uso principal es la gestión de vulnerabilidades y el cumplimiento del Artículo 14 | ✓ | — |
| El caso de uso principal es el cumplimiento de licencias de código abierto | — | ✓ |
| Usas Dependency-Track | ✓ | — |
| Tus compras exigen formatos certificados por ISO | — | ✓ |
| Partes de la exportación del grafo de dependencias de GitHub | — | ✓ |
| Tu equipo usa Syft o cdxgen | ✓ | — |
| Necesitas herramientas VEX maduras | ✓ | — |

Si la gestión de vulnerabilidades es tu principal preocupación, elige CycloneDX. Si ya tienes un flujo de trabajo SPDX para el cumplimiento de licencias, ampliarlo para cubrir la gestión de vulnerabilidades es razonable: solo ten en cuenta que las herramientas VEX están menos maduras.

Muchas organizaciones producen ambos: CycloneDX para operaciones de seguridad, SPDX para asuntos legales y de compras. Las herramientas lo permiten. Syft puede generar ambos a partir del mismo análisis.

## Puntos clave

1. SPDX (ISO/IEC 5962:2021) es el formato de SBOM estándar de ISO. La versión actual es la 2.3 para el estándar ISO, y la 3.0 para el nuevo modelo de datos. Se diseñó para el cumplimiento de licencias de código abierto.
2. Tanto [[CycloneDX]] como SPDX cumplen como formatos "de uso común y legibles por máquina" conforme al Artículo 13(5) CRA. Ninguno es oficialmente preferido por la orientación de la UE.
3. Ventajas de SPDX: estatus ISO, modelo de licencias más rico, exportación nativa del grafo de dependencias de GitHub, múltiples formatos de salida.
4. Ventajas de CycloneDX: soporte nativo de [[VEX]], integración con Dependency-Track, ecosistema de herramientas de vulnerabilidades más maduro.
5. Si la notificación de vulnerabilidades del Artículo 14 CRA es tu principal motor, CycloneDX es el ajuste más natural. Producir ambos formatos a partir de un único análisis de Syft es una estrategia válida.
