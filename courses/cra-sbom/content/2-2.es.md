# Lección 2.2: SPDX y elección del formato

[[SPDX]] es el otro formato que cumple el requisito del Anexo I, parte II, punto (1) del CRA de un SBOM "de uso común y legible por máquina". Esta lección explica qué es SPDX, en qué se diferencia de CycloneDX y cómo decidir qué formato utilizar.

## Qué es SPDX

Software Package Data Exchange (SPDX) se creó en la Linux Foundation en 2010. Se convirtió en norma ISO en 2021: ISO/IEC 5962:2021. La versión 2.3 es la vigente para la norma ISO. La versión 3.0 se publicó en 2024 con un nuevo modelo de datos y sistema de perfiles.

SPDX se diseñó para resolver el problema de cumplimiento de licencias de código abierto. Cuando se distribuye un producto que incluye componentes de código abierto, se contraen obligaciones legales: atribución, inclusión del texto de la licencia y divulgación del código fuente para licencias copyleft. SPDX ofrece una forma legible por máquina de expresar qué licencias se aplican a cada componente y qué obligaciones se han aceptado.

Con el tiempo se convirtió en norma de SBOM y ahora cubre también los campos de inventario de componentes necesarios para la gestión de vulnerabilidades. Sin embargo, su intención de diseño original (cumplimiento de licencias) sigue siendo visible en el modelo de datos.

## Estructura del documento SPDX

Un documento SPDX 2.3 en JSON contiene:

- **Información de creación del documento**: equivalente a los metadatos de CycloneDX: creador, marca temporal de creación, espacio de nombres del documento, versión de SPDX
- **Paquetes**: el inventario de componentes. Cada paquete incluye: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` o `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (aquí se inserta [[PURL]])
- **Relaciones**: cómo se relacionan los paquetes entre sí. La relación `DESCRIBES` identifica el producto de nivel superior. `DEPENDS_ON` y `DEPENDENCY_OF` representan el grafo de dependencias.
- **Archivos** (opcional): inventario a nivel de archivo con hashes, si se necesita granularidad a nivel de archivo
- **Fragmentos** (opcional): nivel de fragmento de código, para código copiado que no procede de un paquete

El campo PURL de SPDX 2.3 se encuentra dentro del array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Esto es más verboso que el campo `purl` de primera clase de CycloneDX, pero sigue siendo legible por máquina y analizable por escáneres de vulnerabilidades.

## Dónde tiene ventaja SPDX

**Normalización ISO.** ISO/IEC 5962:2021 significa que SPDX es el único formato de SBOM que constituye una norma internacional. Para las organizaciones que exigen formatos certificados ISO en sus procesos de contratación o contratos con proveedores, esto resulta relevante.

**Flujos de trabajo de cumplimiento de licencias.** Si el caso de uso principal del SBOM es el cumplimiento de licencias de código abierto, el seguimiento de obligaciones de atribución, la identificación de código contaminado por GPL o la generación de avisos de terceros, el rico modelo de licencias de SPDX resulta más adecuado. SPDX admite identificadores de licencia SPDX, `LicenseInfoInFile` para la detección de licencias a nivel de archivo y `licenseComments` para situaciones complejas.

**Integración con el grafo de dependencias de GitHub.** El grafo de dependencias de GitHub exporta de forma nativa SPDX 2.3 JSON. Si el repositorio está en GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` proporciona un SBOM en SPDX sin necesidad de ejecutar herramientas locales. Para muchos equipos este es el punto de partida más sencillo.

**Múltiples formatos de salida.** SPDX admite JSON, YAML, RDF/XML y un formato de texto de etiqueta-valor. El formato de etiqueta-valor es legible para las personas (a diferencia de JSON o XML), lo que puede resultar útil para la revisión.

## Dónde tiene ventaja CycloneDX

**Gestión de vulnerabilidades.** CycloneDX cuenta con soporte nativo de [[VEX]]. SPDX 3.0 añadió un perfil de seguridad con capacidades VEX, pero el soporte del ecosistema para VEX en SPDX todavía está en fase de maduración. Para los flujos de trabajo de cumplimiento del artículo 14, VEX de CycloneDX es más maduro y cuenta con mejor soporte por parte de las herramientas.

**Dependency-Track.** La principal plataforma de gestión de SBOM de código abierto, OWASP Dependency-Track, se diseñó para CycloneDX. Acepta entradas SPDX, pero sus funciones nativas (correspondencia de vulnerabilidades, gestión de VEX, evaluación de políticas) están más completas para CycloneDX.

**Madurez de las herramientas.** La mayoría de las herramientas de SBOM, Syft, cdxgen, trivy, grype, tratan CycloneDX como formato de salida principal y SPDX como secundario.

## Ambos formatos cumplen los requisitos de conformidad con el CRA

El CRA exige que sea "de uso común y legible por máquina". Tanto CycloneDX como SPDX son utilizados por cientos de organizaciones. Ambos son legibles por máquina. Ambos pueden transportar los campos de inventario de componentes exigidos por el Anexo I, parte II, punto (1). No se suspenderá una auditoría del CRA por haber elegido SPDX en lugar de CycloneDX o viceversa.

Tanto la orientación de la Comisión Europea como el documento de buenas prácticas de SBOM de ENISA hacen referencia a ambos formatos. Ninguna orientación oficial de la UE ha designado un formato como preferente frente al otro.

## Cómo elegir

Utilice este marco de decisión:

| Pregunta | CycloneDX | SPDX |
|---|---|---|
| El caso de uso principal es la gestión de vulnerabilidades y el cumplimiento del artículo 14 | ✓ | - |
| El caso de uso principal es el cumplimiento de licencias de código abierto | - | ✓ |
| Utiliza Dependency-Track | ✓ | - |
| Sus procesos de contratación exigen formatos certificados ISO | - | ✓ |
| Parte de la exportación del grafo de dependencias de GitHub | - | ✓ |
| Su equipo utiliza Syft o cdxgen | ✓ | - |
| Necesita herramientas VEX maduras | ✓ | - |

Si la gestión de vulnerabilidades es su principal preocupación, elija CycloneDX. Si ya dispone de un flujo de trabajo SPDX para el cumplimiento de licencias, resulta razonable ampliarlo para cubrir la gestión de vulnerabilidades. Tenga en cuenta, no obstante, que las herramientas VEX son menos maduras.

Muchas organizaciones generan ambos formatos: CycloneDX para las operaciones de seguridad y SPDX para los aspectos legales y de contratación. Las herramientas lo admiten. Syft puede generar ambos a partir del mismo análisis.

## Conclusiones principales

1. SPDX (ISO/IEC 5962:2021) es el formato de SBOM normalizado por la ISO. La versión vigente es la 2.3 para la norma ISO y la 3.0 para el nuevo modelo de datos. Se diseñó para el cumplimiento de licencias de código abierto.
2. Tanto [[CycloneDX]] como SPDX cumplen como formatos "de uso común y legibles por máquina" conforme al Anexo I, parte II, punto (1) del CRA. Ninguno es preferente según las orientaciones de la UE.
3. Ventajas de SPDX: estatus ISO, modelo de licencias más rico, exportación nativa del grafo de dependencias de GitHub, múltiples formatos de salida.
4. Ventajas de CycloneDX: soporte nativo de [[VEX]], integración con Dependency-Track, ecosistema de herramientas de vulnerabilidades más maduro.
5. Si el motor principal es la notificación de vulnerabilidades del artículo 14 del CRA, CycloneDX es la opción más natural. Generar ambos formatos a partir de un único análisis con Syft constituye una estrategia válida.
