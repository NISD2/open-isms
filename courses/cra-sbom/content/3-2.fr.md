# Leçon 3.2 : Maintenir votre SBOM à jour et surveiller les vulnérabilités

Un SBOM généré une fois et plus jamais retouché échoue à sa raison d'être. L'inventaire des composants change à chaque mise à jour de dépendance, correctif du système d'exploitation ou changement de chaîne d'outils de build. Et les vulnérabilités dans ces composants sont publiées en continu. Cette leçon traite de comment maintenir le SBOM à jour et de comment l'utiliser comme outil de surveillance au titre de l'article 14.

## Pourquoi le SBOM vieillit

Un SBOM reflète l'état de votre produit à un moment précis. À l'instant où vous fusionnez une pull request qui met à jour une dépendance, votre SBOM est périmé. À l'instant où une nouvelle [[CVE]] est publiée pour un composant de votre SBOM, votre exposition aux vulnérabilités a changé, mais pas votre SBOM.

Deux choses provoquent la dérive du SBOM :

1. **Changements de composants** : mises à jour de dépendances, correctifs du système d'exploitation, mises à jour des outils de build, changements de résolution des dépendances transitives quand vous figez une version de premier niveau et que ses sous-dépendances évoluent.
2. **Publication de vulnérabilités** : une CVE pour un composant qui était sûr hier peut être publiée aujourd'hui.

La réponse à la dérive de type 1 est la régénération automatisée. La réponse à la dérive de type 2 est l'analyse automatisée.

## Régénération automatisée du SBOM

Déclenchez la génération du SBOM dans le cadre de chaque build qui produit un artefact de publication. Ne générez pas le SBOM selon un calendrier, générez-le dans le cadre du build, à partir du même artefact que le build produit.

La règle est : un SBOM par artefact de publication, généré au moment du build, stocké avec l'artefact.

Si votre produit livre des correctifs entre les versions mineures, ce qu'il devrait faire, pour satisfaire aux exigences de mise à jour de sécurité de l'annexe I partie I du CRA, chaque version corrective obtient son propre SBOM. Ce SBOM reflète l'inventaire des composants de ce correctif. Quand une vulnérabilité est divulguée pour un composant qui a été corrigé dans le correctif 2.4.1 mais pas dans le 2.4.0, vous avez besoin du SBOM de la version 2.4.0 pour savoir que cette version était affectée.

## La boucle de surveillance des vulnérabilités

[[Grype]] d'Anchore est l'outil de référence pour la boucle de surveillance. Il prend un SBOM CycloneDX en entrée, compare chaque composant à plusieurs flux de vulnérabilités, et produit un rapport :

```bash
grype sbom:sbom.cdx.json
```

Options de format de sortie :

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

La sortie CycloneDX de Grype peut être refusionnée dans votre SBOM comme un enrichissement de vulnérabilités, vous donnant un document unique qui contient à la fois l'inventaire des composants et le statut de vulnérabilité actuel.

Grype puise dans :
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Les avis de sécurité Red Hat, Debian, Ubuntu, Alpine
- Les bases d'avis Amazon, Oracle, SUSE
- Les flux d'avis spécifiques aux langages (PyPI, npm, Go, Maven, NuGet, Ruby)

## Exécuter la boucle de surveillance automatiquement

Planifiez l'exécution de Grype sur vos SBOM de production à une cadence qui correspond à votre obligation de surveillance de l'article 14 :

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

L'échec du code de sortie déclenche une notification à l'équipe. Le flux de notification devrait être acheminé vers la personne responsable de la décision de signalement de l'article 14.

## Seuils de gravité et le déclencheur de l'article 14

Toutes les vulnérabilités ne nécessitent pas un signalement au titre de l'article 14. L'obligation est déclenchée par une [[actively exploited vulnerability|vulnérabilité activement exploitée]], une vulnérabilité qu'un acteur malveillant utilise actuellement contre des systèmes réels sans autorisation.

La gravité de la CVE (score CVSS) est un signal, pas le déclencheur. Une vulnérabilité CVSS 9.8 qui n'a aucun code d'exploitation public et n'est pas utilisée dans des attaques ne déclenche pas l'article 14. Une vulnérabilité CVSS 6.5 qui figure au catalogue Known Exploited Vulnerabilities (KEV) de la CISA et est activement utilisée dans des campagnes de rançongiciel, oui.

Votre processus de surveillance devrait :

1. **Détecter toutes les gravités au-dessus d'un seuil** : Critique et Élevée au minimum
2. **Vérifier le KEV** : le catalogue KEV de la CISA liste les vulnérabilités actuellement exploitées. Grype signale les entrées KEV. La CISA publie le KEV sous forme de flux JSON à l'adresse `kev.cisa.gov/api/v1/catalog`.
3. **Évaluer l'applicabilité** : le composant vulnérable est-il réellement atteignable dans votre produit ? Le chemin de code vulnérable est-il sollicité ? Documentez cette évaluation.
4. **Escalader si activement exploitée** : si un composant de votre SBOM a une CVE qui figure au catalogue KEV et que le composant est atteignable dans votre produit, escaladez immédiatement pour la décision de signalement sous 24 heures de l'article 14.
5. **Documenter la décision** : que vous signaliez ou que vous concluiez à un « non affecté », documentez la décision et le raisonnement. Utilisez une déclaration [[VEX]] pour consigner les décisions « non affecté » sous forme lisible par machine.

## Utiliser Dependency-Track pour une surveillance continue

Pour les organisations gérant plusieurs produits, OWASP Dependency-Track fournit un tableau de bord centralisé. Vous téléversez des SBOM dans Dependency-Track, il surveille en continu les flux de vulnérabilités, et vous alerte quand une nouvelle CVE affecte un composant dans n'importe quel SBOM téléversé.

Dependency-Track s'intègre avec :
- JIRA (crée des tickets pour les nouvelles découvertes critiques)
- Slack et Teams (envoie des alertes)
- API REST (interroge le statut de vulnérabilité par programmation)

Pour un fabricant avec cinq produits ou plus couverts par le CRA, Dependency-Track réduit la charge opérationnelle de la boucle de surveillance de l'article 14, d'un processus manuel quotidien à un système d'alerte automatisé.

## Points clés à retenir

1. Les SBOM vieillissent quand les composants changent et quand de nouvelles CVE sont publiées. Régénérez automatiquement au moment du build, un SBOM par artefact de publication.
2. [[Grype]] analyse un SBOM au regard de plusieurs flux de vulnérabilités et signale les correspondances. Lancez-le quotidiennement ou à chaque déploiement.
3. Le déclencheur de l'article 14 est une vulnérabilité activement exploitée : pas le score CVSS seul. Vérifiez le catalogue KEV de la CISA pour identifier quelles CVE sont actuellement utilisées dans des attaques.
4. Documentez chaque évaluation : que vous signaliez ou que vous concluiez à un « non affecté ». Utilisez les déclarations [[VEX]] pour une documentation « non affecté » lisible par machine.
5. Pour les portefeuilles multiproduits, OWASP Dependency-Track fournit une surveillance continue centralisée qui transforme la boucle d'analyse quotidienne en un système d'alerte automatisé.
