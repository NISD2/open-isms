# Lição 1.1: O que inclui uma SBOM: Componentes, Versões e Identificadores

O Anexo I, Parte II, ponto (1) do CRA indica que deve criar uma SBOM. Não especifica todos os campos a incluir. Os formatos [[CycloneDX]] e [[SPDX]] preenchem essa lacuna. Esta lição aborda os campos que a SBOM deve conter para ser útil na prática: para um analisador de vulnerabilidades, para um auditor e para si quando algo corre mal às 2 da manhã.

## O mínimo exigido pelo CRA

O mínimo do CRA é: "componentes contidos nos produtos com elementos digitais ... pelo menos as dependências de nível superior". Na prática, isso significa que cada entrada de componente precisa de informação suficiente para responder a:

- O que é este componente?
- Quem o produziu?
- Qual é a sua versão?
- Como posso consultá-lo numa base de dados de vulnerabilidades?

Estas quatro perguntas correspondem diretamente aos campos essenciais exigidos tanto pelo CycloneDX como pelo SPDX.

## Os campos essenciais

### Nome

O nome do componente tal como publicado pelo responsável do pacote. Não o seu alias interno. O nome exato tal como aparece no registo do pacote. Para npm: `@angular/core`. Para Maven: `org.springframework.boot:spring-boot`. Para Python: `requests`.

Os nomes exatos são importantes porque as bases de dados de vulnerabilidades indexam pelo nome canónico do pacote. Uma diferença menor na grafia impede a consulta.

### Versão

A cadeia de versão exata. Para pacotes npm: `17.0.0`. Para bibliotecas de sistema: `2.38.1-5+deb12u1`. Intervalos como `>=2.0` não são aceitáveis. Não indicam a um analisador qual o binário que está realmente em execução.

A versão é importante porque uma [[CVE]] afeta normalmente um intervalo de versões e é corrigida numa versão específica. Sem a versão exata, não é possível determinar se o componente está afetado.

### Fornecedor

A organização que publica ou mantém o componente. Para pacotes npm: o autor ou a organização indicados no manifesto do pacote. Para pacotes de sistema operativo: o responsável pela distribuição. Para bibliotecas comerciais: o fornecedor.

O fornecedor é relevante para a imagem de risco de [[supply chain attack|ataque à cadeia de fornecimento]]. Se um fornecedor for comprometido, saber quais dos seus componentes provêm desse fornecedor indica onde procurar primeiro.

### Identificador único: o PURL

Um [[PURL]] (Package URL) é a forma normalizada de identificar um componente de forma única entre registos e bases de dados. O formato é:

```
pkg:type/namespace/name@version
```

Exemplos:

- `pkg:npm/%40angular/core@17.0.0`: Angular Core 17.0.0 do npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0`: Spring Boot 3.2.0 do Maven Central
- `pkg:pypi/requests@2.31.0`: requests 2.31.0 do PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3`: libc6 do Debian Bookworm

Tanto o CycloneDX como o SPDX tratam o PURL como o identificador único recomendado. As bases de dados de vulnerabilidades utilizam-no para associar registos CVE a componentes específicos. Quando o analisador compara uma SBOM com um feed de vulnerabilidades, está a comparar PURLs.

### Hash

Um [[hash|hash]] é uma impressão digital de comprimento fixo do ficheiro do componente. O SHA-256 é o padrão. Incluir um hash em cada entrada da SBOM permite verificar que o componente não foi alterado desde a geração da SBOM. É também a única forma de confirmar que duas equipas estão a falar do mesmo binário e não apenas da mesma cadeia de versão.

O CycloneDX e o SPDX suportam ambos hashes por componente. Adicione-os sempre que as ferramentas os produzirem.

### Licença

Não exigida pelo mínimo do CRA, mas exigida pela maioria dos fluxos de trabalho SPDX e útil na prática. O Identificador de Licença SPDX (por exemplo, `Apache-2.0`, `MIT`, `GPL-2.0-only`) remete para o texto integral da licença.

Se for uma empresa que utiliza componentes de código aberto, a informação de licença na SBOM constitui a base do seu programa de conformidade de licenças de código aberto.

## Metadados da SBOM

Para além da lista de componentes, uma SBOM válida inclui metadados sobre o próprio documento da SBOM:

- **Timestamp**: momento em que a SBOM foi gerada
- **Versão da SBOM**: uma versão ou identificador para este documento de SBOM específico
- **Informação da ferramenta**: qual a ferramenta que gerou a SBOM e em que versão
- **Descreve**: qual o produto ou componente que esta SBOM descreve (o pacote de nível superior)

O CycloneDX designa este objeto por `metadata`. O SPDX designa-o por secção de informação de criação do documento. Os auditores consultam primeiro esta secção para verificar a atualidade.

## O que significa "legível por máquina" na prática

O CRA exige um formato "legível por máquina". Isto significa que um analisador de vulnerabilidades deve conseguir analisar a SBOM sem intervenção humana. O JSON e o XML satisfazem este requisito. Uma folha de cálculo ou um PDF não.

Uma SBOM legível por máquina permite automatizar o ciclo de monitorização do Artigo 14: nova CVE publicada → analisador compara com a SBOM → alerta gerado → equipa avalia → relatório apresentado se necessário.

Se a SBOM for um PDF, nenhuma dessa automação funciona.

## Principais conclusões

1. Cada entrada de componente da SBOM necessita, no mínimo, de: nome, versão, fornecedor e um identificador único. O [[PURL]] é o identificador único normalizado.
2. São necessárias cadeias de versão exatas. Os intervalos comprometem a análise de vulnerabilidades.
3. Um hash por componente permite verificar que a SBOM não divergiu do binário realmente implementado.
4. Os metadados da SBOM (timestamp, ferramenta, descreve) são o primeiro elemento que um auditor verifica.
5. "Legível por máquina" significa JSON ou XML: formatos que um analisador de vulnerabilidades pode analisar automaticamente. Uma folha de cálculo ou um PDF não qualificam.
