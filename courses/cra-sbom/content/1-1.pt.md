# Lição 1.1: O Que Entra Num SBOM: Componentes, Versões e Identificadores

O Artigo 13(5) do CRA diz-lhe para criar um SBOM. Não lhe diz todos os campos a incluir. Os formatos, [[CycloneDX]] e [[SPDX]], preenchem essa lacuna. Esta lição abrange os campos que o seu SBOM deve conter para ser útil na prática: para um scanner de vulnerabilidades, para um auditor e para si quando algo corre mal às 2 da manhã.

## O mínimo que o CRA exige

O mínimo do CRA é: "componentes contidos nos produtos com elementos digitais ... pelo menos as dependências de topo." Na prática, isto significa que cada entrada de componente precisa de informação suficiente para responder a:

- O que é este componente?
- Quem o fez?
- Qual é a sua versão?
- Como o procuro numa base de dados de vulnerabilidades?

Estas quatro perguntas correspondem diretamente aos campos centrais que tanto o CycloneDX como o SPDX exigem.

## Os campos centrais

### Nome

O nome do componente tal como o mantenedor do pacote o publica. Não o seu alias interno. O nome exato tal como aparece no registo de pacotes. Para npm: `@angular/core`. Para Maven: `org.springframework.boot:spring-boot`. Para Python: `requests`.

Os nomes exatos são importantes porque as bases de dados de vulnerabilidades indexam pelo nome canónico do pacote. Uma pequena diferença de ortografia quebra a pesquisa.

### Versão

A string exata da versão. Para pacotes npm: `17.0.0`. Para bibliotecas de sistema: `2.38.1-5+deb12u1`. Intervalos como `>=2.0` não são aceitáveis. Não dizem a um scanner qual o binário que está realmente a correr.

A versão é importante porque um [[CVE]] afeta normalmente um intervalo de versões e é corrigido numa versão específica. Sem a versão exata, não consegue determinar se o seu componente está afetado.

### Fornecedor

A organização que publica ou mantém o componente. Para pacotes npm: o autor ou organização listado no manifesto do pacote. Para pacotes de sistema operativo: o mantenedor da distribuição. Para bibliotecas comerciais: o fornecedor.

O fornecedor é importante para o panorama de risco de [[supply chain attack|ataque à cadeia de fornecimento]]. Se um fornecedor for comprometido, saber quais dos seus componentes vêm desse fornecedor diz-lhe onde procurar primeiro.

### Identificador único: o PURL

Um [[PURL]] (Package URL) é a forma padrão de identificar um componente de forma única através de registos e bases de dados. O formato é:

```
pkg:type/namespace/name@version
```

Exemplos:

- `pkg:npm/%40angular/core@17.0.0`: Angular Core 17.0.0 do npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0`: Spring Boot 3.2.0 do Maven Central
- `pkg:pypi/requests@2.31.0`: requests 2.31.0 do PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3`: libc6 do Debian Bookworm

Tanto o CycloneDX como o SPDX tratam o PURL como o identificador único recomendado. As bases de dados de vulnerabilidades usam-no para ligar registos CVE a componentes específicos. Quando o seu scanner compara um SBOM com um feed de vulnerabilidades, está a comparar PURLs.

### Hash

Um [[hash]] é uma impressão digital de comprimento fixo do ficheiro do componente. SHA-256 é o padrão. Incluir um hash em cada entrada do SBOM permite-lhe verificar que o componente não foi alterado desde que o SBOM foi gerado. É também a única forma de confirmar que duas equipas estão a falar do mesmo binário, e não apenas da mesma string de versão.

O CycloneDX e o SPDX suportam ambos hashes por componente. Adicione-os sempre que as suas ferramentas os produzam.

### Licença

Não exigida pelo mínimo do CRA, mas exigida pela maioria dos fluxos de trabalho SPDX e útil na prática. O SPDX License Identifier (por exemplo, `Apache-2.0`, `MIT`, `GPL-2.0-only`) liga ao texto completo da licença.

Se for uma empresa que usa componentes open-source, a informação de licença no SBOM é a base do seu programa de conformidade de licenças open-source.

## Metadados do SBOM

Para além da lista de componentes, um SBOM válido inclui metadados sobre o próprio documento SBOM:

- **Carimbo temporal**: quando o SBOM foi gerado
- **Versão do SBOM**: uma versão ou identificador para este documento SBOM específico
- **Informação da ferramenta**: que ferramenta gerou o SBOM e em que versão
- **Descreve**: que produto ou componente este SBOM descreve (o pacote de topo)

O CycloneDX chama a isto o objeto `metadata`. O SPDX chama-lhe a secção de informação de criação do documento. Os auditores olham aqui primeiro para verificar a atualidade.

## O que significa "legível por máquina" na prática

O CRA exige um formato "legível por máquina". Isto significa que um scanner de vulnerabilidades deve conseguir interpretar o SBOM sem intervenção humana. JSON e XML satisfazem este requisito. Uma folha de cálculo ou um PDF não.

Um SBOM legível por máquina permite-lhe automatizar o ciclo de monitorização do Artigo 14: novo CVE publicado, o scanner compara o SBOM, o alerta é gerado, a equipa avalia, o relatório é apresentado se necessário.

Se o seu SBOM for um PDF, nenhuma dessa automatização funciona.

## Pontos-chave

1. Cada entrada de componente do SBOM precisa, no mínimo, de: nome, versão, fornecedor e um identificador único. O [[PURL]] é o identificador único padrão.
2. As strings de versão exatas são obrigatórias. Os intervalos quebram a análise de vulnerabilidades.
3. Um hash por componente permite-lhe verificar que o SBOM não se desviou do binário realmente implementado.
4. Os metadados do SBOM (carimbo temporal, ferramenta, descreve) são a primeira coisa que um auditor verifica.
5. "Legível por máquina" significa JSON ou XML, formatos que um scanner de vulnerabilidades consegue interpretar automaticamente. Uma folha de cálculo ou um PDF não qualificam.
