# Lição 3.2: Manter o seu SBOM atualizado e monitorizar vulnerabilidades

Um SBOM gerado uma única vez e nunca mais tocado falha no seu propósito fundamental. O inventário de componentes muda a cada atualização de dependência, patch do sistema operativo ou alteração na cadeia de ferramentas de build. E as vulnerabilidades nesses componentes são publicadas continuamente. Esta lição aborda como manter o SBOM atualizado e como usá-lo como ferramenta de monitorização ao abrigo do Artigo 14.

## Porque é que o SBOM envelhece

Um SBOM reflete o estado do seu produto num momento específico. No instante em que faz merge de um pull request que atualiza uma dependência, o seu SBOM fica desatualizado. No instante em que é publicado um novo [[CVE|CVE]] para um componente do seu SBOM, a sua exposição a vulnerabilidades mudou, mas o seu SBOM não.

Há duas coisas que causam a deriva do SBOM:

1. **Alterações de componentes**: atualizações de dependências, patches do sistema operativo, atualizações das ferramentas de build, alterações na resolução de dependências transitivas quando fixa uma versão de topo e as suas subdependências mudam.
2. **Publicação de vulnerabilidades**: um CVE para um componente que estava seguro ontem pode ser publicado hoje.

A resposta à deriva do tipo 1 é a regeneração automatizada. A resposta à deriva do tipo 2 é a análise automatizada.

## Regeneração automatizada do SBOM

Acione a geração do SBOM como parte de cada build que produz um artefacto de release. Não gere o SBOM com base num agendamento, gere-o como parte do build, a partir do mesmo artefacto que o build produz.

A regra é: um SBOM por artefacto de release, gerado no momento do build, armazenado com o artefacto.

Se o seu produto disponibiliza patches entre versões menores, o que deve fazer para cumprir os requisitos de atualizações de segurança do CRA Anexo I Parte I, cada release de patch recebe o seu próprio SBOM. Esse SBOM reflete o inventário de componentes desse patch. Quando uma vulnerabilidade é divulgada para um componente que foi corrigido no patch 2.4.1 mas não no 2.4.0, precisa do SBOM da versão 2.4.0 para saber que essa versão foi afetada.

## O ciclo de monitorização de vulnerabilidades

O [[Grype|Grype]] da Anchore é a ferramenta padrão para o ciclo de monitorização. Recebe um SBOM CycloneDX como entrada, compara cada componente com vários feeds de vulnerabilidades e produz um relatório:

```bash
grype sbom:sbom.cdx.json
```

Opções de formato de saída:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

A saída CycloneDX do Grype pode ser integrada de volta no seu SBOM como um enriquecimento de vulnerabilidades, dando-lhe um único documento que contém tanto o inventário de componentes como o estado atual de vulnerabilidades.

O Grype recolhe dados de:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Avisos de segurança da Red Hat, Debian, Ubuntu, Alpine
- Bases de dados de avisos da Amazon, Oracle, SUSE
- Feeds de avisos específicos por linguagem (PyPI, npm, Go, Maven, NuGet, Ruby)

## Executar o ciclo de monitorização automaticamente

Agende o Grype para correr contra os seus SBOMs de produção com uma cadência que corresponda à sua obrigação de monitorização do Artigo 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

A falha no código de saída aciona uma notificação para a equipa. O fluxo de notificação deve ser encaminhado para quem é responsável pela decisão de reporte do Artigo 14.

## Limiares de severidade e o gatilho do Artigo 14

Nem toda a vulnerabilidade exige um reporte ao abrigo do Artigo 14. A obrigação é acionada por uma [[actively exploited vulnerability|vulnerabilidade ativamente explorada]], uma vulnerabilidade que um agente malicioso está a usar neste momento contra sistemas reais sem autorização.

A severidade do CVE (pontuação CVSS) é um sinal, não o gatilho. Uma vulnerabilidade CVSS 9.8 que não tenha código de exploração público e não esteja a ser usada em ataques não aciona o Artigo 14. Uma vulnerabilidade CVSS 6.5 que conste do catálogo Known Exploited Vulnerabilities (KEV) da CISA e esteja a ser ativamente usada em campanhas de ransomware aciona.

O seu processo de monitorização deve:

1. **Capturar todas as severidades acima de um limiar**: no mínimo, Crítica e Alta.
2. **Verificar o KEV**: o catálogo KEV da CISA enumera as vulnerabilidades que estão a ser exploradas neste momento. O Grype sinaliza as entradas do KEV. A CISA publica o KEV como um feed JSON em `kev.cisa.gov/api/v1/catalog`.
3. **Avaliar a aplicabilidade**: o componente vulnerável é de facto alcançável no seu produto? O caminho de código vulnerável é exercido? Documente esta avaliação.
4. **Escalar se estiver a ser ativamente explorado**: se um componente do seu SBOM tiver um CVE que conste do catálogo KEV e o componente for alcançável no seu produto, escale de imediato para a decisão de reporte das 24 horas do Artigo 14.
5. **Documentar a decisão**: quer reporte, quer conclua que não está afetado, documente a decisão e a respetiva fundamentação. Use uma declaração [[VEX|VEX]] para registar as decisões de "não afetado" em formato legível por máquina.

## Usar o Dependency-Track para monitorização contínua

Para organizações que gerem vários produtos, o OWASP Dependency-Track fornece um painel centralizado. Carrega os SBOMs para o Dependency-Track, ele monitoriza continuamente os feeds de vulnerabilidades e alerta-o quando um novo CVE afeta um componente de qualquer SBOM carregado.

O Dependency-Track integra-se com:
- JIRA (cria tickets para novas constatações críticas)
- Slack e Teams (envia alertas)
- API REST (consulta o estado de vulnerabilidades de forma programática)

Para um fabricante com cinco ou mais produtos abrangidos pelo CRA, o Dependency-Track reduz a carga operacional do ciclo de monitorização do Artigo 14, passando de um processo manual diário para um sistema de alertas automatizado.

## Pontos-chave

1. Os SBOMs envelhecem quando os componentes mudam e quando são publicados novos CVEs. Regenere automaticamente no momento do build, um SBOM por artefacto de release.
2. O [[Grype|Grype]] analisa um SBOM contra vários feeds de vulnerabilidades e reporta as correspondências. Execute-o diariamente ou em cada implementação.
3. O gatilho do Artigo 14 é uma vulnerabilidade ativamente explorada, não a pontuação CVSS isolada. Verifique o catálogo KEV da CISA para identificar que CVEs estão a ser usados neste momento em ataques.
4. Documente cada avaliação: quer reporte, quer conclua que não está afetado. Use declarações [[VEX|VEX]] para documentação legível por máquina de "não afetado".
5. Para portefólios com vários produtos, o OWASP Dependency-Track fornece monitorização contínua centralizada que transforma o ciclo de análise diário num sistema de alertas automatizado.
