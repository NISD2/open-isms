# Lição 3.2: Manter o seu SBOM atualizado e monitorizar vulnerabilidades

Um SBOM gerado uma única vez e nunca mais atualizado falha no seu objetivo principal. O inventário de componentes altera-se com cada atualização de dependência, patch do sistema operativo ou alteração da toolchain de compilação. As vulnerabilidades nesses componentes são publicadas continuamente. Esta lição explica como manter o SBOM atualizado e como utilizá-lo como ferramenta de monitorização nos termos do Artigo 14.

## Por que o SBOM envelhece

Um SBOM reflete o estado do produto num momento específico. No instante em que funde um pull request que atualiza uma dependência, o seu SBOM fica desatualizado. No instante em que é publicada uma nova [[CVE]] relativa a um componente presente no seu SBOM, a sua exposição a vulnerabilidades alterou-se, mas o SBOM não.

Duas causas provocam a deriva do SBOM:

1. **Alterações de componentes**: atualizações de dependências, patches do sistema operativo, atualizações de ferramentas de compilação, alterações na resolução de dependências transitivas quando fixa uma versão de nível superior e as suas subdependências mudam.
2. **Publicação de vulnerabilidades**: uma CVE relativa a um componente que estava seguro ontem pode ser publicada hoje.

A resposta à deriva do tipo 1 é a regeneração automática. A resposta à deriva do tipo 2 é a análise automática.

## Regeneração automática do SBOM

Desencadeie a geração do SBOM como parte de cada compilação que produza um artefacto de lançamento. Não gere o SBOM num agendamento fixo; gere-o como parte da compilação, a partir do mesmo artefacto que a compilação produz.

A regra é: um SBOM por artefacto de lançamento, gerado no momento da compilação e armazenado com o artefacto.

Se o seu produto distribui patches entre versões menores, como deve fazer para cumprir os requisitos de atualização de segurança do Anexo I Parte I do CRA, cada lançamento de patch recebe o seu próprio SBOM. Esse SBOM reflete o inventário de componentes desse patch. Quando for divulgada uma vulnerabilidade relativa a um componente corrigido no patch 2.4.1 mas não no 2.4.0, precisa do SBOM da versão 2.4.0 para saber que essa versão estava afetada.

## O ciclo de monitorização de vulnerabilidades

[[Grype]] da Anchore é a ferramenta padrão para o ciclo de monitorização. Recebe um SBOM CycloneDX como entrada, compara cada componente com múltiplas fontes de vulnerabilidades e produz um relatório:

```bash
grype sbom:sbom.cdx.json
```

Opções de formato de saída:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

A saída CycloneDX do Grype pode ser fundida de novo no seu SBOM como um aumento de vulnerabilidades, produzindo um único documento que contém tanto o inventário de componentes como o estado atual das vulnerabilidades.

O Grype consulta:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Avisos de segurança da Red Hat, Debian, Ubuntu e Alpine
- Bases de dados de avisos da Amazon, Oracle e SUSE
- Fontes de avisos específicas de linguagens (PyPI, npm, Go, Maven, NuGet, Ruby)

## Execução automática do ciclo de monitorização

Agende a execução do Grype sobre os seus SBOM de produção com uma cadência compatível com a obrigação de monitorização do Artigo 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

A falha no código de saída dispara uma notificação para a equipa. O fluxo de notificação deve ser encaminhado para quem for responsável pela decisão de comunicação prevista no Artigo 14.

## Limiares de gravidade e o acionador do Artigo 14

Nem toda vulnerabilidade exige uma comunicação nos termos do Artigo 14. A obrigação é acionada por uma [[actively exploited vulnerability|vulnerabilidade ativamente explorada]], ou seja, uma vulnerabilidade que um ator malicioso está a utilizar atualmente contra sistemas reais sem autorização.

A gravidade da CVE (pontuação CVSS) é um sinal, não o acionador. Uma vulnerabilidade com CVSS 9.8 sem código de exploração público e que não esteja a ser utilizada em ataques não aciona o Artigo 14. Uma vulnerabilidade com CVSS 6.5 que conste do catálogo Known Exploited Vulnerabilities (KEV) da CISA e esteja a ser utilizada em campanhas de ransomware aciona-o.

O seu processo de monitorização deve:

1. **Capturar todas as gravidades acima de um limiar**: Críticas e Altas, no mínimo.
2. **Verificar o KEV**: o catálogo KEV da CISA lista as vulnerabilidades que estão a ser exploradas atualmente. O Grype sinaliza as entradas do KEV. A CISA publica o KEV como feed JSON em `kev.cisa.gov/api/v1/catalog`.
3. **Avaliar a aplicabilidade**: o componente vulnerável é efetivamente alcançável no seu produto? O caminho de código vulnerável é executado? Documente esta avaliação.
4. **Escalar se ativamente explorada**: se um componente presente no seu SBOM tiver uma CVE que conste do catálogo KEV e o componente for alcançável no seu produto, escale imediatamente para a decisão de comunicação no prazo de 24 horas prevista no Artigo 14.
5. **Documentar a decisão**: independentemente de comunicar ou concluir que não está afetado, documente a decisão e a respetiva fundamentação. Utilize uma declaração [[VEX]] para registar as decisões de «não afetado» em formato legível por máquina.

## Utilização do Dependency-Track para monitorização contínua

Para organizações que gerem vários produtos, o OWASP Dependency-Track fornece um painel centralizado. Carrega os SBOM para o Dependency-Track; este monitoriza continuamente as fontes de vulnerabilidades e alerta quando uma nova CVE afeta um componente de qualquer SBOM carregado.

O Dependency-Track integra-se com:
- JIRA (cria tickets para novas descobertas críticas)
- Slack e Teams (envia alertas)
- REST API (consulta o estado de vulnerabilidades de forma programática)

Para um fabricante com cinco ou mais produtos abrangidos pelo CRA, o Dependency-Track reduz a sobrecarga operacional do ciclo de monitorização do Artigo 14, transformando um processo manual diário num sistema de alertas automatizado.

## Principais conclusões

1. Os SBOM envelhecem quando os componentes mudam e quando são publicadas novas CVE. Regenere-os automaticamente no momento da compilação, um SBOM por artefacto de lançamento.
2. O [[Grype]] analisa um SBOM contra múltiplas fontes de vulnerabilidades e reporta correspondências. Execute-o diariamente ou em cada implementação.
3. O acionador do Artigo 14 é uma vulnerabilidade ativamente explorada, não apenas a pontuação CVSS. Consulte o catálogo KEV da CISA para identificar quais CVE estão a ser utilizadas em ataques.
4. Documente todas as avaliações: independentemente de comunicar ou concluir que não está afetado. Utilize declarações [[VEX]] para documentação legível por máquina das decisões de «não afetado».
5. Para carteiras com vários produtos, o OWASP Dependency-Track fornece monitorização contínua centralizada que converte o ciclo de análise diário num sistema de alertas automatizado.
