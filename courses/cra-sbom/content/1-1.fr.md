# Leçon 1.1 : Ce que contient un SBOM : composants, versions et identifiants

L'annexe I, partie II, point (1) du CRA indique de créer un SBOM. Elle ne précise pas tous les champs à inclure. Les formats [[CycloneDX]] et [[SPDX]] comblent cette lacune. Cette leçon présente les champs que le SBOM doit contenir pour être utile en pratique : à un scanner de vulnérabilités, à un auditeur et à vous-même lorsqu'un incident survient à 2 h du matin.

## Le minimum exigé par le CRA

Le minimum du CRA est : « composants contenus dans les produits comportant des éléments numériques ... au moins les dépendances de premier niveau ». En pratique, cela signifie que chaque entrée de composant doit fournir suffisamment d'informations pour répondre aux questions suivantes :

- De quel composant s'agit-il ?
- Qui l'a créé ?
- Quelle est sa version ?
- Comment le rechercher dans une base de données de vulnérabilités ?

Ces quatre questions correspondent directement aux champs principaux que CycloneDX et SPDX exigent tous deux.

## Les champs principaux

### Nom

Le nom du composant tel que le mainteneur du paquet le publie. Il ne s'agit pas de votre alias interne, mais du nom exact tel qu'il figure dans le registre de paquets. Pour npm : `@angular/core`. Pour Maven : `org.springframework.boot:spring-boot`. Pour Python : `requests`.

Les noms exacts comptent, car les bases de données de vulnérabilités indexent par le nom canonique du paquet. Une différence mineure d'orthographe empêche la recherche.

### Version

La chaîne de version exacte. Pour les paquets npm : `17.0.0`. Pour les bibliothèques système : `2.38.1-5+deb12u1`. Les intervalles tels que `>=2.0` ne sont pas acceptables. Ils n'indiquent pas à un scanner quel binaire est réellement exécuté.

La version compte, car une [[CVE]] affecte généralement un intervalle de versions et est corrigée dans une version précise. Sans la version exacte, il est impossible de déterminer si le composant est affecté.

### Fournisseur

L'organisation qui publie ou maintient le composant. Pour les paquets npm : l'auteur ou l'organisation indiqué dans le manifeste du paquet. Pour les paquets de système d'exploitation : le mainteneur de la distribution. Pour les bibliothèques commerciales : l'éditeur.

Le fournisseur compte pour l'évaluation du [[supply chain attack|risque d'attaque de la chaîne d'approvisionnement]]. Si un fournisseur est compromis, savoir quels composants proviennent de ce fournisseur permet de savoir où chercher en priorité.

### Identifiant unique : le PURL

Un [[PURL]] (Package URL) est la méthode normalisée pour identifier un composant de façon unique entre registres et bases de données. Le format est :

```
pkg:type/namespace/name@version
```

Exemples :

- `pkg:npm/%40angular/core@17.0.0` : Angular Core 17.0.0 depuis npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0` : Spring Boot 3.2.0 depuis Maven Central
- `pkg:pypi/requests@2.31.0` : requests 2.31.0 depuis PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3` : libc6 depuis Debian Bookworm

CycloneDX et SPDX considèrent tous deux le PURL comme l'identifiant unique recommandé. Les bases de données de vulnérabilités l'utilisent pour lier les enregistrements CVE à des composants précis. Lorsqu'un scanner met en correspondance un SBOM avec un flux de vulnérabilités, il utilise les PURL.

### Empreinte

Une [[hash|empreinte]] est une empreinte de longueur fixe du fichier du composant. SHA-256 est la norme. L'inclusion d'une empreinte dans chaque entrée du SBOM permet de vérifier que le composant n'a pas été modifié depuis la génération du SBOM. C'est également le seul moyen de confirmer que deux équipes parlent du même binaire et non seulement de la même chaîne de version.

CycloneDX et SPDX prennent tous deux en charge les empreintes par composant. Ajoutez-les chaque fois que l'outil les produit.

### Licence

Non exigée par le minimum du CRA, mais requise par la plupart des flux SPDX et utile en pratique. L'identifiant de licence SPDX (par exemple `Apache-2.0`, `MIT`, `GPL-2.0-only`) renvoie au texte complet de la licence.

Si vous êtes une entreprise utilisant des composants open source, les informations de licence dans le SBOM constituent le socle de votre programme de conformité aux licences open source.

## Métadonnées du SBOM

Au-delà de la liste des composants, un SBOM valide inclut des métadonnées sur le document SBOM lui-même :

- **Horodatage** : date et heure de génération du SBOM
- **Version du SBOM** : version ou identifiant de ce document SBOM précis
- **Informations sur l'outil** : quel outil a généré le SBOM et à quelle version
- **Décrit** : quel produit ou composant ce SBOM décrit (le paquet de premier niveau)

CycloneDX nomme cet objet `metadata`. SPDX l'appelle la section d'informations sur la création du document. Les auditeurs consultent ces données en premier pour vérifier la fraîcheur.

## Ce que signifie « lisible par machine » en pratique

Le CRA exige un format « lisible par machine ». Cela signifie qu'un scanner de vulnérabilités doit pouvoir analyser le SBOM sans intervention humaine. JSON et XML satisfont cette exigence. Une feuille de calcul ou un PDF ne la satisfait pas.

Un SBOM lisible par machine permet d'automatiser la boucle de surveillance de l'article 14 : nouvelle CVE publiée → le scanner met en correspondance le SBOM → alerte déclenchée → l'équipe évalue → rapport déposé si nécessaire.

Si votre SBOM est un PDF, aucune de ces automatisations ne fonctionne.

## Points clés

1. Chaque entrée de composant du SBOM doit contenir au minimum : nom, version, fournisseur et un identifiant unique. Le [[PURL]] est l'identifiant unique normalisé.
2. Les chaînes de version exactes sont requises. Les intervalles perturbent l'analyse des vulnérabilités.
3. Une empreinte par composant permet de vérifier que le SBOM n'a pas dévié du binaire réellement déployé.
4. Les métadonnées du SBOM (horodatage, outil, décrit) sont les premières informations qu'un auditeur vérifie.
5. « Lisible par machine » signifie JSON ou XML : des formats qu'un scanner de vulnérabilités peut analyser automatiquement. Une feuille de calcul ou un PDF ne convient pas.
