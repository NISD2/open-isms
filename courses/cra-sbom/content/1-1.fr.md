# Leçon 1.1 : Ce qui entre dans un SBOM : composants, versions et identifiants

L'article 13(5) du CRA vous demande de créer un SBOM. Il ne vous indique pas chaque champ à inclure. Les formats, [[CycloneDX]] et [[SPDX]], comblent ce vide. Cette leçon traite des champs que votre SBOM doit contenir pour être utile en pratique : à un scanner de vulnérabilités, à un auditeur, et à vous-même quand quelque chose tourne mal à 2 heures du matin.

## Le minimum exigé par le CRA

Le minimum du CRA est : « composants contenus dans les produits comportant des éléments numériques ... au minimum les dépendances de premier niveau ». En pratique, cela signifie que chaque entrée de composant a besoin d'assez d'informations pour répondre à :

- Quel est ce composant ?
- Qui l'a créé ?
- Quelle est sa version ?
- Comment le rechercher dans une base de données de vulnérabilités ?

Ces quatre questions correspondent directement aux champs fondamentaux que CycloneDX et SPDX exigent tous deux.

## Les champs fondamentaux

### Nom

Le nom du composant tel que le mainteneur du paquet le publie. Pas votre alias interne. Le nom exact tel qu'il apparaît dans le registre de paquets. Pour npm : `@angular/core`. Pour Maven : `org.springframework.boot:spring-boot`. Pour Python : `requests`.

Les noms exacts comptent, car les bases de données de vulnérabilités indexent par le nom canonique du paquet. Une différence d'orthographe mineure casse la recherche.

### Version

La chaîne de version exacte. Pour les paquets npm : `17.0.0`. Pour les bibliothèques système : `2.38.1-5+deb12u1`. Les plages comme `>=2.0` ne sont pas acceptables, elles n'indiquent pas à un scanner quel binaire est réellement exécuté.

La version compte, car une [[CVE]] affecte généralement une plage de versions et est corrigée dans une version précise. Sans la version exacte, vous ne pouvez pas déterminer si votre composant est affecté.

### Fournisseur

L'organisation qui publie ou maintient le composant. Pour les paquets npm : l'auteur ou l'organisation indiqué dans le manifeste du paquet. Pour les paquets de système d'exploitation : le mainteneur de la distribution. Pour les bibliothèques commerciales : le fournisseur.

Le fournisseur compte pour le tableau de risque d'[[supply chain attack|attaque de la chaîne d'approvisionnement]]. Si un fournisseur est compromis, savoir lesquels de vos composants proviennent de ce fournisseur vous indique où regarder en premier.

### Identifiant unique : le PURL

Un [[PURL]] (Package URL) est la manière standard d'identifier un composant de manière unique à travers les registres et les bases de données. Le format est :

```
pkg:type/namespace/name@version
```

Exemples :

- `pkg:npm/%40angular/core@17.0.0` : Angular Core 17.0.0 depuis npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0` : Spring Boot 3.2.0 depuis Maven Central
- `pkg:pypi/requests@2.31.0` : requests 2.31.0 depuis PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3` : libc6 depuis Debian Bookworm

CycloneDX et SPDX considèrent tous deux le PURL comme l'identifiant unique recommandé. Les bases de données de vulnérabilités l'utilisent pour relier les fiches CVE à des composants précis. Quand votre scanner compare un SBOM à un flux de vulnérabilités, il compare des PURL.

### Empreinte (hash)

Une [[hash|empreinte]] est une signature de longueur fixe du fichier de composant. SHA-256 est la norme. Inclure une empreinte dans chaque entrée du SBOM vous permet de vérifier que le composant n'a pas changé depuis la génération du SBOM. C'est aussi la seule façon de confirmer que deux équipes parlent du même binaire, pas seulement de la même chaîne de version.

CycloneDX et SPDX prennent tous deux en charge les empreintes par composant. Ajoutez-les chaque fois que votre outillage les produit.

### Licence

Non requise par le minimum du CRA, mais requise par la plupart des flux SPDX et utile en pratique. L'identifiant de licence SPDX (par ex. `Apache-2.0`, `MIT`, `GPL-2.0-only`) renvoie au texte complet de la licence.

Si vous êtes une entreprise qui utilise des composants open source, l'information de licence dans le SBOM est le socle de votre programme de conformité des licences open source.

## Métadonnées du SBOM

Au-delà de la liste des composants, un SBOM valide inclut des métadonnées sur le document SBOM lui-même :

- **Horodatage** : quand le SBOM a été généré
- **Version du SBOM** : une version ou un identifiant pour ce document SBOM précis
- **Information sur l'outil** : quel outil a généré le SBOM et à quelle version
- **Décrit** : quel produit ou composant ce SBOM décrit (le paquet de premier niveau)

CycloneDX appelle cela l'objet `metadata`. SPDX l'appelle la section d'information sur la création du document. Les auditeurs regardent ici en premier pour vérifier la fraîcheur.

## Ce que « lisible par machine » signifie en pratique

Le CRA exige un format « lisible par machine ». Cela signifie qu'un scanner de vulnérabilités doit pouvoir analyser le SBOM sans intervention humaine. JSON et XML satisfont à cette exigence. Un tableur ou un PDF non.

Un SBOM lisible par machine vous permet d'automatiser la boucle de surveillance de l'article 14 : nouvelle CVE publiée → le scanner compare le SBOM → alerte déclenchée → l'équipe évalue → signalement déposé si nécessaire.

Si votre SBOM est un PDF, aucune de ces automatisations ne fonctionne.

## Points clés à retenir

1. Chaque entrée de composant du SBOM a besoin au minimum de : nom, version, fournisseur et un identifiant unique. Le [[PURL]] est l'identifiant unique standard.
2. Les chaînes de version exactes sont requises : les plages cassent l'analyse des vulnérabilités.
3. Une empreinte par composant vous permet de vérifier que le SBOM n'a pas dérivé par rapport au binaire réellement déployé.
4. Les métadonnées du SBOM (horodatage, outil, ce qu'il décrit) sont la première chose qu'un auditeur vérifie.
5. « Lisible par machine » signifie JSON ou XML : des formats qu'un scanner de vulnérabilités peut analyser automatiquement. Un tableur ou un PDF ne satisfont pas à cette exigence.
