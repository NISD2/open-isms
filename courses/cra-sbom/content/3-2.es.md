# Lección 3.2: Mantener el SBOM actualizado y supervisar vulnerabilidades

Un SBOM generado una sola vez y que nunca se modifica vuelve a fallar en su propósito principal. El inventario de componentes cambia con cada actualización de dependencias, parche del sistema operativo o modificación de la cadena de herramientas de compilación. Las vulnerabilidades de esos componentes se publican de forma continua. Esta lección explica cómo mantener el SBOM actualizado y cómo utilizarlo como herramienta de supervisión conforme al Artículo 14.

## Por qué el SBOM envejece

Un SBOM refleja el estado del producto en un momento concreto. En el instante en que se fusiona una solicitud de cambios que actualiza una dependencia, el SBOM deja de estar vigente. Cuando se publica un nuevo [[CVE]] para un componente del SBOM, la exposición a vulnerabilidades ha cambiado, pero el SBOM no.

Dos factores provocan la deriva del SBOM:

1. **Cambios en los componentes**: actualizaciones de dependencias, parches del sistema operativo, actualizaciones de herramientas de compilación, cambios en la resolución de dependencias transitivas cuando se fija una versión de nivel superior y sus subdependencias se desplazan.
2. **Publicación de vulnerabilidades**: un CVE para un componente que ayer era seguro puede publicarse hoy.

La solución al primer tipo de deriva es la regeneración automatizada. La solución al segundo tipo es el escaneo automatizado.

## Regeneración automatizada del SBOM

Active la generación del SBOM como parte de cada compilación que produzca un artefacto de publicación. No genere el SBOM según una programación fija; genérelo durante la compilación, a partir del mismo artefacto que esta produce.

La regla es: un SBOM por artefacto de publicación, generado en el momento de la compilación y almacenado junto con el artefacto.

Si el producto distribuye parches entre versiones menores, como debe hacer para cumplir los requisitos de actualización de seguridad del Anexo I Parte I del CRA, cada publicación de parche recibe su propio SBOM. Ese SBOM refleja el inventario de componentes de ese parche. Cuando se divulga una vulnerabilidad de un componente corregido en el parche 2.4.1 pero no en el 2.4.0, se necesita el SBOM de la versión 2.4.0 para saber que esa versión estaba afectada.

## El bucle de supervisión de vulnerabilidades

[[Grype]] de Anchore es la herramienta estándar para el bucle de supervisión. Recibe como entrada un SBOM en formato CycloneDX, compara cada componente con varias fuentes de vulnerabilidades y genera un informe:

```bash
grype sbom:sbom.cdx.json
```

Opciones de formato de salida:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

La salida en formato CycloneDX de Grype puede fusionarse de nuevo con el SBOM como aumento de vulnerabilidades, de modo que se obtiene un único documento que contiene tanto el inventario de componentes como el estado actual de vulnerabilidades.

Grype consulta:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Avisos de seguridad de Red Hat, Debian, Ubuntu y Alpine
- Bases de datos de avisos de Amazon, Oracle y SUSE
- Fuentes de avisos específicas de lenguajes (PyPI, npm, Go, Maven, NuGet, Ruby)

## Ejecución automática del bucle de supervisión

Programe Grype para que se ejecute sobre los SBOM de producción con una periodicidad acorde con la obligación de supervisión del Artículo 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

El fallo del código de salida activa una notificación al equipo. El flujo de notificación debe dirigirse a quien sea responsable de la decisión de notificación conforme al Artículo 14.

## Umbrales de gravedad y el disparador del Artículo 14

No toda vulnerabilidad exige una notificación conforme al Artículo 14. La obligación se activa ante una [[actively exploited vulnerability|vulnerabilidad explotada activamente]], es decir, una vulnerabilidad que un actor malicioso está utilizando en ese momento contra sistemas reales sin autorización.

La gravedad del CVE (puntuación CVSS) es una señal, no el disparador. Una vulnerabilidad con CVSS 9.8 sin código de explotación público y que no se esté utilizando en ataques no activa el Artículo 14. Una vulnerabilidad con CVSS 6.5 que figure en el catálogo Known Exploited Vulnerabilities (KEV) de CISA y se esté utilizando en campañas de ransomware sí lo activa.

El proceso de supervisión debe:

1. **Capturar todas las vulnerabilidades por encima de un umbral**: como mínimo, las de gravedad Crítica y Alta.
2. **Consultar el KEV**: el catálogo KEV de CISA enumera las vulnerabilidades que se están explotando actualmente. Grype marca las entradas del KEV. CISA publica el KEV como fuente JSON en `kev.cisa.gov/api/v1/catalog`.
3. **Evaluar la aplicabilidad**: ¿el componente vulnerable es realmente accesible en el producto? ¿Se ejecuta la ruta de código vulnerable? Documente esta evaluación.
4. **Escalar si se explota activamente**: si un componente del SBOM tiene un CVE que figura en el catálogo KEV y el componente es accesible en el producto, escale de inmediato para la decisión de notificación en 24 horas del Artículo 14.
5. **Documentar la decisión**: tanto si se notifica como si se concluye que no está afectado, documente la decisión y su justificación. Utilice una declaración [[VEX]] para registrar las decisiones de «no afectado» en formato legible por máquina.

## Uso de Dependency-Track para la supervisión continua

Para las organizaciones que gestionan varios productos, OWASP Dependency-Track ofrece un panel centralizado. Se cargan los SBOM en Dependency-Track, que supervisa de forma continua las fuentes de vulnerabilidades y envía alertas cuando un nuevo CVE afecta a un componente de cualquier SBOM cargado.

Dependency-Track se integra con:
- JIRA (crea incidencias para nuevos hallazgos críticos)
- Slack y Teams (envía alertas)
- REST API (consulta el estado de vulnerabilidades de forma programática)

Para un fabricante con cinco o más productos cubiertos por el CRA, Dependency-Track reduce la carga operativa del bucle de supervisión del Artículo 14, pasando de un proceso manual diario a un sistema de alertas automatizado.

## Conclusiones principales

1. Los SBOM envejecen cuando cambian los componentes y cuando se publican nuevos CVE. Regenerelos automáticamente en el momento de la compilación, un SBOM por artefacto de publicación.
2. [[Grype]] analiza un SBOM frente a varias fuentes de vulnerabilidades e informa de las coincidencias. Ejecútelo a diario o en cada despliegue.
3. El disparador del Artículo 14 es una vulnerabilidad explotada activamente, no solo la puntuación CVSS. Consulte el catálogo KEV de CISA para identificar qué CVE se están utilizando actualmente en ataques.
4. Documente cada evaluación: tanto si notifica como si concluye que no está afectado. Utilice declaraciones [[VEX]] para la documentación legible por máquina de las decisiones de «no afectado».
5. Para carteras con varios productos, OWASP Dependency-Track ofrece supervisión continua centralizada que convierte el bucle de escaneo diario en un sistema de alertas automatizado.
