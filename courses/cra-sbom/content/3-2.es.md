# Lección 3.2: Mantener tu SBOM actualizado y vigilar las vulnerabilidades

Un SBOM generado una vez y no tocado nunca más falla en su propósito esencial. El inventario de componentes cambia con cada actualización de dependencias, parche del SO o cambio en la cadena de herramientas de compilación. Y las vulnerabilidades en esos componentes se publican de forma continua. Esta lección trata cómo mantener el SBOM actualizado y cómo usarlo como herramienta de seguimiento del Artículo 14.

## Por qué envejece el SBOM

Un SBOM refleja el estado de tu producto en un momento concreto. En el momento en que fusionas una pull request que actualiza una dependencia, tu SBOM queda obsoleto. En el momento en que se publica un nuevo [[CVE]] para un componente de tu SBOM, tu exposición a vulnerabilidades ha cambiado, pero tu SBOM no.

Dos cosas provocan la deriva del SBOM:

1. **Cambios de componentes**: actualizaciones de dependencias, parches del SO, actualizaciones de herramientas de compilación, cambios en la resolución de dependencias transitivas cuando fijas una versión de nivel superior y sus subdependencias se desplazan.
2. **Publicación de vulnerabilidades**: un CVE para un componente que ayer era seguro puede publicarse hoy.

La respuesta a la deriva de tipo 1 es la regeneración automatizada. La respuesta a la deriva de tipo 2 es el análisis automatizado.

## Regeneración automatizada del SBOM

Desencadena la generación del SBOM como parte de cada compilación que produzca un artefacto de release. No generes el SBOM según un calendario, genéralo como parte de la compilación, a partir del mismo artefacto que la compilación produce.

La regla es: un SBOM por artefacto de release, generado en tiempo de compilación, almacenado con el artefacto.

Si tu producto entrega parches entre versiones menores, lo que debería hacer, para cumplir los requisitos de actualizaciones de seguridad del Anexo I Parte I del CRA, cada versión de parche obtiene su propio SBOM. Ese SBOM refleja el inventario de componentes de ese parche. Cuando se divulga una vulnerabilidad para un componente que se corrigió en el parche 2.4.1 pero no en el 2.4.0, necesitas el SBOM del 2.4.0 para saber que esa versión estaba afectada.

## El bucle de seguimiento de vulnerabilidades

[[Grype]] de Anchore es la herramienta estándar para el bucle de seguimiento. Toma como entrada un SBOM CycloneDX, coteja cada componente contra múltiples feeds de vulnerabilidades y produce un informe:

```bash
grype sbom:sbom.cdx.json
```

Opciones de formato de salida:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

La salida CycloneDX de Grype puede fusionarse de nuevo en tu SBOM como una ampliación de vulnerabilidades, dándote un único documento que contiene tanto el inventario de componentes como el estado actual de vulnerabilidades.

Grype obtiene datos de:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Avisos de seguridad de Red Hat, Debian, Ubuntu, Alpine
- Bases de datos de avisos de Amazon, Oracle, SUSE
- Feeds de avisos específicos del lenguaje (PyPI, npm, Go, Maven, NuGet, Ruby)

## Ejecutar el bucle de seguimiento automáticamente

Programa Grype para que se ejecute contra tus SBOM de producción con una cadencia que coincida con tu obligación de seguimiento del Artículo 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

El fallo del código de salida desencadena una notificación al equipo. El flujo de notificación debe enrutarse hacia quien sea responsable de la decisión de notificación del Artículo 14.

## Umbrales de severidad y el desencadenante del Artículo 14

No toda vulnerabilidad requiere una notificación del Artículo 14. La obligación se desencadena por una [[actively exploited vulnerability|vulnerabilidad explotada activamente]], una vulnerabilidad que un actor malicioso está usando actualmente contra sistemas reales sin autorización.

La severidad del CVE (puntuación CVSS) es una señal, no el desencadenante. Una vulnerabilidad CVSS 9.8 que no tiene código de explotación público y no se está usando en ataques no desencadena el Artículo 14. Una vulnerabilidad CVSS 6.5 que figura en el catálogo de Known Exploited Vulnerabilities (KEV) de CISA y se usa activamente en campañas de ransomware sí lo hace.

Tu proceso de seguimiento debería:

1. **Captar todas las severidades por encima de un umbral**: Crítica y Alta como mínimo
2. **Comprobar el KEV**: el catálogo KEV de CISA enumera las vulnerabilidades que se están explotando actualmente. Grype señala las entradas del KEV. CISA publica el KEV como un feed JSON en `kev.cisa.gov/api/v1/catalog`.
3. **Evaluar la aplicabilidad**: ¿es el componente vulnerable realmente alcanzable en tu producto? ¿Se ejercita la ruta de código vulnerable? Documenta esta evaluación.
4. **Escalar si está explotada activamente**: si un componente de tu SBOM tiene un CVE que figura en el catálogo KEV y el componente es alcanzable en tu producto, escala de inmediato para la decisión de notificación en 24 horas del Artículo 14.
5. **Documentar la decisión**: tanto si notificas como si concluyes que no está afectado, documenta la decisión y el razonamiento. Usa una declaración [[VEX]] para capturar las decisiones de "no afectado" en forma legible por máquina.

## Usar Dependency-Track para el seguimiento continuo

Para las organizaciones que gestionan múltiples productos, OWASP Dependency-Track proporciona un panel centralizado. Subes los SBOM a Dependency-Track, este vigila de forma continua los feeds de vulnerabilidades y te alerta cuando un nuevo CVE afecta a un componente de cualquier SBOM subido.

Dependency-Track se integra con:
- JIRA (crea tickets para nuevos hallazgos críticos)
- Slack y Teams (envía alertas)
- API REST (consulta el estado de vulnerabilidades mediante programación)

Para un fabricante con cinco o más productos cubiertos por el CRA, Dependency-Track reduce la carga operativa del bucle de seguimiento del Artículo 14, pasando de un proceso manual diario a un sistema de alertas automatizado.

## Puntos clave

1. Los SBOM envejecen cuando los componentes cambian y cuando se publican nuevos CVE. Regenéralos automáticamente en tiempo de compilación, un SBOM por artefacto de release.
2. [[Grype]] analiza un SBOM contra múltiples feeds de vulnerabilidades e informa de las coincidencias. Ejecútalo a diario o en cada despliegue.
3. El desencadenante del Artículo 14 es una vulnerabilidad explotada activamente, no la puntuación CVSS por sí sola. Comprueba el catálogo KEV de CISA para identificar qué CVE se están usando actualmente en ataques.
4. Documenta cada evaluación: tanto si notificas como si concluyes que no está afectado. Usa declaraciones [[VEX]] para documentación de "no afectado" legible por máquina.
5. Para carteras de múltiples productos, OWASP Dependency-Track proporciona un seguimiento continuo centralizado que convierte el bucle de análisis diario en un sistema de alertas automatizado.
