# Lição 2.2: SPDX e Escolha do Seu Formato

[[SPDX]] é o outro formato que satisfaz o requisito do Anexo I, Parte II, ponto (1) do CRA para um SBOM "comum e legível por máquina". Esta lição aborda o que é o SPDX, onde difere do CycloneDX e como decidir qual formato utilizar.

## O que é o SPDX

O Software Package Data Exchange (SPDX) foi criado na Linux Foundation em 2010. Tornou-se norma ISO em 2021: ISO/IEC 5962:2021. A versão 2.3 é a atual para a norma ISO. A versão 3.0 foi publicada em 2024 com um novo modelo de dados e sistema de perfis.

O SPDX foi concebido para resolver o problema da conformidade de licenças de código aberto. Quando se distribui um produto que inclui componentes de código aberto, existem obrigações legais: atribuição, inclusão do texto da licença e divulgação do código-fonte para licenças copyleft. O SPDX oferece uma forma legível por máquina de expressar que licenças se aplicam a cada componente e que obrigações foram aceites.

Com o tempo, tornou-se uma norma de SBOM e agora abrange também os campos de inventário de componentes necessários para a gestão de vulnerabilidades. Contudo, a intenção original de conceção (conformidade de licenças) continua visível no modelo de dados.

## Estrutura do documento SPDX

Um documento SPDX 2.3 em JSON contém:

- **Informação de criação do documento**: equivalente aos metadados do CycloneDX: criador, data e hora de criação, espaço de nomes do documento, versão do SPDX
- **Packages**: o inventário de componentes. Cada pacote inclui: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` ou `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (onde se insere o [[PURL]])
- **Relationships**: como os pacotes se relacionam entre si. A relação `DESCRIBES` identifica o produto de nível superior. `DEPENDS_ON` e `DEPENDENCY_OF` mapeiam o grafo de dependências.
- **Files** (opcional): inventário ao nível do ficheiro com hashes, caso seja necessária granularidade ao nível do ficheiro
- **Snippets** (opcional): ao nível do excerto de código, para código copiado que não provém de um pacote

O campo PURL do SPDX 2.3 encontra-se dentro do array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Isto é mais verboso do que o campo `purl` de primeira classe do CycloneDX, mas continua a ser legível por máquina e analisável por scanners de vulnerabilidades.

## Vantagens do SPDX

**Normalização ISO.** ISO/IEC 5962:2021 significa que o SPDX é o único formato de SBOM que constitui uma norma internacional. Para organizações que exigem formatos certificados pela ISO nos seus processos de aquisição ou contratos com fornecedores, isto é relevante.

**Fluxos de trabalho de conformidade de licenças.** Se o principal caso de uso do SBOM for a conformidade de licenças de código aberto, o acompanhamento de obrigações de atribuição, a identificação de código contaminado por GPL ou a geração de avisos de terceiros, o modelo rico de licenças do SPDX é mais adequado. O SPDX suporta identificadores de licença SPDX, `LicenseInfoInFile` para deteção de licenças ao nível do ficheiro e `licenseComments` para situações complexas.

**Integração com o grafo de dependências do GitHub.** O grafo de dependências do GitHub exporta nativamente SPDX 2.3 em JSON. Se o repositório estiver no GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` fornece um SBOM em SPDX sem necessidade de executar ferramentas locais. Para muitas equipas, este é o ponto de partida mais simples.

**Múltiplos formatos de saída.** O SPDX suporta JSON, YAML, RDF/XML e um formato de texto tag-value. O formato tag-value é legível por humanos (ao contrário de JSON ou XML), o que pode ser útil para revisão.

## Vantagens do CycloneDX

**Gestão de vulnerabilidades.** O CycloneDX possui suporte nativo a [[VEX]]. O SPDX 3.0 acrescentou um perfil de segurança com capacidades VEX, mas o suporte do ecossistema para VEX em SPDX ainda está em maturação. Para os fluxos de trabalho de conformidade com o Artigo 14, o VEX do CycloneDX é mais maduro e melhor suportado por ferramentas.

**Dependency-Track.** A principal plataforma de gestão de SBOM de código aberto, o OWASP Dependency-Track, foi construída para o CycloneDX. Aceita entrada em SPDX, mas as suas funcionalidades nativas (correspondência de vulnerabilidades, gestão de VEX, avaliação de políticas) são mais completas para o CycloneDX.

**Maturidade das ferramentas.** A maioria das ferramentas de SBOM, Syft, cdxgen, trivy, grype, trata o CycloneDX como formato de saída principal e o SPDX como secundário.

## Ambos os formatos qualificam para conformidade com o CRA

O CRA exige "comum e legível por máquina". Tanto o CycloneDX como o SPDX são utilizados por centenas de organizações. Ambos são legíveis por máquina. Ambos podem transportar os campos de inventário de componentes exigidos pelo Anexo I, Parte II, ponto (1). Não se falhará uma auditoria ao CRA por ter escolhido SPDX em vez de CycloneDX, ou vice-versa.

A orientação da Comissão Europeia e o documento de boas práticas de SBOM da ENISA referenciam ambos os formatos. Não existe orientação oficial da UE que designe um formato como preferencial em relação ao outro.

## Como escolher

Utilize este quadro de decisão:

| Pergunta | CycloneDX | SPDX |
|---|---|---|
| O principal caso de uso é a gestão de vulnerabilidades e a conformidade com o Artigo 14 | ✓ | - |
| O principal caso de uso é a conformidade de licenças de código aberto | - | ✓ |
| Utiliza o Dependency-Track | ✓ | - |
| Os seus processos de aquisição exigem formatos certificados pela ISO | - | ✓ |
| Está a partir da exportação do grafo de dependências do GitHub | - | ✓ |
| A sua equipa utiliza Syft ou cdxgen | ✓ | - |
| Necessita de ferramentas VEX maduras | ✓ | - |

Se a gestão de vulnerabilidades for a principal preocupação, escolha o CycloneDX. Se já possui um fluxo de trabalho SPDX para conformidade de licenças, estendê-lo para abranger a gestão de vulnerabilidades é razoável. Basta ter em conta que as ferramentas VEX são menos maduras.

Muitas organizações produzem ambos: CycloneDX para operações de segurança e SPDX para fins jurídicos e de aquisição. As ferramentas suportam esta abordagem. O Syft pode gerar ambos a partir da mesma análise.

## Pontos-chave

1. O SPDX (ISO/IEC 5962:2021) é o formato de SBOM normalizado pela ISO. A versão atual é a 2.3 para a norma ISO e a 3.0 para o novo modelo de dados. Foi concebido para conformidade de licenças de código aberto.
2. Tanto o [[CycloneDX]] como o SPDX qualificam como formatos "comuns e legíveis por máquina" nos termos do Anexo I, Parte II, ponto (1) do CRA. Nenhum é oficialmente preferido pela orientação da UE.
3. Vantagens do SPDX: estatuto ISO, modelo de licenças mais rico, exportação nativa do grafo de dependências do GitHub, múltiplos formatos de saída.
4. Vantagens do CycloneDX: suporte nativo a [[VEX]], integração com o Dependency-Track, ecossistema de ferramentas de vulnerabilidades mais maduro.
5. Se o principal impulsionador for a comunicação de vulnerabilidades do Artigo 14 do CRA, o CycloneDX é a escolha mais natural. Produzir ambos os formatos a partir de uma única análise com o Syft é uma estratégia válida.
