# Lição 2.2: SPDX e a Escolha do Formato

O [[SPDX|SPDX]] é o outro formato que cumpre o requisito do Artigo 13(5) do CRA para um SBOM "de uso corrente e legível por máquina". Esta lição aborda o que é o SPDX, em que difere do CycloneDX e como decidir qual o formato a utilizar.

## O que é o SPDX

O Software Package Data Exchange (SPDX) foi criado na Linux Foundation em 2010. Tornou-se uma norma ISO em 2021: ISO/IEC 5962:2021. A versão 2.3 é a versão atual para a norma ISO. A versão 3.0 foi lançada em 2024, com um novo modelo de dados e um sistema de perfis.

O SPDX foi concebido para resolver o problema da conformidade com as licenças de código aberto. Quando se distribui um produto que inclui componentes de código aberto, existem obrigações legais: atribuição, inclusão do texto da licença e divulgação do código-fonte no caso das licenças copyleft. O SPDX oferece uma forma legível por máquina de exprimir que licenças se aplicam a que componentes e que obrigações foram aceites.

Com o tempo, tornou-se uma norma para SBOM e cobre agora também os campos do inventário de componentes necessários para a gestão de vulnerabilidades. Mas a intenção original do seu desenho, a conformidade com licenças, continua visível no modelo de dados.

## Estrutura de um documento SPDX

Um documento JSON SPDX 2.3 tem:

- **Informação de criação do documento** equivalente aos metadados do CycloneDX: criador, data e hora de criação, espaço de nomes do documento, versão do SPDX
- **Packages** o inventário de componentes. Cada package tem: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` ou `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (onde fica o [[PURL|PURL]])
- **Relationships** como os packages se relacionam entre si. A relação `DESCRIBES` identifica o produto de nível superior. `DEPENDS_ON` e `DEPENDENCY_OF` mapeiam o grafo de dependências.
- **Files** (opcional) inventário ao nível do ficheiro, com hashes, se for necessária granularidade ao nível do ficheiro
- **Snippets** (opcional) ao nível do excerto de código, para código copiado que não provém de um package

O campo PURL do SPDX 2.3 fica dentro do array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Isto é mais prolixo do que o campo `purl` de primeira classe do CycloneDX, mas continua a ser legível por máquina e analisável por scanners de vulnerabilidades.

## Onde o SPDX tem vantagem

**Normalização ISO.** A ISO/IEC 5962:2021 significa que o SPDX é o único formato de SBOM que é uma norma internacional. Para organizações que exigem formatos certificados pela ISO nos seus contratos de aquisição ou de fornecedores, isto é relevante.

**Fluxos de trabalho de conformidade com licenças.** Se o seu principal caso de uso do SBOM for a conformidade com licenças de código aberto, o acompanhamento de obrigações de atribuição, a identificação de código contaminado por GPL e a geração de avisos de terceiros, o rico modelo de licenças do SPDX é mais adequado. O SPDX suporta SPDX License Identifiers, `LicenseInfoInFile` para deteção de licenças ao nível do ficheiro e `licenseComments` para situações complexas.

**Integração com o grafo de dependências do GitHub.** O grafo de dependências do GitHub exporta nativamente SPDX 2.3 JSON. Se o seu repositório estiver no GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` dá-lhe um SBOM SPDX sem executar qualquer ferramenta local. Para muitas equipas, este é o ponto de partida mais fácil.

**Vários formatos de saída.** O SPDX suporta JSON, YAML, RDF/XML e um formato de texto tag-value. O formato tag-value é legível por humanos (ao contrário do JSON ou do XML), o que pode ser útil para revisão.

## Onde o CycloneDX tem vantagem

**Gestão de vulnerabilidades.** O CycloneDX tem suporte nativo para [[VEX|VEX]]. O SPDX 3.0 acrescentou um perfil de segurança com capacidades VEX, mas o suporte do ecossistema para o VEX em SPDX ainda está a amadurecer. Para os fluxos de trabalho de conformidade com o Artigo 14, o VEX em CycloneDX é mais maduro e está mais bem suportado pelas ferramentas.

**Dependency-Track.** A principal plataforma de gestão de SBOM em código aberto, o OWASP Dependency-Track, foi construída para o CycloneDX. Aceita entradas em SPDX, mas as suas funcionalidades nativas, a correspondência de vulnerabilidades, a gestão de VEX e a avaliação de políticas, estão mais completas para o CycloneDX.

**Maturidade das ferramentas.** A maioria das ferramentas de SBOM, Syft, cdxgen, trivy, grype, trata o CycloneDX como o seu formato de saída principal e o SPDX como secundário.

## Ambos os formatos qualificam para a conformidade com o CRA

O CRA exige "de uso corrente e legível por máquina". Tanto o CycloneDX como o SPDX são usados por centenas de organizações. Ambos são legíveis por máquina. Ambos podem transportar os campos do inventário de componentes exigidos pelo Artigo 13(5). Não irá reprovar numa auditoria ao CRA por ter escolhido o SPDX em vez do CycloneDX, ou vice-versa.

A orientação da Comissão Europeia e o documento de boas práticas para SBOM da ENISA referem ambos os formatos. Nenhuma orientação oficial da UE designou um formato como preferido em relação ao outro.

## Como escolher

Use este quadro de decisão:

| Pergunta | CycloneDX | SPDX |
|---|---|---|
| O principal caso de uso é a gestão de vulnerabilidades e a conformidade com o Artigo 14 | ✓ | Não |
| O principal caso de uso é a conformidade com licenças de código aberto | Não | ✓ |
| Usa o Dependency-Track | ✓ | Não |
| As suas aquisições exigem formatos certificados pela ISO | Não | ✓ |
| Está a partir da exportação do grafo de dependências do GitHub | Não | ✓ |
| A sua equipa usa o Syft ou o cdxgen | ✓ | Não |
| Precisa de ferramentas VEX maduras | ✓ | Não |

Se a gestão de vulnerabilidades for a sua principal preocupação, escolha o CycloneDX. Se já tiver um fluxo de trabalho em SPDX para conformidade com licenças, estendê-lo para cobrir a gestão de vulnerabilidades é razoável. Tenha apenas presente que as ferramentas VEX são menos maduras.

Muitas organizações produzem ambos: CycloneDX para as operações de segurança, SPDX para o jurídico e as aquisições. As ferramentas suportam isto. O Syft consegue produzir os dois a partir da mesma análise.

## Pontos-chave

1. O SPDX (ISO/IEC 5962:2021) é o formato de SBOM normalizado pela ISO. A versão atual é a 2.3 para a norma ISO e a 3.0 para o novo modelo de dados. Foi concebido para a conformidade com licenças de código aberto.
2. Tanto o [[CycloneDX|CycloneDX]] como o SPDX qualificam como formatos "de uso corrente e legíveis por máquina" ao abrigo do Artigo 13(5) do CRA. Nenhum é oficialmente preferido pela orientação da UE.
3. Vantagens do SPDX: estatuto ISO, modelo de licenças mais rico, exportação nativa do grafo de dependências do GitHub, vários formatos de saída.
4. Vantagens do CycloneDX: suporte nativo para [[VEX|VEX]], integração com o Dependency-Track, ecossistema de ferramentas de vulnerabilidades mais maduro.
5. Se a comunicação de vulnerabilidades do Artigo 14 do CRA for o seu principal motor, o CycloneDX é o que mais naturalmente se enquadra. Produzir ambos os formatos a partir de uma única análise do Syft é uma estratégia válida.
