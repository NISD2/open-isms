# Lesson 3.2: Keeping Your SBOM Current and Monitoring for Vulnerabilities

An SBOM generated once and never touched again fails at its core purpose. The component inventory changes with every dependency update, OS patch, or build toolchain change. And vulnerabilities in those components are published continuously. This lesson covers how to keep the SBOM current and how to use it as an Article 14 monitoring tool.

## Why the SBOM ages

An SBOM reflects the state of your product at a specific moment. The moment you merge a pull request that updates a dependency, your SBOM is stale. The moment a new [[CVE]] is published for a component in your SBOM, your vulnerability exposure has changed, but your SBOM has not.

Two things cause SBOM drift:

1. **Component changes**: dependency updates, OS patches, build tool updates, transitive dependency resolution changes when you pin a top-level version and its sub-dependencies shift.
2. **Vulnerability publication**: a CVE for a component that was safe yesterday may be published today.

The answer to drift type 1 is automated regeneration. The answer to drift type 2 is automated scanning.

## Automated SBOM regeneration

Trigger SBOM generation as part of every build that produces a release artifact. Do not generate the SBOM on a schedule, generate it as part of the build, from the same artifact the build produces.

The rule is: one SBOM per release artifact, generated at build time, stored with the artifact.

If your product ships patches between minor versions, which it should, to meet CRA Annex I Part I security update requirements, each patch release gets its own SBOM. That SBOM reflects the component inventory of that patch. When a vulnerability is disclosed for a component that was fixed in patch 2.4.1 but not 2.4.0, you need the SBOM for 2.4.0 to know that version was affected.

## The vulnerability monitoring loop

[[Grype]] by Anchore is the standard tool for the monitoring loop. It takes a CycloneDX SBOM as input, matches each component against multiple vulnerability feeds, and outputs a report:

```bash
grype sbom:sbom.cdx.json
```

Output format options:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

The CycloneDX output from Grype can be merged back into your SBOM as a vulnerability augmentation, giving you a single document that contains both the component inventory and the current vulnerability status.

Grype pulls from:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Red Hat, Debian, Ubuntu, Alpine security advisories
- Amazon, Oracle, SUSE advisory databases
- Language-specific advisory feeds (PyPI, npm, Go, Maven, NuGet, Ruby)

## Running the monitoring loop automatically

Schedule Grype to run against your production SBOMs on a cadence that matches your Article 14 monitoring obligation:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

The exit code failure triggers a notification to the team. The notification flow should be routed to whoever is responsible for the Article 14 reporting decision.

## Severity thresholds and the Article 14 trigger

Not every vulnerability requires an Article 14 report. The obligation is triggered by an [[actively exploited vulnerability]], a vulnerability that a malicious actor is currently using against real systems without permission.

The CVE severity (CVSS score) is a signal, not the trigger. A CVSS 9.8 vulnerability that has no public exploit code and is not being used in attacks does not trigger Article 14. A CVSS 6.5 vulnerability that is on CISA's Known Exploited Vulnerabilities (KEV) catalogue and is actively used in ransomware campaigns does.

Your monitoring process should:

1. **Catch all severities above a threshold**: Critical and High at minimum
2. **Check KEV**: the CISA KEV catalogue lists vulnerabilities currently being exploited. Grype flags KEV entries. CISA publishes the KEV as a JSON feed at `kev.cisa.gov/api/v1/catalog`.
3. **Assess applicability**: is the vulnerable component actually reachable in your product? Is the vulnerable code path exercised? Document this assessment.
4. **Escalate if actively exploited**: if a component in your SBOM has a CVE that is in the KEV catalogue and the component is reachable in your product, escalate immediately for the Article 14 24-hour reporting decision.
5. **Document the decision**: whether you report or conclude not affected, document the decision and the reasoning. Use a [[VEX]] statement to capture "not affected" decisions in machine-readable form.

## Using Dependency-Track for continuous monitoring

For organisations managing multiple products, OWASP Dependency-Track provides a centralised dashboard. You upload SBOMs to Dependency-Track, it continuously monitors the vulnerability feeds, and alerts you when a new CVE affects a component in any uploaded SBOM.

Dependency-Track integrates with:
- JIRA (creates tickets for new critical findings)
- Slack and Teams (sends alerts)
- REST API (query vulnerability status programmatically)

For a manufacturer with five or more products covered by the CRA, Dependency-Track reduces the operational overhead of the Article 14 monitoring loop from a manual daily process to an automated alert system.

## Key takeaways

1. SBOMs age when components change and when new CVEs are published. Regenerate automatically at build time, one SBOM per release artifact.
2. [[Grype]] scans an SBOM against multiple vulnerability feeds and reports matches. Run it daily or on every deployment.
3. The Article 14 trigger is an actively exploited vulnerability, not CVSS score alone. Check the CISA KEV catalogue to identify which CVEs are currently being used in attacks.
4. Document every assessment: whether you report or conclude not affected. Use [[VEX]] statements for machine-readable not-affected documentation.
5. For multi-product portfolios, OWASP Dependency-Track provides centralised continuous monitoring that turns the daily scan loop into an automated alert system.
