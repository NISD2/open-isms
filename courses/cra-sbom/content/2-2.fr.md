# Leçon 2.2 : SPDX et choix du format

[[SPDX]] est l'autre format qui satisfait à l'exigence de l'Annexe I, partie II, point (1) du CRA concernant un SBOM « couramment utilisé et lisible par machine ». Cette leçon présente SPDX, ses différences avec CycloneDX et les critères de choix du format.

## Ce qu'est SPDX

Software Package Data Exchange (SPDX) a été créé à la Linux Foundation en 2010. Il est devenu une norme ISO en 2021 : ISO/IEC 5962:2021. La version 2.3 est la version en vigueur pour la norme ISO. La version 3.0 a été publiée en 2024 avec un nouveau modèle de données et un système de profils.

SPDX a été conçu pour résoudre le problème de conformité aux licences open source. Lorsque vous livrez un produit qui inclut des composants open source, vous avez des obligations légales : attribution, inclusion du texte de licence, divulgation du code source pour les licences copyleft. SPDX fournit un moyen lisible par machine d'exprimer les licences applicables aux composants et les obligations acceptées.

Il est devenu une norme SBOM au fil du temps et couvre désormais les champs d'inventaire des composants nécessaires à la gestion des vulnérabilités. Cependant, son intention initiale (conformité aux licences) reste visible dans le modèle de données.

## Structure d'un document SPDX

Un document SPDX 2.3 au format JSON contient :

- **Informations de création du document** : équivalent aux métadonnées de CycloneDX : créateur, horodatage de création, espace de noms du document, version SPDX
- **Packages** : l'inventaire des composants. Chaque package comporte : `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` ou `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (où se trouve [[PURL]])
- **Relationships** : les relations entre les packages. La relation `DESCRIBES` identifie le produit de premier niveau. `DEPENDS_ON` et `DEPENDENCY_OF` cartographient le graphe de dépendances.
- **Files** (facultatif) : inventaire au niveau des fichiers avec hachages, si une granularité au niveau des fichiers est requise
- **Snippets** (facultatif) : niveau des extraits de code, pour le code copié qui ne provient pas d'un package

Le champ PURL de SPDX 2.3 se trouve dans le tableau `externalRefs` :

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Ce format est plus verbeux que le champ `purl` de première classe de CycloneDX, mais il reste lisible par machine et exploitable par les scanners de vulnérabilités.

## Avantages de SPDX

**Normalisation ISO.** ISO/IEC 5962:2021 signifie que SPDX est le seul format SBOM qui constitue une norme internationale. Pour les organisations qui exigent des formats certifiés ISO dans leurs achats ou contrats fournisseurs, cela compte.

**Processus de conformité aux licences.** Si votre cas d'usage principal du SBOM est la conformité aux licences open source, le suivi des obligations d'attribution, l'identification du code contaminé par la GPL ou la génération d'avis de tiers, le modèle de licences riche de SPDX est mieux adapté. SPDX prend en charge les identifiants de licence SPDX, `LicenseInfoInFile` pour la détection des licences au niveau des fichiers et `licenseComments` pour les situations complexes.

**Intégration au graphe de dépendances GitHub.** Le graphe de dépendances de GitHub exporte nativement au format SPDX 2.3 JSON. Si votre dépôt se trouve sur GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` fournit un SBOM SPDX sans exécuter d'outil local. Pour de nombreuses équipes, il s'agit du point de départ le plus simple.

**Formats de sortie multiples.** SPDX prend en charge JSON, YAML, RDF/XML et un format texte tag-value. Le format tag-value est lisible par l'humain (contrairement à JSON ou XML), ce qui peut être utile pour la relecture.

## Avantages de CycloneDX

**Gestion des vulnérabilités.** CycloneDX dispose d'un support natif de [[VEX]]. SPDX 3.0 a ajouté un profil de sécurité avec des capacités VEX, mais le support de l'écosystème pour VEX dans SPDX est encore en maturation. Pour les processus de conformité à l'article 14, VEX de CycloneDX est plus mature et mieux pris en charge par les outils.

**Dependency-Track.** La principale plateforme open source de gestion des SBOM, OWASP Dependency-Track, a été conçue pour CycloneDX. Elle accepte les entrées SPDX, mais ses fonctionnalités natives (mise en correspondance des vulnérabilités, gestion VEX, évaluation des politiques) sont les plus complètes pour CycloneDX.

**Maturité des outils.** La majorité des outils SBOM, Syft, cdxgen, trivy, grype, traitent CycloneDX comme format de sortie principal et SPDX comme format secondaire.

## Les deux formats sont conformes au CRA

Le CRA exige un format « couramment utilisé, lisible par machine ». CycloneDX et SPDX sont tous deux utilisés par des centaines d'organisations. Les deux sont lisibles par machine. Les deux peuvent transporter les champs d'inventaire des composants requis par l'Annexe I, partie II, point (1). Le choix de SPDX plutôt que CycloneDX, ou inversement, ne fera pas échouer un audit CRA.

Les orientations de la Commission européenne et le document de bonnes pratiques SBOM d'ENISA font référence aux deux formats. Aucune orientation officielle de l'UE n'a désigné un format comme préféré à l'autre.

## Comment choisir

Utilisez ce cadre de décision :

| Question | CycloneDX | SPDX |
|---|---|---|
| Le cas d'usage principal est la gestion des vulnérabilités et la conformité à l'article 14 | ✓ | - |
| Le cas d'usage principal est la conformité aux licences open source | - | ✓ |
| Vous utilisez Dependency-Track | ✓ | - |
| Vos achats exigent des formats certifiés ISO | - | ✓ |
| Vous partez de l'export du graphe de dépendances GitHub | - | ✓ |
| Votre équipe utilise Syft ou cdxgen | ✓ | - |
| Vous avez besoin d'outils VEX matures | ✓ | - |

Si la gestion des vulnérabilités constitue votre préoccupation principale, choisissez CycloneDX. Si vous disposez déjà d'un processus SPDX pour la conformité aux licences, l'étendre à la gestion des vulnérabilités est raisonnable. Gardez simplement à l'esprit que les outils VEX sont moins matures.

De nombreuses organisations produisent les deux formats : CycloneDX pour les opérations de sécurité, SPDX pour les aspects juridiques et les achats. Les outils le permettent. Syft peut produire les deux à partir du même scan.

## Points clés à retenir

1. SPDX (ISO/IEC 5962:2021) est le format SBOM normalisé ISO. La version en vigueur est la 2.3 pour la norme ISO et la 3.0 pour le nouveau modèle de données. Il a été conçu pour la conformité aux licences open source.
2. [[CycloneDX]] et SPDX sont tous deux des formats « couramment utilisés et lisibles par machine » au sens de l'Annexe I, partie II, point (1) du CRA. Aucun n'est officiellement préféré par les orientations de l'UE.
3. Avantages de SPDX : statut ISO, modèle de licences plus riche, export natif du graphe de dépendances GitHub, formats de sortie multiples.
4. Avantages de CycloneDX : support natif de [[VEX]], intégration avec Dependency-Track, écosystème d'outils de vulnérabilité plus mature.
5. Si le signalement des vulnérabilités au titre de l'article 14 du CRA constitue votre moteur principal, CycloneDX constitue le choix le plus naturel. Produire les deux formats à partir d'un seul scan Syft constitue une stratégie valide.
