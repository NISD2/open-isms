# Leçon 2.2 : SPDX et le choix de votre format

[[SPDX]] est l'autre format qui satisfait à l'exigence de l'article 13(5) du CRA d'un SBOM « couramment utilisé et lisible par machine ». Cette leçon traite de ce qu'est SPDX, de ce qui le distingue de CycloneDX, et de comment décider quel format utiliser.

## Ce qu'est SPDX

Software Package Data Exchange (SPDX) a été créé à la Linux Foundation en 2010. Il est devenu une norme ISO en 2021 : ISO/IEC 5962:2021. La version 2.3 est la version actuelle pour la norme ISO. La version 3.0 a été publiée en 2024 avec un nouveau modèle de données et un système de profils.

SPDX a été conçu pour résoudre le problème de la conformité des licences open source. Quand vous livrez un produit incluant des composants open source, vous avez des obligations légales : attribution, inclusion du texte de licence, divulgation du code source pour les licences copyleft. SPDX vous donne une manière lisible par machine d'exprimer quelles licences s'appliquent à quels composants et quelles obligations vous avez acceptées.

Il est devenu un standard SBOM avec le temps, et couvre désormais aussi les champs d'inventaire des composants nécessaires à la gestion des vulnérabilités. Mais son intention de conception d'origine, la conformité des licences, reste visible dans le modèle de données.

## Structure d'un document SPDX

Un document SPDX 2.3 JSON comporte :

- **Information sur la création du document** : équivalente aux métadonnées CycloneDX : créateur, horodatage de création, espace de noms du document, version SPDX
- **Paquets** : l'inventaire des composants. Chaque paquet a : `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` ou `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (où va le [[PURL]])
- **Relations** : comment les paquets se rapportent les uns aux autres. La relation `DESCRIBES` identifie le produit de premier niveau. `DEPENDS_ON` et `DEPENDENCY_OF` cartographient le graphe de dépendances.
- **Fichiers** (facultatif) : inventaire au niveau des fichiers avec empreintes, si vous avez besoin d'une granularité au niveau des fichiers
- **Extraits** (facultatif) : au niveau de l'extrait de code, pour le code copié qui ne provient pas d'un paquet

Le champ PURL de SPDX 2.3 réside à l'intérieur du tableau `externalRefs` :

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

C'est plus verbeux que le champ `purl` de première classe de CycloneDX, mais cela reste lisible par machine et analysable par les scanners de vulnérabilités.

## Là où SPDX a un avantage

**Normalisation ISO.** ISO/IEC 5962:2021 fait de SPDX le seul format SBOM qui est une norme internationale. Pour les organisations qui exigent des formats certifiés ISO dans leurs achats ou leurs contrats fournisseurs, cela compte.

**Flux de conformité des licences.** Si votre cas d'usage principal du SBOM est la conformité des licences open source, le suivi des obligations d'attribution, l'identification du code contaminé par GPL, la génération des avis tiers, le modèle de licence riche de SPDX est mieux adapté. SPDX prend en charge les identifiants de licence SPDX, `LicenseInfoInFile` pour la détection de licence au niveau des fichiers, et `licenseComments` pour les situations complexes.

**Intégration au graphe de dépendances GitHub.** Le graphe de dépendances de GitHub exporte nativement du SPDX 2.3 JSON. Si votre dépôt est sur GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` vous donne un SBOM SPDX sans exécuter aucun outillage local. Pour beaucoup d'équipes, c'est le point de départ le plus simple.

**Formats de sortie multiples.** SPDX prend en charge JSON, YAML, RDF/XML et un format texte tag-value. Le format tag-value est lisible par un humain (contrairement à JSON ou XML), ce qui peut être utile pour la relecture.

## Là où CycloneDX a un avantage

**Gestion des vulnérabilités.** CycloneDX a une prise en charge native de [[VEX]]. SPDX 3.0 a ajouté un profil de sécurité avec des capacités VEX, mais la prise en charge de l'écosystème pour VEX dans SPDX est encore en maturation. Pour les flux de conformité à l'article 14, VEX dans CycloneDX est plus mature et mieux pris en charge par l'outillage.

**Dependency-Track.** La principale plateforme open source de gestion des SBOM, OWASP Dependency-Track, a été conçue pour CycloneDX. Elle accepte les entrées SPDX, mais ses fonctionnalités natives : correspondance des vulnérabilités, gestion VEX, évaluation des politiques, sont les plus complètes pour CycloneDX.

**Maturité de l'outillage.** La majorité des outils SBOM, Syft, cdxgen, trivy, grype, traitent CycloneDX comme leur format de sortie principal et SPDX comme secondaire.

## Les deux formats satisfont à la conformité au CRA

Le CRA exige « couramment utilisé et lisible par machine ». CycloneDX et SPDX sont tous deux utilisés par des centaines d'organisations. Les deux sont lisibles par machine. Les deux peuvent porter les champs d'inventaire des composants requis par l'article 13(5). Vous n'échouerez pas à un audit du CRA parce que vous avez choisi SPDX plutôt que CycloneDX, ou inversement.

Les orientations de la Commission européenne et le document de bonnes pratiques SBOM de l'ENISA font tous deux référence aux deux formats. Aucune orientation officielle de l'UE n'a désigné un format comme préféré par rapport à l'autre.

## Comment choisir

Utilisez ce cadre de décision :

| Question | CycloneDX | SPDX |
|---|---|---|
| Le cas d'usage principal est la gestion des vulnérabilités et la conformité à l'article 14 | ✓ | - |
| Le cas d'usage principal est la conformité des licences open source | - | ✓ |
| Vous utilisez Dependency-Track | ✓ | - |
| Vos achats exigent des formats certifiés ISO | - | ✓ |
| Vous partez de l'export du graphe de dépendances GitHub | - | ✓ |
| Votre équipe utilise Syft ou cdxgen | ✓ | - |
| Vous avez besoin d'un outillage VEX mature | ✓ | - |

Si la gestion des vulnérabilités est votre préoccupation principale, choisissez CycloneDX. Si vous avez déjà un flux SPDX pour la conformité des licences, l'étendre pour couvrir la gestion des vulnérabilités est raisonnable, soyez simplement conscient que l'outillage VEX est moins mature.

Beaucoup d'organisations produisent les deux : CycloneDX pour les opérations de sécurité, SPDX pour le juridique et les achats. Les outils prennent cela en charge. Syft peut produire les deux à partir d'une même analyse.

## Points clés à retenir

1. SPDX (ISO/IEC 5962:2021) est le format SBOM normalisé ISO. La version actuelle est la 2.3 pour la norme ISO, la 3.0 pour le nouveau modèle de données. Il a été conçu pour la conformité des licences open source.
2. [[CycloneDX]] et SPDX satisfont tous deux comme formats « couramment utilisés et lisibles par machine » au titre de l'article 13(5) du CRA. Aucun n'est officiellement préféré par les orientations de l'UE.
3. Avantages de SPDX : statut ISO, modèle de licence plus riche, export natif du graphe de dépendances GitHub, formats de sortie multiples.
4. Avantages de CycloneDX : prise en charge native de [[VEX]], intégration à Dependency-Track, écosystème d'outillage des vulnérabilités plus mature.
5. Si le signalement des vulnérabilités de l'article 14 du CRA est votre moteur principal, CycloneDX est le choix le plus naturel. Produire les deux formats à partir d'une seule analyse Syft est une stratégie valable.
