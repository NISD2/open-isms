# Lezione 2.2: SPDX e la scelta del formato

[[SPDX]] è l'altro formato che soddisfa il requisito dell'Articolo 13(5) CRA di un SBOM "comunemente utilizzato e leggibile meccanicamente". Questa lezione copre cos'è SPDX, dove differisce da CycloneDX e come decidere quale formato usare.

## Cos'è SPDX

Software Package Data Exchange (SPDX) è stato creato presso la Linux Foundation nel 2010. È diventato uno standard ISO nel 2021: ISO/IEC 5962:2021. La versione 2.3 è quella attuale per lo standard ISO. La versione 3.0 è stata rilasciata nel 2024 con un nuovo modello di dati e un sistema di profili.

SPDX è stato progettato per risolvere il problema della conformità alle licenze open source. Quando distribuisci un prodotto che include componenti open source, hai obblighi di legge: attribuzione, inclusione del testo della licenza, divulgazione del codice sorgente per le licenze copyleft. SPDX ti offre un modo leggibile meccanicamente per esprimere quali licenze si applicano a quali componenti e quali obblighi hai accettato.

È diventato uno standard SBOM nel tempo, e ora copre anche i campi dell'inventario dei componenti necessari per la gestione delle vulnerabilità. Ma la sua intenzione progettuale originaria, la conformità alle licenze, è ancora visibile nel modello di dati.

## Struttura di un documento SPDX

Un documento SPDX 2.3 JSON ha:

- **Informazioni di creazione del documento**: equivalente ai metadati di CycloneDX: creatore, timestamp di creazione, namespace del documento, versione SPDX
- **Pacchetti**: l'inventario dei componenti. Ogni pacchetto ha: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` o `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (dove va il [[PURL]])
- **Relazioni**: come i pacchetti si relazionano tra loro. La relazione `DESCRIBES` identifica il prodotto di primo livello. `DEPENDS_ON` e `DEPENDENCY_OF` mappano il grafo delle dipendenze.
- **File** (facoltativo), inventario a livello di file con hash, se hai bisogno di granularità a livello di file
- **Snippet** (facoltativo), a livello di frammento di codice, per il codice copiato che non proviene da un pacchetto

Il campo PURL di SPDX 2.3 risiede all'interno dell'array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Questo è più prolisso del campo `purl` di prima classe di CycloneDX, ma è comunque leggibile meccanicamente e analizzabile dagli scanner di vulnerabilità.

## Dove SPDX ha un vantaggio

**Standardizzazione ISO.** ISO/IEC 5962:2021 significa che SPDX è l'unico formato SBOM che sia uno standard internazionale. Per le organizzazioni che richiedono formati certificati ISO nei loro appalti o contratti con i fornitori, questo conta.

**Flussi di lavoro per la conformità alle licenze.** Se il tuo caso d'uso principale dell'SBOM è la conformità alle licenze open source, il tracciamento degli obblighi di attribuzione, l'identificazione del codice contaminato da GPL, la generazione di avvisi di terze parti, il ricco modello di licenza di SPDX è più adatto. SPDX supporta gli identificatori di licenza SPDX, `LicenseInfoInFile` per il rilevamento delle licenze a livello di file e `licenseComments` per situazioni complesse.

**Integrazione con il dependency graph di GitHub.** Il dependency graph di GitHub esporta nativamente SPDX 2.3 JSON. Se il tuo repository è su GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` ti fornisce un SBOM SPDX senza eseguire alcuno strumento locale. Per molti team questo è il punto di partenza più semplice.

**Formati di output multipli.** SPDX supporta JSON, YAML, RDF/XML e un formato di testo tag-value. Il formato tag-value è leggibile dall'uomo (a differenza di JSON o XML), il che può essere utile per la revisione.

## Dove CycloneDX ha un vantaggio

**Gestione delle vulnerabilità.** CycloneDX ha il supporto nativo per [[VEX]]. SPDX 3.0 ha aggiunto un profilo di sicurezza con capacità VEX, ma il supporto dell'ecosistema per VEX in SPDX è ancora in fase di maturazione. Per i flussi di lavoro di conformità all'Articolo 14, VEX di CycloneDX è più maturo e meglio supportato dagli strumenti.

**Dependency-Track.** La principale piattaforma open source di gestione degli SBOM, OWASP Dependency-Track, è stata costruita per CycloneDX. Accetta input SPDX, ma le sue funzionalità native, corrispondenza delle vulnerabilità, gestione VEX, valutazione delle politiche, sono più complete per CycloneDX.

**Maturità degli strumenti.** La maggior parte degli strumenti per SBOM, Syft, cdxgen, trivy, grype, tratta CycloneDX come formato di output principale e SPDX come secondario.

## Entrambi i formati soddisfano i requisiti del CRA

Il CRA richiede "comunemente utilizzato e leggibile meccanicamente". Sia CycloneDX sia SPDX sono utilizzati da centinaia di organizzazioni. Entrambi sono leggibili meccanicamente. Entrambi possono contenere i campi dell'inventario dei componenti richiesti dall'Articolo 13(5). Non fallirai un audit del CRA per aver scelto SPDX al posto di CycloneDX o viceversa.

Gli orientamenti della Commissione europea e il documento sulle buone prassi per gli SBOM di ENISA fanno entrambi riferimento a entrambi i formati. Nessun orientamento ufficiale dell'UE ha designato un formato come preferito rispetto all'altro.

## Come scegliere

Usa questo schema decisionale:

| Domanda | CycloneDX | SPDX |
|---|---|---|
| Il caso d'uso principale è la gestione delle vulnerabilità e la conformità all'Articolo 14 | ✓ | — |
| Il caso d'uso principale è la conformità alle licenze open source | — | ✓ |
| Usi Dependency-Track | ✓ | — |
| I tuoi appalti richiedono formati certificati ISO | — | ✓ |
| Parti dall'esportazione del dependency graph di GitHub | — | ✓ |
| Il tuo team usa Syft o cdxgen | ✓ | — |
| Hai bisogno di strumenti VEX maturi | ✓ | — |

Se la gestione delle vulnerabilità è la tua preoccupazione principale, scegli CycloneDX. Se hai già un flusso di lavoro SPDX per la conformità alle licenze, estenderlo per coprire la gestione delle vulnerabilità è ragionevole, sii solo consapevole che gli strumenti VEX sono meno maturi.

Molte organizzazioni producono entrambi: CycloneDX per le operazioni di sicurezza, SPDX per il legale e gli appalti. Gli strumenti supportano questa scelta. Syft può produrre entrambi dalla stessa scansione.

## Punti chiave

1. SPDX (ISO/IEC 5962:2021) è il formato SBOM standard ISO. La versione attuale è la 2.3 per lo standard ISO, la 3.0 per il nuovo modello di dati. È stato progettato per la conformità alle licenze open source.
2. Sia [[CycloneDX]] sia SPDX soddisfano i requisiti di formato "comunemente utilizzato e leggibile meccanicamente" ai sensi dell'Articolo 13(5) CRA. Nessuno dei due è ufficialmente preferito dagli orientamenti dell'UE.
3. Vantaggi di SPDX: status ISO, modello di licenza più ricco, esportazione nativa dal dependency graph di GitHub, formati di output multipli.
4. Vantaggi di CycloneDX: supporto nativo per [[VEX]], integrazione con Dependency-Track, ecosistema di strumenti per le vulnerabilità più maturo.
5. Se la segnalazione delle vulnerabilità di cui all'Articolo 14 CRA è il tuo motore principale, CycloneDX è la scelta più naturale. Produrre entrambi i formati da un'unica scansione Syft è una strategia valida.
