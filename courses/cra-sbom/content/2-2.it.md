# Lezione 2.2: SPDX e la scelta del formato

[[SPDX]] è l'altro formato che soddisfa il requisito di cui all'Allegato I, Parte II, punto (1) del CRA per un SBOM "di uso comune e leggibile automaticamente". Questa lezione illustra la natura di SPDX, le differenze rispetto a CycloneDX e i criteri per scegliere il formato.

## Cos'è SPDX

Software Package Data Exchange (SPDX) è stato creato presso la Linux Foundation nel 2010. È diventato uno standard ISO nel 2021: ISO/IEC 5962:2021. La versione 2.3 è quella corrente per lo standard ISO. La versione 3.0 è stata rilasciata nel 2024 con un nuovo modello di dati e un sistema di profili.

SPDX è stato concepito per risolvere il problema della conformità alle licenze open source. Quando si distribuisce un prodotto che include componenti open source, sussistono obblighi giuridici: attribuzione, inclusione del testo della licenza, divulgazione del codice sorgente per le licenze copyleft. SPDX offre un modo leggibile automaticamente per esprimere quali licenze si applicano a quali componenti e quali obblighi sono stati accettati.

Nel tempo è diventato uno standard per gli SBOM e ora copre anche i campi dell'inventario dei componenti necessari per la gestione delle vulnerabilità. Il suo intento progettuale originario (conformità alle licenze) resta tuttavia visibile nel modello di dati.

## Struttura del documento SPDX

Un documento SPDX 2.3 in JSON contiene:

- **Informazioni sulla creazione del documento**: equivalenti ai metadati di CycloneDX: creatore, timestamp di creazione, namespace del documento, versione SPDX
- **Packages**: l'inventario dei componenti. Ogni package include: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` o `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (dove si inserisce [[PURL]])
- **Relationships**: le relazioni tra i package. La relazione `DESCRIBES` identifica il prodotto di livello superiore. `DEPENDS_ON` e `DEPENDENCY_OF` mappano il grafo delle dipendenze.
- **Files** (facoltativo): inventario a livello di file con hash, se serve granularità a livello di file
- **Snippets** (facoltativo): livello di frammenti di codice, per codice copiato che non proviene da un package

Il campo PURL di SPDX 2.3 si trova all'interno dell'array `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Questa struttura è più verbosa del campo `purl` di prima classe di CycloneDX, ma resta leggibile automaticamente e analizzabile dagli scanner di vulnerabilità.

## Vantaggi di SPDX

**Standardizzazione ISO.** ISO/IEC 5962:2021 significa che SPDX è l'unico formato di SBOM che costituisce uno standard internazionale. Per le organizzazioni che richiedono formati certificati ISO nei contratti di approvvigionamento o con i fornitori, questo aspetto conta.

**Flussi di lavoro per la conformità alle licenze.** Se l'uso primario dell'SBOM è la conformità alle licenze open source, il monitoraggio degli obblighi di attribuzione, l'identificazione del codice contaminato da GPL e la generazione di note per terzi, il ricco modello di licenze di SPDX è più adatto. SPDX supporta gli identificatori di licenza SPDX, `LicenseInfoInFile` per il rilevamento delle licenze a livello di file e `licenseComments` per le situazioni complesse.

**Integrazione con il grafo delle dipendenze di GitHub.** Il grafo delle dipendenze di GitHub esporta nativamente SPDX 2.3 JSON. Se il repository si trova su GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` fornisce un SBOM SPDX senza eseguire strumenti locali. Per molti team questo è il punto di partenza più semplice.

**Formati di output multipli.** SPDX supporta JSON, YAML, RDF/XML e un formato testuale tag-value. Il formato tag-value è leggibile da persone (a differenza di JSON o XML) e può risultare utile per le revisioni.

## Vantaggi di CycloneDX

**Gestione delle vulnerabilità.** CycloneDX offre supporto nativo a [[VEX]]. SPDX 3.0 ha aggiunto un profilo di sicurezza con funzionalità VEX, ma il supporto dell'ecosistema per VEX in SPDX è ancora in fase di maturazione. Per i flussi di lavoro di conformità all'articolo 14, VEX di CycloneDX è più maturo e meglio supportato dagli strumenti.

**Dependency-Track.** La principale piattaforma open source per la gestione degli SBOM, OWASP Dependency-Track, è stata sviluppata per CycloneDX. Accetta input SPDX, ma le sue funzionalità native (corrispondenza delle vulnerabilità, gestione VEX, valutazione delle policy) sono più complete per CycloneDX.

**Maturità degli strumenti.** La maggior parte degli strumenti per SBOM, Syft, cdxgen, trivy, grype, tratta CycloneDX come formato di output primario e SPDX come formato secondario.

## Entrambi i formati sono validi per la conformità al CRA

Il CRA richiede un formato "di uso comune e leggibile automaticamente". Sia CycloneDX sia SPDX sono utilizzati da centinaia di organizzazioni. Entrambi sono leggibili automaticamente. Entrambi possono contenere i campi dell'inventario dei componenti richiesti dall'Allegato I, Parte II, punto (1). La scelta di SPDX invece di CycloneDX, o viceversa, non comporta il fallimento di un audit CRA.

Sia la guida della Commissione europea sia il documento ENISA sulle buone prassi per gli SBOM fanno riferimento a entrambi i formati. Nessuna guida ufficiale dell'UE ha designato un formato come preferibile rispetto all'altro.

## Come scegliere

Utilizzare questo quadro decisionale:

| Domanda | CycloneDX | SPDX |
|---|---|---|
| Il caso d'uso primario è la gestione delle vulnerabilità e la conformità all'articolo 14 | ✓ | - |
| Il caso d'uso primario è la conformità alle licenze open source | - | ✓ |
| Si utilizza Dependency-Track | ✓ | - |
| Gli approvvigionamenti richiedono formati certificati ISO | - | ✓ |
| Si parte dall'esportazione del grafo delle dipendenze di GitHub | - | ✓ |
| Il team utilizza Syft o cdxgen | ✓ | - |
| Serve un tooling VEX maturo | ✓ | - |

Se la gestione delle vulnerabilità è la preoccupazione primaria, scegliere CycloneDX. Se si dispone già di un flusso di lavoro SPDX per la conformità alle licenze, estenderlo alla gestione delle vulnerabilità è ragionevole. Occorre solo tenere presente che il tooling VEX è meno maturo.

Molte organizzazioni producono entrambi i formati: CycloneDX per le operazioni di sicurezza e SPDX per gli aspetti giuridici e di approvvigionamento. Gli strumenti lo supportano. Syft può generare entrambi a partire dalla stessa scansione.

## Punti chiave

1. SPDX (ISO/IEC 5962:2021) è il formato di SBOM standard ISO. La versione corrente è la 2.3 per lo standard ISO e la 3.0 per il nuovo modello di dati. È stato progettato per la conformità alle licenze open source.
2. Sia [[CycloneDX]] sia SPDX soddisfano i requisiti di formato "di uso comune e leggibile automaticamente" ai sensi dell'Allegato I, Parte II, punto (1) del CRA. Nessuna guida UE indica una preferenza ufficiale.
3. Vantaggi di SPDX: status ISO, modello di licenze più ricco, esportazione nativa dal grafo delle dipendenze di GitHub, formati di output multipli.
4. Vantaggi di CycloneDX: supporto nativo a [[VEX]], integrazione con Dependency-Track, ecosistema di tooling per le vulnerabilità più maturo.
5. Se il principale motore è la segnalazione delle vulnerabilità ai sensi dell'articolo 14 del CRA, CycloneDX è la scelta più naturale. Produrre entrambi i formati da una singola scansione Syft è una strategia valida.
