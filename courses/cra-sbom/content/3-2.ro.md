# Lecția 3.2: Cum mențineți SBOM-ul la zi și cum monitorizați vulnerabilitățile

Un SBOM generat o singură dată și nemaiatins ratează scopul său fundamental. Inventarul componentelor se schimbă cu fiecare actualizare de dependență, cu fiecare patch de sistem de operare sau cu fiecare modificare a lanțului de instrumente de build. Iar vulnerabilitățile din aceste componente sunt publicate continuu. Această lecție arată cum mențineți SBOM-ul la zi și cum îl folosiți ca instrument de monitorizare conform articolului 14.

## De ce îmbătrânește SBOM-ul

Un SBOM reflectă starea produsului dumneavoastră la un moment precis. În clipa în care faceți merge la un pull request care actualizează o dependență, SBOM-ul devine perimat. În clipa în care un nou [[CVE]] este publicat pentru o componentă din SBOM-ul dumneavoastră, expunerea la vulnerabilități s-a schimbat, însă SBOM-ul nu.

Două lucruri provoacă derapajul SBOM-ului (drift):

1. **Modificările de componente.** Actualizări de dependențe, patch-uri de sistem de operare, actualizări ale instrumentelor de build, schimbări în rezolvarea dependențelor tranzitive atunci când fixați o versiune de nivel superior, iar sub-dependențele se deplasează.
2. **Publicarea vulnerabilităților.** Un CVE pentru o componentă care ieri era sigură poate fi publicat astăzi.

Răspunsul la derapajul de tip 1 este regenerarea automată. Răspunsul la derapajul de tip 2 este scanarea automată.

## Regenerarea automată a SBOM-ului

Declanșați generarea SBOM-ului ca parte a fiecărui build care produce un artefact de release. Nu generați SBOM-ul pe bază de program orar, ci ca parte a build-ului, din același artefact pe care îl produce build-ul.

Regula este: un SBOM per artefact de release, generat la momentul build-ului, stocat împreună cu artefactul.

Dacă produsul dumneavoastră livrează patch-uri între versiunile minore, ceea ce ar trebui să facă pentru a respecta cerințele de actualizare de securitate din CRA Anexa I Partea I, fiecare release de patch primește propriul SBOM. Acel SBOM reflectă inventarul de componente al acelui patch. Când o vulnerabilitate este divulgată pentru o componentă care a fost reparată în patch-ul 2.4.1, dar nu și în 2.4.0, aveți nevoie de SBOM-ul pentru 2.4.0 ca să știți că acea versiune a fost afectată.

## Bucla de monitorizare a vulnerabilităților

[[Grype]] de la Anchore este instrumentul standard pentru bucla de monitorizare. Primește la intrare un SBOM CycloneDX, compară fiecare componentă cu mai multe fluxuri de vulnerabilități și produce un raport:

```bash
grype sbom:sbom.cdx.json
```

Opțiuni pentru formatul de ieșire:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

Ieșirea CycloneDX produsă de Grype poate fi reintegrată în SBOM-ul dumneavoastră ca o augmentare cu vulnerabilități, oferindu-vă un document unic care conține atât inventarul de componente, cât și starea curentă a vulnerabilităților.

Grype extrage din:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Avizele de securitate Red Hat, Debian, Ubuntu, Alpine
- Bazele de date de avize Amazon, Oracle, SUSE
- Fluxuri de avize specifice limbajelor (PyPI, npm, Go, Maven, NuGet, Ruby)

## Rularea automată a buclei de monitorizare

Programați rularea Grype pe SBOM-urile dumneavoastră de producție, cu o cadență care corespunde obligației de monitorizare din articolul 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

Eșecul codului de ieșire (exit code) declanșează o notificare către echipă. Fluxul de notificare ar trebui dirijat către persoana responsabilă de decizia de raportare conform articolului 14.

## Praguri de severitate și declanșatorul articolului 14

Nu orice vulnerabilitate impune un raport conform articolului 14. Obligația este declanșată de o [[actively exploited vulnerability|vulnerabilitate exploatată activ]], o vulnerabilitate pe care un actor rău-intenționat o folosește în prezent împotriva unor sisteme reale, fără permisiune.

Severitatea CVE (scorul CVSS) este un semnal, nu declanșatorul. O vulnerabilitate cu scor CVSS 9.8 care nu are cod de exploatare public și nu este folosită în atacuri nu declanșează articolul 14. O vulnerabilitate cu scor CVSS 6.5 care figurează în catalogul Known Exploited Vulnerabilities (KEV) al CISA și care este folosită activ în campanii de ransomware, da.

Procesul dumneavoastră de monitorizare ar trebui:

1. **Să capteze toate severitățile peste un prag.** Cel puțin Critical și High.
2. **Să verifice KEV.** Catalogul KEV al CISA listează vulnerabilitățile exploatate în prezent. Grype marchează intrările KEV. CISA publică KEV ca flux JSON la `kev.cisa.gov/api/v1/catalog`.
3. **Să evalueze aplicabilitatea.** Componenta vulnerabilă este efectiv accesibilă în produsul dumneavoastră? Calea de cod vulnerabilă este parcursă? Documentați această evaluare.
4. **Să escaladeze dacă este exploatată activ.** Dacă o componentă din SBOM-ul dumneavoastră are un CVE care figurează în catalogul KEV, iar componenta este accesibilă în produs, escaladați imediat pentru decizia de raportare în 24 de ore conform articolului 14.
5. **Să documenteze decizia.** Indiferent dacă raportați sau concluzionați că nu sunteți afectați, documentați decizia și raționamentul. Folosiți o declarație [[VEX]] pentru a consemna deciziile de tip "neafectat" într-o formă citibilă de mașină.

## Folosirea Dependency-Track pentru monitorizare continuă

Pentru organizațiile care gestionează mai multe produse, OWASP Dependency-Track oferă un tablou de bord centralizat. Încărcați SBOM-uri în Dependency-Track, acesta monitorizează continuu fluxurile de vulnerabilități și vă alertează când un nou CVE afectează o componentă din oricare dintre SBOM-urile încărcate.

Dependency-Track se integrează cu:
- JIRA (creează tichete pentru noile constatări critice)
- Slack și Teams (trimite alerte)
- API REST (interogarea programatică a stării vulnerabilităților)

Pentru un producător cu cinci sau mai multe produse acoperite de CRA, Dependency-Track reduce efortul operațional al buclei de monitorizare din articolul 14, transformând-o dintr-un proces manual zilnic într-un sistem automat de alerte.

## Concluzii cheie

1. SBOM-urile îmbătrânesc atunci când se schimbă componentele și când se publică noi CVE-uri. Regenerați-le automat la momentul build-ului, câte un SBOM per artefact de release.
2. [[Grype]] scanează un SBOM comparându-l cu mai multe fluxuri de vulnerabilități și raportează potrivirile. Rulați-l zilnic sau la fiecare implementare.
3. Declanșatorul articolului 14 este o vulnerabilitate exploatată activ, nu doar scorul CVSS. Verificați catalogul KEV al CISA pentru a identifica ce CVE-uri sunt folosite în prezent în atacuri.
4. Documentați fiecare evaluare: indiferent dacă raportați sau concluzionați că nu sunteți afectați. Folosiți declarații [[VEX]] pentru documentația citibilă de mașină a stării "neafectat".
5. Pentru portofoliile cu mai multe produse, OWASP Dependency-Track oferă monitorizare continuă centralizată care transformă bucla de scanare zilnică într-un sistem automat de alerte.
