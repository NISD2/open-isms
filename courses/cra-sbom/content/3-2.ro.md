# Lecția 3.2: Menținerea actualității SBOM și monitorizarea vulnerabilităților

Un SBOM generat o singură dată și niciodată actualizat nu își îndeplinește scopul principal. Inventarul componentelor se modifică la fiecare actualizare de dependență, corecție de sistem de operare sau modificare a lanțului de instrumente de construire. Iar vulnerabilitățile din acele componente sunt publicate în mod continuu. Această lecție prezintă modul de menținere a actualității SBOM și modul de utilizare a acestuia ca instrument de monitorizare conform Articolului 14.

## De ce îmbătrânește SBOM

Un SBOM reflectă starea produsului la un moment specific. În momentul în care integrați o cerere de extragere care actualizează o dependență, SBOM devine învechit. În momentul în care se publică un nou [[CVE]] pentru o componentă din SBOM, expunerea la vulnerabilități s-a modificat, însă SBOM nu.

Două cauze determină derivarea SBOM:

1. **Modificări ale componentelor**: actualizări de dependențe, corecții de sistem de operare, actualizări ale instrumentelor de construire, modificări ale rezoluției dependențelor tranzitive atunci când se fixează o versiune de nivel superior și dependențele sale secundare se modifică.
2. **Publicarea de vulnerabilități**: un CVE pentru o componentă care era sigură ieri poate fi publicat astăzi.

Răspunsul la derivarea de tip 1 este regenerarea automată. Răspunsul la derivarea de tip 2 este scanarea automată.

## Regenerarea automată a SBOM

Declanșați generarea SBOM ca parte a fiecărei construcții care produce un artefact de lansare. Nu generați SBOM conform unui program, generați-l ca parte a construcției, din același artefact pe care îl produce construcția.

Regula este: un SBOM pe artefact de lansare, generat la momentul construirii, stocat împreună cu artefactul.

Dacă produsul distribuie corecții între versiuni minore, ceea ce trebuie să facă pentru a îndeplini cerințele de actualizare de securitate din CRA Anexa I Partea I, fiecare lansare de corecție primește propriul SBOM. Acel SBOM reflectă inventarul de componente al acelei corecții. Atunci când se divulgă o vulnerabilitate pentru o componentă care a fost corectată în corecția 2.4.1 dar nu în 2.4.0, aveți nevoie de SBOM pentru 2.4.0 pentru a ști că versiunea respectivă era afectată.

## Bucla de monitorizare a vulnerabilităților

[[Grype]] de la Anchore este instrumentul standard pentru bucla de monitorizare. Primește ca intrare un SBOM CycloneDX, compară fiecare componentă cu mai multe fluxuri de vulnerabilități și produce un raport:

```bash
grype sbom:sbom.cdx.json
```

Opțiuni de format de ieșire:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

Ieșirea CycloneDX din Grype poate fi fuzionată înapoi în SBOM ca augmentare a vulnerabilităților, oferind un singur document care conține atât inventarul de componente, cât și starea curentă a vulnerabilităților.

Grype preia date din:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- Advisories de securitate Red Hat, Debian, Ubuntu, Alpine
- Bazele de date de advisories Amazon, Oracle, SUSE
- Fluxuri de advisories specifice limbajelor (PyPI, npm, Go, Maven, NuGet, Ruby)

## Executarea automată a buclei de monitorizare

Programați Grype să ruleze împotriva SBOM-urilor de producție la un interval care corespunde obligației de monitorizare conform Articolului 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

Eșecul codului de ieșire declanșează o notificare către echipă. Fluxul de notificare trebuie direcționat către persoana responsabilă de decizia de raportare conform Articolului 14.

## Praguri de severitate și declanșatorul Articolului 14

Nu fiecare vulnerabilitate necesită un raport conform Articolului 14. Obligația este declanșată de o [[actively exploited vulnerability|vulnerabilitate exploatată activ]], o vulnerabilitate pe care un actor malițios o utilizează în prezent împotriva unor sisteme reale fără permisiune.

Severitatea CVE (scorul CVSS) este un semnal, nu declanșatorul. O vulnerabilitate cu CVSS 9.8 care nu are cod de exploit public și nu este utilizată în atacuri nu declanșează Articolul 14. O vulnerabilitate cu CVSS 6.5 care se află în catalogul Known Exploited Vulnerabilities (KEV) al CISA și este utilizată activ în campanii de ransomware declanșează.

Procesul de monitorizare trebuie să:

1. **Captureze toate severitățile peste un prag**: Critical și High cel puțin
2. **Verifice KEV**: catalogul CISA KEV listează vulnerabilitățile exploatate în prezent. Grype marchează intrările KEV. CISA publică KEV ca flux JSON la `kev.cisa.gov/api/v1/catalog`.
3. **Evalueze aplicabilitatea**: componenta vulnerabilă este de fapt accesibilă în produsul dumneavoastră? Calea de cod vulnerabilă este executată? Documentați această evaluare.
4. **Escaladeze dacă este exploatată activ**: dacă o componentă din SBOM are un CVE care se află în catalogul KEV și componenta este accesibilă în produsul dumneavoastră, escaladați imediat pentru decizia de raportare în termen de 24 de ore conform Articolului 14.
5. **Documenteze decizia**: indiferent dacă raportați sau concluzionați că nu este afectat, documentați decizia și raționamentul. Utilizați o declarație [[VEX]] pentru a captura deciziile „not affected” într-o formă lizibilă automat.

## Utilizarea Dependency-Track pentru monitorizare continuă

Pentru organizațiile care gestionează mai multe produse, OWASP Dependency-Track oferă un tablou de bord centralizat. Încărcați SBOM-uri în Dependency-Track, acesta monitorizează continuu fluxurile de vulnerabilități și vă alertează atunci când un nou CVE afectează o componentă din orice SBOM încărcat.

Dependency-Track se integrează cu:
- JIRA (creează tichete pentru constatări critice noi)
- Slack și Teams (trimite alerte)
- REST API (interoghează programatic starea vulnerabilităților)

Pentru un producător cu cinci sau mai multe produse vizate de CRA, Dependency-Track reduce sarcina operațională a buclei de monitorizare conform Articolului 14 de la un proces manual zilnic la un sistem automat de alerte.

## Concluzii cheie

1. SBOM-urile îmbătrânesc atunci când componentele se modifică și atunci când se publică CVE-uri noi. Regenerați automat la momentul construirii, un SBOM pe artefact de lansare.
2. [[Grype]] scanează un SBOM împotriva mai multor fluxuri de vulnerabilități și raportează corespondențele. Executați-l zilnic sau la fiecare implementare.
3. Declanșatorul Articolului 14 este o vulnerabilitate exploatată activ, nu doar scorul CVSS. Verificați catalogul CISA KEV pentru a identifica care CVE-uri sunt utilizate în prezent în atacuri.
4. Documentați fiecare evaluare: indiferent dacă raportați sau concluzionați că nu este afectat. Utilizați declarații [[VEX]] pentru documentarea „not affected” lizibilă automat.
5. Pentru portofolii cu mai multe produse, OWASP Dependency-Track oferă monitorizare continuă centralizată care transformă bucla zilnică de scanare într-un sistem automat de alerte.
