# Lecția 3.1: Construirea SBOM-ului: Instrumente și Integrare în Pipeline

A ști ce trebuie să conțină un SBOM este un aspect. Generarea lui fiabilă, ca parte a procesului de construire, pentru fiecare versiune, este alt aspect. Această lecție prezintă instrumentele care generează SBOM-uri și modul de integrare a generării SBOM-urilor într-un pipeline CI/CD, astfel încât rezultatul să fie întotdeauna actual.

## Cele două categorii de generare a SBOM-urilor

### Analiză la momentul sursei

Instrumentele de analiză la momentul sursei citesc fișierele manifest ale dependențelor din cod, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, și produc un SBOM pe baza dependențelor declarate. Aceste instrumente înțeleg fișierele de blocare ale managerilor de pachete și pot genera grafuri complete de dependențe tranzitive din ele.

**cdxgen** (CycloneDX Generator) este instrumentul de analiză la momentul sursei cel mai capabil. Acesta acceptă peste 30 de ecosisteme de limbaje: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP și altele. Citește fișierul de blocare pentru ecosistem și generează CycloneDX JSON.

```bash
# Proiect Node.js
cdxgen -t npm -o sbom.cdx.json .

# Proiect Python
cdxgen -t python -o sbom.cdx.json .

# Proiect Java Maven
cdxgen -t maven -o sbom.cdx.json .
```

Analiza la momentul sursei este precisă pentru dependențele aplicației, dar omite pachetele de sistem de operare și bibliotecile de sistem care nu se regăsesc în manifestele specifice limbajului.

### Scanare de imagine/sistem de fișiere

Scanerele de imagine examinează un artefact construit, o imagine de container, un director de sistem de fișiere, un binar compilat și identifică pachetele din bazele de date de pachete prezente. [[Syft]] de la Anchore este instrumentul principal pentru acest scop.

```bash
# Scanare imagine de container
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scanare director
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scanare arhivă tar
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifică pachetele prin citirea:
- bazelor de date de pachete de sistem de operare (dpkg pentru Debian/Ubuntu, rpm pentru RHEL/Fedora, apk pentru Alpine)
- manifestelor și fișierelor de blocare specifice limbajului incluse în imagine
- semnăturilor binare pentru pachetele care au fost compilate și instalate fără un manager de pachete

Avantajul scanării de imagine: se vede exact ce conține artefactul care va fi implementat. Dezavantajul: dacă un pachet a fost instalat fără un manager de pachete (situație frecventă în sistemele de construire vechi), Syft poate să îl omită.

## Cea mai bună practică: combinarea ambelor abordări

Executați cdxgen pe codul sursă pentru dependențele aplicației și Syft pe imaginea de container pentru pachetele de sistem de operare și runtime. Combinați cele două SBOM-uri cu ajutorul unui instrument de fuzionare. CycloneDX oferă o operațiune de fuzionare care unește listele de componente și elimină duplicatele.

SBOM-ul fuzionat acoperă:
- dependențele aplicației (de la cdxgen, graf tranzitiv complet)
- pachetele de sistem de operare (de la Syft)
- dependențele de runtime (runtime Node.js, interpretor Python, JVM)

Aceasta este imaginea completă cerută de CRA și de monitorizarea din Article 14.

## Integrarea generării SBOM-urilor în CI/CD

SBOM-ul trebuie generat automat ca parte a pipeline-ului de construire. Generarea manuală a SBOM-urilor creează riscul unui SBOM învechit sau lipsă atunci când este necesar pentru un audit sau pentru răspuns la incident.

### Exemplu GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Atașați SBOM-ul la artefactul de versiune. Fiecare versiune primește un SBOM. Numele de fișier marcat cu SHA creează pista de audit care leagă fiecare SBOM de build-ul corespunzător.

### Exemplu GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` asigură că GitLab nu șterge artefactul. Combinat cu etichetarea versiunilor, acest lucru oferă istoric SBOM pentru fiecare versiune, pe o perioadă cât de lungă este necesar.

## Validarea SBOM-ului

Înainte de stocare sau transmitere, validați SBOM-ul:

```bash
# Validare schemă CycloneDX
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

CLI-ul CycloneDX este disponibil de la `@cyclonedx/cyclonedx-cli`. Validarea schemei detectează câmpuri obligatorii lipsă, tipuri incorecte și PURL-uri incorecte înainte ca SBOM-ul să intre în registrele de documentație.

## Semnarea SBOM-ului

Un SBOM semnat constituie o probă mai puternică într-un audit decât unul nesemnat. Dacă puteți demonstra că SBOM-ul a fost generat la un moment precis și nu a fost modificat de atunci, dețineți o lanț de custodie mai solid.

Cosign (din proiectul Sigstore) poate semna și verifica fișiere SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Fișierul de semnătură demonstrează că SBOM-ul a fost produs de sistemul de construire și nu a fost alterat. Stocați semnătura împreună cu SBOM-ul.

## Concluzii cheie

1. Instrumentele de analiză la momentul sursei (cdxgen) citesc manifestele de pachete și produc grafuri complete de dependențe tranzitive. Scanerele de imagine (Syft) examinează artefactele construite și identifică pachetele de sistem de operare și runtime.
2. Cea mai bună practică combină ambele abordări: cdxgen pentru dependențele aplicației, Syft pentru pachetele de sistem de operare și runtime, fuzionate într-un singur SBOM.
3. Generarea SBOM-urilor trebuie integrată în CI/CD. Generarea manuală creează SBOM-uri învechite sau lipsă sub presiune.
4. Atașați SBOM-ul la fiecare artefact de versiune, marcat cu SHA-ul build-ului sau cu versiunea. Aceasta creează pista de audit cerută de regula de păstrare pe 10 ani.
5. Validați cu CLI-ul CycloneDX înainte de stocare. Semnați cu Cosign pentru a crea un lanț de custodie.
