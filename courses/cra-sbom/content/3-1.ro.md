# Lecția 3.1: Construirea SBOM: instrumente și integrarea în pipeline

Să știi ce ar trebui să conțină un SBOM este un lucru. Să îl generezi în mod fiabil, ca parte a procesului de build, pentru fiecare lansare, este altceva. Această lecție acoperă instrumentele care generează SBOM și modul în care integrezi generarea SBOM într-un pipeline CI/CD, astfel încât rezultatul să fie mereu actual.

## Cele două categorii de generare a SBOM

### Analiza la nivel de sursă

Instrumentele la nivel de sursă citesc fișierele manifest cu dependențe ale codului tău, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, și produc un SBOM din dependențele declarate. Aceste instrumente înțeleg fișierele de blocare ale managerilor de pachete și pot produce din ele grafuri complete de dependențe tranzitive.

**cdxgen** (CycloneDX Generator) este cel mai capabil instrument la nivel de sursă. Suportă peste 30 de ecosisteme de limbaje: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP și altele. Citește fișierul de blocare al ecosistemului și produce CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Analiza la nivel de sursă este precisă pentru dependențele aplicației, dar omite pachetele sistemului de operare și bibliotecile de sistem care nu se află în manifestele specifice limbajului.

### Scanarea imaginii sau a sistemului de fișiere

Scanerele de imagini examinează un artefact construit, o imagine de container, un director de sistem de fișiere, un binar compilat, și identifică pachetele din bazele de date de pachete prezente. [[Syft|Syft]] de la Anchore este instrumentul principal pentru acest lucru.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifică pachetele citind:
- Bazele de date de pachete ale sistemului de operare (dpkg pentru Debian/Ubuntu, rpm pentru RHEL/Fedora, apk pentru Alpine)
- Manifestele și fișierele de blocare specifice limbajului, încorporate în imagine
- Semnăturile binare pentru pachetele care au fost compilate și instalate fără un manager de pachete

Avantajul scanării imaginii: vezi exact ce se află în artefactul care va fi implementat. Dezavantajul: dacă un pachet a fost instalat fără un manager de pachete (lucru frecvent în sistemele de build mai vechi), Syft îl poate rata.

## Bună practică: combină ambele abordări

Rulează cdxgen pe codul sursă pentru dependențele aplicației și Syft pe imaginea de container pentru pachetele de sistem de operare și de runtime. Îmbină cele două SBOM-uri folosind un instrument de îmbinare. CycloneDX oferă o operație de îmbinare care combină listele de componente și elimină duplicatele.

SBOM-ul îmbinat acoperă:
- Dependențele aplicației (de la cdxgen, graful tranzitiv complet)
- Pachetele sistemului de operare (de la Syft)
- Dependențele de runtime (runtime-ul Node.js, interpretorul Python, JVM)

Aceasta este imaginea completă pe care o cer CRA și monitorizarea din Articolul 14.

## Integrarea generării SBOM în CI/CD

SBOM-ul ar trebui generat automat ca parte a pipeline-ului de build. Generarea manuală a SBOM creează riscul unui SBOM învechit sau lipsă atunci când ai nevoie de el pentru un audit sau pentru răspunsul la un incident.

### Exemplu GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Atașează SBOM-ul la artefactul de lansare. Fiecare lansare primește un SBOM. Numele de fișier marcat cu SHA creează pista de audit care leagă fiecare SBOM de build-ul corespunzător.

### Exemplu GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` asigură că GitLab nu șterge artefactul. Combinat cu marcarea lansărilor, acest lucru îți oferă un istoric SBOM pentru fiecare lansare, cât de departe în timp ai nevoie.

## Validarea SBOM

Înainte de a stoca sau de a trimite un SBOM, validează-l:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

CycloneDX CLI este disponibil din `@cyclonedx/cyclonedx-cli`. Validarea schemei detectează câmpurile obligatorii lipsă, tipurile incorecte și PURL-urile malformate înainte ca SBOM-ul să intre în înregistrările documentației tale.

## Semnarea SBOM

Un SBOM semnat este o dovadă mai puternică într-un audit decât unul nesemnat. Dacă poți arăta că SBOM-ul a fost generat la un anumit moment în timp și nu a fost modificat de atunci, ai un lanț de custodie mai solid.

Cosign (din proiectul Sigstore) poate semna și verifica fișierele SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Fișierul de semnătură dovedește că SBOM-ul a fost produs de sistemul tău de build și nu a fost modificat. Stochează semnătura alături de SBOM.

## Concluzii cheie

1. Instrumentele la nivel de sursă (cdxgen) citesc manifestele de pachete și produc grafuri complete de dependențe tranzitive. Scanerele de imagini (Syft) examinează artefactele construite și găsesc pachetele de sistem de operare și de runtime.
2. Buna practică le combină pe ambele: cdxgen pentru dependențele aplicației, Syft pentru pachetele de sistem de operare și de runtime, îmbinate într-un singur SBOM.
3. Generarea SBOM trebuie integrată în CI/CD. Generarea manuală produce SBOM-uri învechite sau lipsă sub presiune.
4. Atașează SBOM-ul la fiecare artefact de lansare, marcat cu SHA-ul build-ului sau cu versiunea. Acest lucru creează pista de audit pe care o cere regula de păstrare timp de 10 ani.
5. Validează cu CycloneDX CLI înainte de stocare. Semnează cu Cosign pentru a crea un lanț de custodie.
