# Lekcja 2.2: SPDX i wybór formatu

[[SPDX]] jest drugim formatem, który spełnia wymaganie CRA Załącznik I Część II punkt (1) dotyczące „powszechnie stosowanego i czytelnego maszynowo” SBOM. Lekcja omawia, czym jest SPDX, czym różni się od CycloneDX oraz jak wybrać format.

## Czym jest SPDX

Software Package Data Exchange (SPDX) powstał w Linux Foundation w 2010 r. W 2021 r. stał się normą ISO: ISO/IEC 5962:2021. Dla normy ISO aktualna jest wersja 2.3. Wersja 3.0 ukazała się w 2024 r. i wprowadziła nowy model danych oraz system profili.

SPDX zaprojektowano, aby rozwiązać problem zgodności licencji open source. Gdy produkt zawiera komponenty open source, powstają obowiązki prawne: podanie autorstwa, dołączenie tekstu licencji, ujawnienie kodu źródłowego w przypadku licencji copyleft. SPDX zapewnia maszynowo czytelny sposób wyrażenia, jakie licencje dotyczą poszczególnych komponentów i jakie obowiązki przyjęto.

Z czasem format stał się standardem SBOM i obecnie obejmuje także pola inwentarza komponentów potrzebne do zarządzania podatnościami. Pierwotny cel projektowy (zgodność licencji) pozostaje jednak widoczny w modelu danych.

## Struktura dokumentu SPDX

Dokument SPDX 2.3 w formacie JSON zawiera:

- **Informacje o utworzeniu dokumentu**: odpowiednik metadanych CycloneDX: twórca, znacznik czasu utworzenia, przestrzeń nazw dokumentu, wersja SPDX
- **Pakiety**: inwentarz komponentów. Każdy pakiet zawiera: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` lub `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (tu umieszczany jest [[PURL]])
- **Relacje**: sposób powiązania pakietów. Relacja `DESCRIBES` wskazuje produkt najwyższego poziomu. Relacje `DEPENDS_ON` i `DEPENDENCY_OF` odwzorowują graf zależności.
- **Pliki** (opcjonalnie): inwentarz na poziomie plików z wartościami skrótu, gdy wymagana jest granularność na poziomie plików
- **Fragmenty** (opcjonalnie): poziom fragmentów kodu, dla kodu skopiowanego, który nie pochodzi z pakietu

Pole PURL w SPDX 2.3 znajduje się w tablicy `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Rozwiązanie to jest bardziej rozbudowane niż pierwszorzędne pole `purl` w CycloneDX, pozostaje jednak czytelne maszynowo i możliwe do przetworzenia przez skanery podatności.

## Gdzie SPDX ma przewagę

**Normalizacja ISO.** ISO/IEC 5962:2021 oznacza, że SPDX jest jedynym formatem SBOM będącym normą międzynarodową. Dla organizacji wymagających w zamówieniach lub umowach z dostawcami formatów certyfikowanych ISO ma to znaczenie.

**Przepływy pracy związane ze zgodnością licencji.** Gdy głównym zastosowaniem SBOM jest zgodność licencji open source, śledzenie obowiązków dotyczących autorstwa, identyfikacja kodu zanieczyszczonego GPL czy generowanie informacji o komponentach stron trzecich, bogaty model licencji SPDX jest lepiej dopasowany. SPDX obsługuje identyfikatory licencji SPDX, `LicenseInfoInFile` do wykrywania licencji na poziomie plików oraz `licenseComments` w sytuacjach złożonych.

**Integracja z grafem zależności GitHub.** Graf zależności GitHub natywnie eksportuje SPDX 2.3 JSON. Gdy repozytorium znajduje się na GitHub, adres `github.com/your-org/your-repo/dependency-graph/sbom` dostarcza SBOM w formacie SPDX bez uruchamiania narzędzi lokalnych. Dla wielu zespołów jest to najprostszy punkt wyjścia.

**Wiele formatów wyjściowych.** SPDX obsługuje JSON, YAML, RDF/XML oraz format tekstowy tag-value. Format tag-value jest czytelny dla człowieka (w przeciwieństwie do JSON lub XML), co bywa przydatne podczas przeglądu.

## Gdzie CycloneDX ma przewagę

**Zarządzanie podatnościami.** CycloneDX posiada natywne wsparcie dla [[VEX]]. SPDX 3.0 dodał profil bezpieczeństwa z możliwościami VEX, lecz wsparcie ekosystemu dla VEX w SPDX nadal dojrzewa. W przepływach pracy związanych ze zgodnością z Artykuł 14 dojrzałe i lepiej obsługiwane przez narzędzia jest VEX CycloneDX.

**Dependency-Track.** Wiodąca otwartoźródłowa platforma zarządzania SBOM, OWASP Dependency-Track, powstała z myślą o CycloneDX. Akceptuje dane SPDX, lecz jej funkcje natywne (dopasowywanie podatności, zarządzanie VEX, ocena polityk) są najpełniejsze dla CycloneDX.

**Dojrzałość narzędzi.** Większość narzędzi SBOM, Syft, cdxgen, trivy, grype, traktuje CycloneDX jako format wyjściowy podstawowy, a SPDX jako drugorzędny.

## Oba formaty kwalifikują się do zgodności z CRA

CRA wymaga formatu „powszechnie stosowanego i czytelnego maszynowo”. Zarówno CycloneDX, jak i SPDX są wykorzystywane przez setki organizacji. Oba są czytelne maszynowo. Oba mogą przenosić pola inwentarza komponentów wymagane przez Załącznik I Część II punkt (1). Wybór SPDX zamiast CycloneDX lub odwrotnie nie spowoduje niepowodzenia audytu CRA.

Dokumenty Komisji Europejskiej oraz dokument ENISA dotyczący dobrych praktyk SBOM odwołują się do obu formatów. Brak oficjalnych wytycznych UE, które wskazywałyby jeden format jako preferowany.

## Jak wybrać

Należy skorzystać z poniższych ram decyzyjnych:

| Pytanie | CycloneDX | SPDX |
|---|---|---|
| Głównym zastosowaniem jest zarządzanie podatnościami i zgodność z Artykuł 14 | ✓ | - |
| Głównym zastosowaniem jest zgodność licencji open source | - | ✓ |
| Używane jest Dependency-Track | ✓ | - |
| Zamówienia wymagają formatów certyfikowanych ISO | - | ✓ |
| Punktem wyjścia jest eksport grafu zależności GitHub | - | ✓ |
| Zespół korzysta z Syft lub cdxgen | ✓ | - |
| Potrzebne jest dojrzałe narzędzie VEX | ✓ | - |

Gdy głównym zagadnieniem jest zarządzanie podatnościami, należy wybrać CycloneDX. Gdy istnieje już proces SPDX dotyczący zgodności licencji, rozsądne jest rozszerzenie go o zarządzanie podatnościami. Należy jednak pamiętać, że narzędzia VEX są mniej dojrzałe.

Wiele organizacji wytwarza oba formaty: CycloneDX na potrzeby operacji bezpieczeństwa, SPDX na potrzeby działów prawnych i zamówień. Narzędzia to umożliwiają. Syft może wygenerować oba formaty z tego samego skanu.

## Kluczowe wnioski

1. SPDX (ISO/IEC 5962:2021) jest formatem SBOM będącym normą ISO. Dla normy ISO aktualna jest wersja 2.3, a dla nowego modelu danych wersja 3.0. Format zaprojektowano z myślą o zgodności licencji open source.
2. Zarówno [[CycloneDX]], jak i SPDX kwalifikują się jako formaty „powszechnie stosowane i czytelne maszynowo” zgodnie z CRA Załącznik I Część II punkt (1). Żaden z nich nie jest oficjalnie preferowany w wytycznych UE.
3. Zalety SPDX: status normy ISO, bogatszy model licencji, natywny eksport z grafu zależności GitHub, wiele formatów wyjściowych.
4. Zalety CycloneDX: natywne wsparcie dla [[VEX]], integracja z Dependency-Track, bardziej dojrzały ekosystem narzędzi do zarządzania podatnościami.
5. Gdy głównym czynnikiem jest raportowanie podatności zgodnie z CRA Artykuł 14, bardziej naturalnym wyborem jest CycloneDX. Wytwarzanie obu formatów z jednego skanu Syft stanowi prawidłową strategię.
