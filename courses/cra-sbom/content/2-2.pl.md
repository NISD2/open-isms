# Lekcja 2.2: SPDX i wybór formatu

[[SPDX]] jest drugim formatem, który spełnia wymóg Artykułu 13(5) CRA dotyczący „powszechnie używanego, nadającego się do odczytu maszynowego" SBOM-u. Ta lekcja obejmuje to, czym jest SPDX, w czym różni się od CycloneDX oraz jak zdecydować, którego formatu użyć.

## Czym jest SPDX

Software Package Data Exchange (SPDX) został stworzony w Linux Foundation w 2010 roku. W 2021 roku stał się standardem ISO: ISO/IEC 5962:2021. Wersja 2.3 jest bieżąca dla standardu ISO. Wersja 3.0 została wydana w 2024 roku z nowym modelem danych i systemem profili.

SPDX został zaprojektowany, aby rozwiązać problem zgodności licencji open source. Gdy dostarczasz produkt zawierający komponenty open source, masz obowiązki prawne: atrybucję, dołączenie tekstu licencji, ujawnienie kodu źródłowego dla licencji typu copyleft. SPDX daje Ci nadający się do odczytu maszynowego sposób wyrażenia, jakie licencje mają zastosowanie do których komponentów oraz jakie obowiązki przyjąłeś.

Z czasem stał się standardem SBOM i obejmuje teraz również pola wykazu komponentów potrzebne do zarządzania podatnościami. Ale jego pierwotny zamysł projektowy (zgodność licencji) jest nadal widoczny w modelu danych.

## Struktura dokumentu SPDX

Dokument SPDX 2.3 JSON ma:

- **Informacje o utworzeniu dokumentu**: odpowiednik metadanych CycloneDX: twórca, znacznik czasu utworzenia, przestrzeń nazw dokumentu, wersja SPDX
- **Packages**: wykaz komponentów. Każdy pakiet ma: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` lub `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (gdzie trafia [[PURL]])
- **Relationships**: jak pakiety odnoszą się do siebie nawzajem. Relacja `DESCRIBES` identyfikuje produkt najwyższego poziomu. `DEPENDS_ON` i `DEPENDENCY_OF` odwzorowują graf zależności.
- **Files** (opcjonalnie): wykaz na poziomie plików ze skrótami, jeśli potrzebujesz granularności na poziomie plików
- **Snippets** (opcjonalnie): poziom fragmentów kodu, dla skopiowanego kodu, który nie pochodzi z pakietu

Pole PURL w SPDX 2.3 znajduje się wewnątrz tablicy `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Jest to bardziej rozwlekłe niż pierwszorzędne pole `purl` w CycloneDX, ale nadal nadaje się do odczytu maszynowego i może być przetwarzane przez skanery podatności.

## Gdzie SPDX ma przewagę

**Standaryzacja ISO.** ISO/IEC 5962:2021 oznacza, że SPDX jest jedynym formatem SBOM, który jest standardem międzynarodowym. Dla organizacji wymagających formatów certyfikowanych przez ISO w swoich zamówieniach lub umowach z dostawcami ma to znaczenie.

**Procesy zgodności licencji.** Jeśli Twoim głównym zastosowaniem SBOM-u jest zgodność licencji open source, śledzenie obowiązków atrybucji, identyfikowanie kodu skażonego GPL, generowanie informacji o stronach trzecich, bogaty model licencji SPDX jest lepiej dopasowany. SPDX obsługuje identyfikatory licencji SPDX, `LicenseInfoInFile` do wykrywania licencji na poziomie plików oraz `licenseComments` dla złożonych sytuacji.

**Integracja z grafem zależności GitHub.** Graf zależności GitHub natywnie eksportuje SPDX 2.3 JSON. Jeśli Twoje repozytorium jest na GitHub, `github.com/your-org/your-repo/dependency-graph/sbom` daje Ci SBOM SPDX bez uruchamiania jakichkolwiek lokalnych narzędzi. Dla wielu zespołów to najłatwiejszy punkt startowy.

**Wiele formatów wyjściowych.** SPDX obsługuje JSON, YAML, RDF/XML oraz tekstowy format tag-value. Format tag-value jest czytelny dla człowieka (w przeciwieństwie do JSON czy XML), co może być przydatne podczas przeglądu.

## Gdzie CycloneDX ma przewagę

**Zarządzanie podatnościami.** CycloneDX ma natywne wsparcie [[VEX]]. SPDX 3.0 dodał profil bezpieczeństwa z możliwościami VEX, ale wsparcie ekosystemu dla SPDX VEX nadal dojrzewa. Dla procesów zgodności z Artykułem 14 CycloneDX VEX jest bardziej dojrzały i lepiej wspierany przez narzędzia.

**Dependency-Track.** Wiodąca platforma open source do zarządzania SBOM-ami, OWASP Dependency-Track, została zbudowana dla CycloneDX. Przyjmuje dane wejściowe SPDX, ale jej natywne funkcje (dopasowywanie podatności, zarządzanie VEX, ocena polityk) są najpełniejsze dla CycloneDX.

**Dojrzałość narzędzi.** Większość narzędzi do SBOM-ów, Syft, cdxgen, trivy, grype, traktuje CycloneDX jako swój podstawowy format wyjściowy, a SPDX jako drugorzędny.

## Oba formaty kwalifikują się do zgodności z CRA

CRA wymaga „powszechnie używanego, nadającego się do odczytu maszynowego". Zarówno CycloneDX, jak i SPDX są używane przez setki organizacji. Oba nadają się do odczytu maszynowego. Oba mogą zawierać pola wykazu komponentów wymagane przez Artykuł 13(5). Nie oblejesz audytu CRA dlatego, że wybrałeś SPDX zamiast CycloneDX lub odwrotnie.

Wytyczne Komisji Europejskiej oraz dokument o dobrych praktykach SBOM ENISA odwołują się do obu formatów. Żadne oficjalne wytyczne UE nie wskazały jednego formatu jako preferowanego nad drugim.

## Jak wybrać

Skorzystaj z tych ram decyzyjnych:

| Pytanie | CycloneDX | SPDX |
|---|---|---|
| Głównym zastosowaniem jest zarządzanie podatnościami i zgodność z Artykułem 14 | ✓ | - |
| Głównym zastosowaniem jest zgodność licencji open source | - | ✓ |
| Używasz Dependency-Track | ✓ | - |
| Twoje zamówienia wymagają formatów certyfikowanych przez ISO | - | ✓ |
| Zaczynasz od eksportu z grafu zależności GitHub | - | ✓ |
| Twój zespół używa Syft lub cdxgen | ✓ | - |
| Potrzebujesz dojrzałych narzędzi VEX | ✓ | - |

Jeśli zarządzanie podatnościami jest Twoim głównym celem, wybierz CycloneDX. Jeśli masz już proces SPDX do zgodności licencji, rozszerzenie go o zarządzanie podatnościami jest rozsądne. Pamiętaj tylko, że narzędzia VEX są mniej dojrzałe.

Wiele organizacji generuje oba: CycloneDX do operacji bezpieczeństwa, SPDX do działu prawnego i zamówień. Narzędzia to wspierają. Syft może wygenerować oba z tego samego skanowania.

## Kluczowe wnioski

1. SPDX (ISO/IEC 5962:2021) jest standardem ISO formatu SBOM. Bieżąca wersja to 2.3 dla standardu ISO, 3.0 dla nowego modelu danych. Został zaprojektowany do zgodności licencji open source.
2. Zarówno [[CycloneDX]], jak i SPDX kwalifikują się jako „powszechnie używane, nadające się do odczytu maszynowego" formaty na podstawie Artykułu 13(5) CRA. Żaden nie jest oficjalnie preferowany przez wytyczne UE.
3. Zalety SPDX: status ISO, bogatszy model licencji, natywny eksport z grafu zależności GitHub, wiele formatów wyjściowych.
4. Zalety CycloneDX: natywne wsparcie [[VEX]], integracja z Dependency-Track, bardziej dojrzały ekosystem narzędzi do podatności.
5. Jeśli zgłaszanie podatności z Artykułu 14 CRA jest Twoim głównym motorem, CycloneDX jest bardziej naturalnym wyborem. Generowanie obu formatów z pojedynczego skanowania Syft jest prawidłową strategią.
