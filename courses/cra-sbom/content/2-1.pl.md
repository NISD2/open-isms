# Lekcja 2.1: CycloneDX: Format SBOM skupiony na bezpieczeństwie

CRA wymaga formatu „powszechnie stosowanego i czytelnego maszynowo”. Dwa formaty spełniają to wymaganie: [[CycloneDX]] i [[SPDX]]. Lekcja omawia CycloneDX: czym jest, co czyni go formatem skupionym na bezpieczeństwie oraz dlaczego dobrze wpisuje się w proces zgłaszania podatności określony w CRA Artykuł 14.

## Czym jest CycloneDX

CycloneDX to projekt OWASP. Open Web Application Security Project (OWASP) utrzymuje go jako standard przeznaczony do zastosowań w zakresie bezpieczeństwa. Aktualna wersja to 1.6. Format jest dostępny w JSON i XML.

CycloneDX zaprojektowano z myślą o procesach zarządzania podatnościami. Jego podstawowy model danych koncentruje się na pytaniu: „Mając listę komponentów, które z nich mają znane podatności i czy mogę na nie zareagować?”. Każda istotna funkcja formatu służy odpowiedzi na to pytanie.

## Struktura dokumentu CycloneDX SBOM

Dokument CycloneDX zawiera cztery główne sekcje:

### Metadata

Informacje o samym dokumencie SBOM oraz o opisywanym produkcie:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Znacznik czasu informuje audytora, kiedy wygenerowano SBOM. Pole narzędzia wskazuje, w jaki sposób to zrobiono. Blok komponentu identyfikuje obiekt, którego dotyczy SBOM.

### Components

Lista komponentów oprogramowania. Każdy komponent zawiera:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` lub `operating-system`
- `name`: kanoniczna nazwa pakietu
- `version`: dokładny ciąg wersji
- `supplier`: podmiot publikujący komponent
- `purl`: unikalny identyfikator [[PURL]]
- `hashes`: SHA-256 lub inny skrót pliku komponentu
- `licenses`: wyrażenia licencji SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX w wersji 1.4 i nowszych zawiera sekcję `dependencies`, która mapuje zależności między komponentami. Jest to reprezentacja grafu zależności w formie czytelnej dla maszyn. Dzięki niej narzędzie może odróżnić komponenty najwyższego poziomu od komponentów przechodnich bez ponownego uruchamiania narzędzia budującego.

### Vulnerabilities

CycloneDX umożliwia bezpośrednie osadzenie danych o podatnościach w dokumencie SBOM. Każdy wpis o podatności odwołuje się do [[CVE]] i wskazanego komponentu. Funkcja ta przydaje się do dokumentacji w danym momencie, lecz w praktyce jest stosowana rzadziej. Większość zespołów przechowuje SBOM i wyniki skanowania podatności jako odrębne artefakty.

## VEX: cecha wyróżniająca CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, to najbardziej charakterystyczna funkcja CycloneDX pod kątem zgodności z CRA. Oświadczenie VEX stanowi czytelną maszynowo deklarację dokumentującą relację między znaną podatnością a konkretnym produktem.

CycloneDX VEX obsługuje cztery wartości statusu:

- **not_affected**: komponent jest obecny, lecz podatność nie może być wykorzystana w tym produkcie
- **affected**: podatność może być wykorzystana i nie została jeszcze usunięta
- **fixed**: podatność była obecna i została usunięta
- **under_investigation**: ocena jest w toku

Każde oświadczenie `not_affected` wymaga uzasadnienia:

- `code_not_present`: podatliwy fragment kodu nie występuje w używanej wersji
- `code_not_reachable`: podatliwy kod istnieje, lecz nie jest osiągalny w danym kontekście wykonania
- `requires_configuration`: wykorzystanie wymaga konfiguracji, która nie jest stosowana w danym wdrożeniu
- `requires_environment`: wykorzystanie wymaga warunku środowiskowego, który nie występuje
- `protected_by_mitigating_control`: zastosowano kontrolę kompensacyjną
- `protected_at_perimeter`: zagrożony komponent nie jest osiągalny spoza środowiska

Oświadczenie VEX o statusie `not_affected` z uzasadnieniem `code_not_reachable`, opatrzone datą i podpisem, stanowi mocny dowód w audycie na podstawie Artykuł 14, że podatność została oceniona i uznano, iż nie uruchamia obowiązku zgłoszenia.

## Dlaczego CycloneDX jest preferowany dla zgodności z CRA

Obowiązek wynikający z CRA Artykuł 14 obejmuje:

1. Monitorowanie aktywnie wykorzystywanych podatności w komponentach produktu
2. W przypadku aktywnego wykorzystywania: powiadomienie CSIRT wyznaczonego jako koordynator oraz ENISA za pośrednictwem jednolitej platformy zgłoszeniowej – wczesne ostrzeżenie w ciągu 24 godzin, pełne powiadomienie w ciągu 72 godzin oraz sprawozdanie końcowe w ciągu 14 dni od udostępnienia poprawki

Projekt CycloneDX jest z nim zgodny:

- Identyfikacja komponentów na podstawie PURL mapuje się bezpośrednio na wyszukiwania w bazach podatności
- Oświadczenia VEX zapewniają czytelny maszynowo sposób dokumentowania decyzji monitoringowych
- Narzędzia takie jak [[Grype]] natywnie konsumują SBOM-y CycloneDX i generują wyniki skanowania podatności w formacie CycloneDX
- Numer seryjny CycloneDX BOM (`serialNumber`) umożliwia śledzenie wersji SBOM w czasie

SPDX również obsługuje zarządzanie podatnościami, lecz pierwotnie zaprojektowano go pod kątem zgodności licencyjnej. CycloneDX powstał z myślą o operacjach bezpieczeństwa. Gdy głównym zastosowaniem jest zgodność z Artykuł 14, CycloneDX stanowi bardziej naturalny wybór.

## Generowanie SBOM w formacie CycloneDX

[[Syft]] firmy Anchore domyślnie generuje CycloneDX 1.6 JSON:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` stanowi alternatywę, szczególnie przy kompilacjach specyficznych dla języka, w których skanowanie systemu plików przez Syft może pominąć zależności aplikacji:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Oba narzędzia tworzą poprawny wynik CycloneDX 1.6, który przechodzi walidację schematu i jest akceptowany przez narzędzia downstream, w tym Grype, Dependency-Track oraz większość platform zarządzania podatnościami.

## Kluczowe wnioski

1. CycloneDX to standard OWASP dostępny w JSON i XML. Aktualna wersja to 1.6.
2. Cztery główne sekcje to: metadata (informacje o SBOM), components (inwentarz), dependencies (graf) oraz opcjonalnie vulnerabilities.
3. Oświadczenia VEX umożliwiają formalne udokumentowanie, czy znane [[CVE]] jest możliwe do wykorzystania w kontekście konkretnego produktu. Stanowi to kluczowy dowód w audycie na podstawie Artykuł 14.
4. CycloneDX jest preferowanym formatem dla zgodności z CRA, ponieważ zaprojektowano go pod kątem procesów zarządzania podatnościami, a nie zgodności licencyjnej.
5. Zarówno Syft, jak i cdxgen generują wynik CycloneDX 1.6. Większość narzędzi SBOM jako format wyjściowy wybiera przede wszystkim CycloneDX.
