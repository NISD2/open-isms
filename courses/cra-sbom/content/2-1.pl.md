# Lekcja 2.1: CycloneDX: format SBOM skupiony na bezpieczeństwie

CRA wymaga „powszechnie używanego, nadającego się do odczytu maszynowego" formatu. Kwalifikują się dwa formaty: [[CycloneDX]] i [[SPDX]]. Ta lekcja obejmuje CycloneDX: czym jest, co sprawia, że jest skupiony na bezpieczeństwie, oraz dlaczego dobrze odwzorowuje proces zgłaszania podatności z Artykułu 14 CRA.

## Czym jest CycloneDX

CycloneDX jest projektem OWASP. Open Web Application Security Project (OWASP) utrzymuje go jako standard do zastosowań związanych z bezpieczeństwem. Bieżąca wersja to 1.6. Jest dostępny w formatach JSON i XML.

CycloneDX został zaprojektowany do obsługi procesów zarządzania podatnościami. Jego podstawowy model danych jest zbudowany wokół pytania: „Mając tę listę komponentów, które z nich mają znane podatności i czy mogę na nie zareagować?" Każda istotna funkcja w tym formacie istnieje po to, aby odpowiedzieć na to pytanie.

## Struktura SBOM-u CycloneDX

Dokument CycloneDX ma cztery główne sekcje:

### Metadata

Informacje o samym dokumencie SBOM oraz o produkcie, który opisuje:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Znacznik czasu mówi audytorowi, kiedy SBOM został wygenerowany. Narzędzie mówi mu, jak. Blok komponentu identyfikuje, co opisuje SBOM.

### Components

Lista komponentów oprogramowania. Każdy komponent ma:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` lub `operating-system`
- `name`: kanoniczna nazwa pakietu
- `version`: dokładny ciąg wersji
- `supplier`: kto go publikuje
- `purl`: unikalny identyfikator [[PURL]]
- `hashes`: SHA-256 lub inny skrót pliku komponentu
- `licenses`: wyrażenia licencji SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX 1.4+ zawiera sekcję `dependencies`, która odwzorowuje, który komponent zależy od którego. Jest to nadająca się do odczytu maszynowego reprezentacja grafu zależności. To ona pozwala narzędziu odróżnić komponenty najwyższego poziomu od tranzytywnych bez ponownego uruchamiania narzędzia budowy.

### Vulnerabilities

CycloneDX może osadzać dane o podatnościach bezpośrednio w SBOM-ie. Każdy wpis podatności odwołuje się do [[CVE]] oraz komponentu, którego dotyczy. Jest to użyteczne do dokumentacji w określonym momencie, ale rzadziej spotykane w praktyce. Większość zespołów przechowuje SBOM i wynik skanowania podatności jako oddzielne artefakty.

## VEX: funkcja, która wyróżnia CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, jest najbardziej wyróżniającą funkcją CycloneDX dla zgodności z CRA. Oświadczenie VEX to nadająca się do odczytu maszynowego deklaracja, która dokumentuje związek między znaną podatnością a Twoim konkretnym produktem.

CycloneDX VEX obsługuje cztery wartości statusu:

- **not_affected**: komponent jest obecny, ale podatność nie może być wykorzystana w tym produkcie
- **affected**: podatność może być wykorzystana i jeszcze jej nie złagodziłeś
- **fixed**: podatność była obecna i ją naprawiłeś
- **under_investigation**: nadal oceniasz

Każde oświadczenie `not_affected` wymaga uzasadnienia:

- `code_not_present`: podatna ścieżka kodu nie istnieje w używanej przez Ciebie wersji
- `code_not_reachable`: podatny kod istnieje, ale nie można go osiągnąć w Twoim kontekście wykonania
- `requires_configuration`: wykorzystanie wymaga konfiguracji, której Twoje wdrożenie nie używa
- `requires_environment`: wykorzystanie wymaga warunku środowiskowego, który nie ma zastosowania
- `protected_by_mitigating_control`: masz wdrożony środek kompensujący
- `protected_at_perimeter`: dotknięty komponent nie jest osiągalny spoza Twojego środowiska

Oświadczenie VEX `not_affected` z uzasadnieniem `code_not_reachable`, opatrzone datą i podpisane, jest mocnym dowodem w audycie z Artykułu 14, że oceniłeś podatność i stwierdziłeś, że nie uruchomiła ona obowiązku zgłaszania.

## Dlaczego CycloneDX jest preferowany dla zgodności z CRA

Obowiązek z Artykułu 14 CRA to:

1. Monitorowanie aktywnie wykorzystywanych podatności w komponentach Twojego produktu
2. Zgłoszenie do ENISA za pośrednictwem jednej platformy zgłoszeniowej (Single Reporting Platform) w ciągu 24 godzin, jeśli któraś jest aktywnie wykorzystywana

Konstrukcja CycloneDX jest zgodna z tym:

- Identyfikacja komponentów oparta na PURL odwzorowuje się bezpośrednio na wyszukiwania w bazach danych podatności
- Oświadczenia VEX dają Ci nadający się do odczytu maszynowego sposób dokumentowania decyzji monitorowania
- Narzędzia takie jak [[Grype]] natywnie przyjmują SBOM-y CycloneDX i generują wyniki skanowania podatności w CycloneDX
- Numer seryjny BOM-u CycloneDX (`serialNumber`) pozwala śledzić wersje SBOM-u w czasie

SPDX może zarządzać podatnościami, ale został zaprojektowany głównie do zgodności licencji. CycloneDX został zaprojektowany do operacji bezpieczeństwa. Jeśli Twoim głównym zastosowaniem jest zgodność z Artykułem 14, CycloneDX jest bardziej naturalnym wyborem.

## Generowanie SBOM-u CycloneDX

[[Syft]] od Anchore domyślnie generuje CycloneDX 1.6 JSON:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` to kolejna opcja, szczególnie dla budów specyficznych dla języka, gdzie skanowanie systemu plików przez Syft może pominąć zależności aplikacyjne:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Oba narzędzia generują prawidłowy wynik CycloneDX 1.6, który przechodzi walidację schematu i jest akceptowany przez narzędzia niższego rzędu, w tym Grype, Dependency-Track i większość platform zarządzania podatnościami.

## Kluczowe wnioski

1. CycloneDX jest standardem OWASP dostępnym w formatach JSON i XML. Bieżąca wersja to 1.6.
2. Cztery główne sekcje to: metadata (o SBOM-ie), components (wykaz), dependencies (graf) oraz opcjonalnie vulnerabilities.
3. Oświadczenia VEX pozwalają formalnie udokumentować, czy znane [[CVE]] jest możliwe do wykorzystania w kontekście Twojego konkretnego produktu. Kluczowe dla dowodów w audycie z Artykułu 14.
4. CycloneDX jest preferowanym formatem dla zgodności z CRA, ponieważ został zaprojektowany do procesów zarządzania podatnościami, a nie do zgodności licencji.
5. Zarówno Syft, jak i cdxgen generują wynik CycloneDX 1.6. Większość narzędzi do SBOM-ów ma CycloneDX jako podstawowy format wyjściowy.
