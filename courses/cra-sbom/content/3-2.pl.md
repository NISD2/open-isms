# Lekcja 3.2: Utrzymywanie aktualności SBOM i monitorowanie podatności

SBOM wygenerowany raz i nigdy więcej nieaktualizowany nie spełnia swojej podstawowej roli. Inwentarz komponentów zmienia się przy każdej aktualizacji zależności, łatce systemu operacyjnego lub zmianie łańcucha narzędzi budowania. Podatności w tych komponentach są publikowane bez przerwy. Lekcja opisuje, jak utrzymywać SBOM aktualny oraz jak wykorzystywać go jako narzędzie monitorowania zgodnie z Artykułem 14.

## Dlaczego SBOM się starzeje

SBOM odzwierciedla stan produktu w konkretnym momencie. W chwili scalenia żądania ściągającego aktualizującego zależność SBOM staje się nieaktualny. W chwili publikacji nowego [[CVE]] dotyczącego komponentu z SBOM ekspozycja na podatności ulega zmianie, lecz SBOM pozostaje bez zmian.

Dwie przyczyny powodują dryf SBOM:

1. **Zmiany komponentów**: aktualizacje zależności, łatki systemu operacyjnego, aktualizacje narzędzi budowania, zmiany w rozwiązywaniu zależności przechodnich przy przypięciu wersji najwyższego poziomu i przesunięciu jej podzależności.
2. **Publikacja podatności**: CVE dla komponentu, który wczoraj był bezpieczny, może zostać opublikowane dzisiaj.

Odpowiedzią na dryf typu 1 jest automatyczna regeneracja. Odpowiedzią na dryf typu 2 jest automatyczne skanowanie.

## Automatyczna regeneracja SBOM

Uruchamiaj generowanie SBOM jako część każdego budowania, które produkuje artefakt wydania. Nie generuj SBOM według harmonogramu, generuj go w ramach budowania, z tego samego artefaktu, który budowanie produkuje.

Zasada brzmi: jeden SBOM na artefakt wydania, wygenerowany w czasie budowania i przechowywany razem z artefaktem.

Jeśli produkt wydaje łatki między wersjami minor, co jest wymagane do spełnienia wymogów aktualizacji zabezpieczeń z Załącznika I część I CRA, każde wydanie łaty otrzymuje własny SBOM. Ten SBOM odzwierciedla inwentarz komponentów danej łaty. Gdy ujawniona zostanie podatność komponentu naprawionego w łatce 2.4.1, lecz nie w 2.4.0, potrzebny jest SBOM dla wersji 2.4.0, aby ustalić, że ta wersja była dotknięta.

## Pętla monitorowania podatności

[[Grype]] firmy Anchore to standardowe narzędzie do pętli monitorowania. Przyjmuje jako wejście SBOM w formacie CycloneDX, porównuje każdy komponent z wieloma źródłami informacji o podatnościach i zwraca raport:

```bash
grype sbom:sbom.cdx.json
```

Opcje formatu wyjściowego:

```bash
grype sbom:sbom.cdx.json -o json > vuln-report.json
grype sbom:sbom.cdx.json -o cyclonedx > vuln-cyclonedx.json
grype sbom:sbom.cdx.json -o sarif > results.sarif
```

Wynik CycloneDX z Grype można scalić z powrotem do SBOM jako uzupełnienie informacji o podatnościach, uzyskując jeden dokument zawierający zarówno inwentarz komponentów, jak i bieżący stan podatności.

Grype korzysta z:
- NVD (National Vulnerability Database)
- GitHub Advisory Database
- biuletynów zabezpieczeń Red Hat, Debian, Ubuntu, Alpine
- baz biuletynów Amazon, Oracle, SUSE
- źródeł informacji o podatnościach dla poszczególnych języków (PyPI, npm, Go, Maven, NuGet, Ruby)

## Automatyczne uruchamianie pętli monitorowania

Planuj uruchamianie Grype wobec produkcyjnych SBOM z częstotliwością odpowiadającą obowiązkowi monitorowania z Artykułu 14:

```yaml
# GitHub Actions scheduled scan
on:
  schedule:
    - cron: '0 6 * * *'  # daily at 06:00

jobs:
  vulnerability-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Download production SBOM
        run: aws s3 cp s3://my-sbom-bucket/production/sbom.cdx.json .

      - name: Run Grype scan
        run: grype sbom:sbom.cdx.json -o json > vuln-report.json

      - name: Check for critical/high vulnerabilities
        run: |
          CRITICAL=$(jq '[.matches[] | select(.vulnerability.severity=="Critical")] | length' vuln-report.json)
          if [ "$CRITICAL" -gt "0" ]; then
            echo "::error::$CRITICAL critical vulnerability/ies found"
            exit 1
          fi
```

Błąd kodu wyjścia uruchamia powiadomienie dla zespołu. Przepływ powiadomień należy skierować do osób odpowiedzialnych za decyzję sprawozdawczą z Artykułu 14.

## Progi ważności i wyzwalacz Artykułu 14

Nie każda podatność wymaga zgłoszenia zgodnie z Artykułem 14. Obowiązek jest uruchamiany przez [[actively exploited vulnerability|aktywnie wykorzystywana podatność]], czyli podatność, którą złośliwy podmiot aktualnie wykorzystuje przeciwko rzeczywistym systemom bez uprawnienia.

Ważność CVE (wynik CVSS) stanowi sygnał, nie wyzwalacz. Podatność o wyniku CVSS 9,8, dla której nie istnieje publiczny kod exploita i która nie jest wykorzystywana w atakach, nie uruchamia Artykułu 14. Podatność o wyniku CVSS 6,5 znajdująca się w katalogu CISA Known Exploited Vulnerabilities (KEV) i aktualnie wykorzystywana w kampaniach ransomware uruchamia ten obowiązek.

Proces monitorowania powinien:

1. **Przechwytywać wszystkie poziomy ważności powyżej progu**: co najmniej Critical i High
2. **Sprawdzać KEV**: katalog CISA KEV zawiera podatności aktualnie wykorzystywane. Grype oznacza wpisy KEV. CISA publikuje KEV jako kanał JSON pod adresem `kev.cisa.gov/api/v1/catalog`.
3. **Oceniać stosowalność**: czy podatliwy komponent jest rzeczywiście osiągalny w produkcie? Czy podatliwa ścieżka kodu jest wykonywana? Udokumentuj tę ocenę.
4. **Eskalować w przypadku aktywnego wykorzystywania**: jeśli komponent w SBOM posiada CVE znajdujące się w katalogu KEV i komponent jest osiągalny w produkcie, niezwłocznie eskaluj decyzję o 24-godzinnym zgłoszeniu z Artykułu 14.
5. **Dokumentować decyzję**: niezależnie od tego, czy zgłaszasz, czy stwierdzasz brak wpływu, udokumentuj decyzję i jej uzasadnienie. Użyj oświadczenia [[VEX]], aby uchwycić decyzje „not affected” w formie czytelnej dla maszyn.

## Korzystanie z Dependency-Track do ciągłego monitorowania

W organizacjach zarządzających wieloma produktami OWASP Dependency-Track zapewnia scentralizowany pulpit. Przekazujesz SBOM do Dependency-Track, narzędzie stale monitoruje źródła informacji o podatnościach i alarmuje, gdy nowe CVE dotyczy komponentu w dowolnym przekazanym SBOM.

Dependency-Track integruje się z:
- JIRA (tworzy zgłoszenia dla nowych krytycznych ustaleń)
- Slack i Teams (wysyła alarmy)
- REST API (umożliwia programowe zapytanie o stan podatności)

Dla producenta posiadającego pięć lub więcej produktów objętych CRA, Dependency-Track zmniejsza obciążenie operacyjne pętli monitorowania z Artykułu 14 z ręcznego procesu codziennego do zautomatyzowanego systemu alarmowego.

## Kluczowe wnioski

1. SBOM starzeją się, gdy zmieniają się komponenty i gdy publikowane są nowe CVE. Regeneruj automatycznie w czasie budowania, jeden SBOM na artefakt wydania.
2. [[Grype]] skanuje SBOM wobec wielu źródeł informacji o podatnościach i raportuje dopasowania. Uruchamiaj go codziennie lub przy każdym wdrożeniu.
3. Wyzwalacz Artykułu 14 stanowi aktywnie wykorzystywana podatność, nie sam wynik CVSS. Sprawdzaj katalog CISA KEV, aby zidentyfikować CVE aktualnie wykorzystywane w atakach.
4. Dokumentuj każdą ocenę: niezależnie od tego, czy zgłaszasz, czy stwierdzasz brak wpływu. Używaj oświadczeń [[VEX]] do dokumentacji „not affected” w formie czytelnej dla maszyn.
5. W przypadku portfeli wielu produktów OWASP Dependency-Track zapewnia scentralizowane ciągłe monitorowanie, które przekształca codzienną pętlę skanowania w zautomatyzowany system alarmowy.
