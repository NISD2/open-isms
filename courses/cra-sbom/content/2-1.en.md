# Lesson 2.1: CycloneDX: The Security-Focused SBOM Format

The CRA requires a "commonly used, machine-readable" format. Two formats qualify: [[CycloneDX]] and [[SPDX]]. This lesson covers CycloneDX: what it is, what makes it security-focused, and why it maps well to the CRA Article 14 vulnerability reporting workflow.

## What CycloneDX is

CycloneDX is an OWASP project. The Open Web Application Security Project (OWASP) maintains it as a standard for security use cases. The current version is 1.6. It is available in JSON and XML.

CycloneDX was designed to serve vulnerability management workflows. Its core data model is built around the question: "Given this list of components, which ones have known vulnerabilities, and can I act on them?" Every major feature in the format exists to answer that question.

## Structure of a CycloneDX SBOM

A CycloneDX document has four major sections:

### Metadata

Information about the SBOM document itself and the product it describes:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

The timestamp tells the auditor when the SBOM was generated. The tool tells them how. The component block identifies what the SBOM describes.

### Components

The list of software components. Each component has:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file`, or `operating-system`
- `name`: the canonical package name
- `version`: exact version string
- `supplier`: who publishes it
- `purl`: the [[PURL]] unique identifier
- `hashes`: SHA-256 or other hash of the component file
- `licenses`: SPDX license expressions

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX 1.4+ includes a `dependencies` section that maps which component depends on which. This is the machine-readable representation of the dependency graph. It is what lets a tool distinguish top-level from transitive components without re-running the build tool.

### Vulnerabilities

CycloneDX can embed vulnerability data directly in the SBOM. Each vulnerability entry references a [[CVE]] and the component it affects. This is useful for point-in-time documentation but less common in practice. Most teams keep the SBOM and the vulnerability scan output as separate artifacts.

## VEX: the feature that sets CycloneDX apart

[[VEX]], Vulnerability Exploitability eXchange, is the most distinctive CycloneDX feature for CRA compliance. A VEX statement is a machine-readable declaration that documents the relationship between a known vulnerability and your specific product.

CycloneDX VEX supports four status values:

- **not_affected**: the component is present but the vulnerability cannot be exploited in this product
- **affected**: the vulnerability can be exploited and you have not yet mitigated it
- **fixed**: the vulnerability was present and you have fixed it
- **under_investigation**: you are still assessing

Each `not_affected` statement requires a justification:

- `code_not_present`: the vulnerable code path does not exist in the version you are using
- `code_not_reachable`: the vulnerable code exists but cannot be reached in your execution context
- `requires_configuration`: exploitation requires a configuration that your deployment does not use
- `requires_environment`: exploitation requires an environment condition that does not apply
- `protected_by_mitigating_control`: you have a compensating control in place
- `protected_at_perimeter`: the affected component is not reachable from outside your environment

A VEX statement of `not_affected` with a `code_not_reachable` justification, dated and signed, is strong evidence in an Article 14 audit that you assessed the vulnerability and concluded it did not trigger the reporting obligation.

## Why CycloneDX is preferred for CRA compliance

The CRA Article 14 obligation is:

1. Monitor for actively exploited vulnerabilities in your product's components
2. If one is actively exploited, notify the CSIRT designated as coordinator and ENISA via the single reporting platform: an early warning within 24 hours, a fuller notification within 72 hours, and a final report within 14 days of a fix being available

CycloneDX's design aligns with this:

- PURL-based component identification maps directly to vulnerability database lookups
- VEX statements give you a machine-readable way to document monitoring decisions
- Tools like [[Grype]] natively consume CycloneDX SBOMs and produce CycloneDX vulnerability scan results
- The CycloneDX BOM Serial Number (`serialNumber`) lets you track SBOM versions over time

SPDX can do vulnerability management, but it was designed primarily for license compliance. CycloneDX was designed for security operations. If your primary use case is Article 14 compliance, CycloneDX is the more natural fit.

## Generating a CycloneDX SBOM

[[Syft]] by Anchore produces CycloneDX 1.6 JSON by default:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` is another option, particularly for language-specific builds where Syft's filesystem scan may miss application dependencies:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Both tools produce valid CycloneDX 1.6 output that passes schema validation and is accepted by downstream tools including Grype, Dependency-Track, and most vulnerability management platforms.

## Key takeaways

1. CycloneDX is an OWASP standard available in JSON and XML. Current version is 1.6.
2. The four main sections are: metadata (about the SBOM), components (the inventory), dependencies (the graph), and optionally vulnerabilities.
3. VEX statements let you formally document whether a known [[CVE]] is exploitable in your specific product context. This is critical for Article 14 audit evidence.
4. CycloneDX is the preferred format for CRA compliance because it was designed for vulnerability management workflows, not license compliance.
5. Syft and cdxgen both produce CycloneDX 1.6 output. Most SBOM tooling targets CycloneDX as its primary output format.
