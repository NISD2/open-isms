# Lezione 2.1: CycloneDX: Il formato SBOM orientato alla sicurezza

Il CRA richiede un formato "comunemente usato e leggibile da macchina". Due formati soddisfano i requisiti: [[CycloneDX]] e [[SPDX]]. Questa lezione tratta CycloneDX: cosa è, cosa lo rende orientato alla sicurezza e perché si adatta bene al flusso di lavoro per la segnalazione delle vulnerabilità previsto dall'Articolo 14 del CRA.

## Cos'è CycloneDX

CycloneDX è un progetto OWASP. L'Open Web Application Security Project (OWASP) lo mantiene come standard per i casi d'uso di sicurezza. La versione corrente è la 1.6. È disponibile in JSON e XML.

CycloneDX è stato progettato per supportare i flussi di lavoro di gestione delle vulnerabilità. Il suo modello di dati principale ruota attorno alla domanda: "Data questa lista di componenti, quali hanno vulnerabilità note e posso agire su di esse?". Ogni funzionalità principale del formato esiste per rispondere a tale domanda.

## Struttura di un SBOM CycloneDX

Un documento CycloneDX ha quattro sezioni principali:

### Metadata

Informazioni sul documento SBOM stesso e sul prodotto che descrive:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Il timestamp indica all'auditor quando è stato generato l'SBOM. Lo strumento indica come è stato generato. Il blocco del componente identifica ciò che l'SBOM descrive.

### Components

L'elenco dei componenti software. Ogni componente include:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` o `operating-system`
- `name`: il nome canonico del pacchetto
- `version`: stringa di versione esatta
- `supplier`: chi lo pubblica
- `purl`: l'identificatore univoco [[PURL]]
- `hashes`: SHA-256 o altro hash del file del componente
- `licenses`: espressioni di licenza SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX 1.4+ include una sezione `dependencies` che mappa le dipendenze tra i componenti. Si tratta della rappresentazione leggibile dalla macchina del grafo delle dipendenze. Consente a uno strumento di distinguere i componenti di primo livello da quelli transitivi senza rieseguire lo strumento di build.

### Vulnerabilities

CycloneDX può incorporare direttamente i dati sulle vulnerabilità nell'SBOM. Ogni voce di vulnerabilità fa riferimento a un [[CVE]] e al componente interessato. Ciò è utile per la documentazione puntuale, ma è meno comune nella pratica. La maggior parte dei team mantiene l'SBOM e l'output della scansione delle vulnerabilità come artefatti separati.

## VEX: la funzionalità che distingue CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, è la funzionalità più distintiva di CycloneDX per la conformità al CRA. Un'istruzione VEX è una dichiarazione leggibile dalla macchina che documenta la relazione tra una vulnerabilità nota e il prodotto specifico.

CycloneDX VEX supporta quattro valori di stato:

- **not_affected**: il componente è presente ma la vulnerabilità non può essere sfruttata in questo prodotto
- **affected**: la vulnerabilità può essere sfruttata e non è stata ancora mitigata
- **fixed**: la vulnerabilità era presente ed è stata corretta
- **under_investigation**: la valutazione è ancora in corso

Ogni istruzione `not_affected` richiede una giustificazione:

- `code_not_present`: il percorso di codice vulnerabile non esiste nella versione utilizzata
- `code_not_reachable`: il codice vulnerabile esiste ma non è raggiungibile nel contesto di esecuzione
- `requires_configuration`: lo sfruttamento richiede una configurazione non utilizzata nella distribuzione
- `requires_environment`: lo sfruttamento richiede una condizione ambientale non applicabile
- `protected_by_mitigating_control`: è presente un controllo compensativo
- `protected_at_perimeter`: il componente interessato non è raggiungibile dall'esterno dell'ambiente

Un'istruzione VEX di tipo `not_affected` con giustificazione `code_not_reachable`, datata e firmata, costituisce una prova solida in un audit ai sensi dell'Articolo 14 che la vulnerabilità è stata valutata e non ha attivato l'obbligo di segnalazione.

## Perché CycloneDX è preferibile per la conformità al CRA

L'obbligo previsto dall'Articolo 14 del CRA consiste in:

1. Monitorare le vulnerabilità attivamente sfruttate nei componenti del prodotto
2. In caso di sfruttamento attivo, notificare il CSIRT designato come coordinatore e ENISA tramite la piattaforma unica di segnalazione: un preavviso entro 24 ore, una notifica più completa entro 72 ore e una relazione finale entro 14 giorni dalla disponibilità di una correzione

La progettazione di CycloneDX si allinea con tali requisiti:

- L'identificazione dei componenti basata su PURL si collega direttamente alle ricerche nei database delle vulnerabilità
- Le istruzioni VEX offrono un modo leggibile dalla macchina per documentare le decisioni di monitoraggio
- Strumenti come [[Grype]] consumano in modo nativo gli SBOM CycloneDX e producono risultati di scansione delle vulnerabilità in formato CycloneDX
- Il numero di serie del BOM CycloneDX (`serialNumber`) consente di tracciare le versioni dell'SBOM nel tempo

SPDX può gestire la gestione delle vulnerabilità, ma è stato progettato principalmente per la conformità alle licenze. CycloneDX è stato progettato per le operazioni di sicurezza. Quando l'uso principale è la conformità all'Articolo 14, CycloneDX rappresenta la scelta più naturale.

## Generazione di un SBOM CycloneDX

[[Syft]] di Anchore produce CycloneDX 1.6 JSON per impostazione predefinita:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` è un'altra opzione, particolarmente indicata per le build specifiche del linguaggio in cui la scansione del filesystem di Syft potrebbe non rilevare le dipendenze dell'applicazione:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Entrambi gli strumenti producono output CycloneDX 1.6 valido che supera la convalida dello schema ed è accettato dagli strumenti a valle, inclusi Grype, Dependency-Track e la maggior parte delle piattaforme di gestione delle vulnerabilità.

## Punti chiave

1. CycloneDX è uno standard OWASP disponibile in JSON e XML. La versione corrente è la 1.6.
2. Le quattro sezioni principali sono: metadata (informazioni sull'SBOM), components (l'inventario), dependencies (il grafo) e, facoltativamente, vulnerabilities.
3. Le istruzioni VEX consentono di documentare formalmente se un [[CVE]] noto è sfruttabile nel contesto del prodotto specifico. Questo aspetto è fondamentale come evidenza in un audit ai sensi dell'Articolo 14.
4. CycloneDX è il formato preferito per la conformità al CRA perché è stato progettato per i flussi di lavoro di gestione delle vulnerabilità, non per la conformità alle licenze.
5. Syft e cdxgen producono entrambi output CycloneDX 1.6. La maggior parte degli strumenti SBOM utilizza CycloneDX come formato di output principale.
