# Lezione 2.1: CycloneDX: il formato SBOM orientato alla sicurezza

Il CRA richiede un formato "comunemente utilizzato e leggibile meccanicamente". Due formati soddisfano il requisito: [[CycloneDX]] e [[SPDX]]. Questa lezione copre CycloneDX, cos'è, cosa lo rende orientato alla sicurezza e perché si adatta bene al flusso di lavoro di segnalazione delle vulnerabilità di cui all'Articolo 14 CRA.

## Cos'è CycloneDX

CycloneDX è un progetto OWASP. L'Open Web Application Security Project (OWASP) lo mantiene come standard per i casi d'uso di sicurezza. La versione attuale è la 1.6. È disponibile in JSON e XML.

CycloneDX è stato progettato per servire i flussi di lavoro di gestione delle vulnerabilità. Il suo modello di dati di base è costruito attorno alla domanda: "Dato questo elenco di componenti, quali di essi presentano vulnerabilità note e posso agire su di esse?" Ogni funzionalità principale del formato esiste per rispondere a questa domanda.

## Struttura di un SBOM CycloneDX

Un documento CycloneDX ha quattro sezioni principali:

### Metadati

Informazioni sul documento SBOM stesso e sul prodotto che descrive:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Il timestamp indica all'auditor quando è stato generato l'SBOM. Lo strumento indica loro come. Il blocco component identifica cosa descrive l'SBOM.

### Componenti

L'elenco dei componenti software. Ogni componente ha:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` o `operating-system`
- `name`: il nome canonico del pacchetto
- `version`: la stringa di versione esatta
- `supplier`: chi lo pubblica
- `purl`: l'identificatore univoco [[PURL]]
- `hashes`: SHA-256 o altro hash del file del componente
- `licenses`: espressioni di licenza SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dipendenze

CycloneDX 1.4+ include una sezione `dependencies` che mappa quale componente dipende da quale. Questa è la rappresentazione leggibile meccanicamente del grafo delle dipendenze, è ciò che consente a uno strumento di distinguere i componenti di primo livello da quelli transitivi senza rieseguire lo strumento di build.

### Vulnerabilità

CycloneDX può incorporare i dati sulle vulnerabilità direttamente nell'SBOM. Ogni voce di vulnerabilità fa riferimento a una [[CVE]] e al componente che essa interessa. Questo è utile per la documentazione in un dato momento, ma meno comune nella pratica, la maggior parte dei team mantiene l'SBOM e l'output della scansione delle vulnerabilità come artefatti separati.

## VEX: la funzionalità che distingue CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, è la funzionalità più distintiva di CycloneDX per la conformità al CRA. Una dichiarazione VEX è una dichiarazione leggibile meccanicamente che documenta la relazione tra una vulnerabilità nota e il tuo prodotto specifico.

VEX di CycloneDX supporta quattro valori di stato:

- **not_affected**: il componente è presente ma la vulnerabilità non può essere sfruttata in questo prodotto
- **affected**: la vulnerabilità può essere sfruttata e non l'hai ancora mitigata
- **fixed**: la vulnerabilità era presente e l'hai corretta
- **under_investigation**: la stai ancora valutando

Ogni dichiarazione `not_affected` richiede una giustificazione:

- `code_not_present`: il percorso di codice vulnerabile non esiste nella versione che stai usando
- `code_not_reachable`: il codice vulnerabile esiste ma non può essere raggiunto nel tuo contesto di esecuzione
- `requires_configuration`: lo sfruttamento richiede una configurazione che la tua distribuzione non utilizza
- `requires_environment`: lo sfruttamento richiede una condizione ambientale che non si applica
- `protected_by_mitigating_control`: disponi di un controllo compensativo
- `protected_at_perimeter`: il componente interessato non è raggiungibile dall'esterno del tuo ambiente

Una dichiarazione VEX di `not_affected` con una giustificazione `code_not_reachable`, datata e firmata, è una prova solida, in un audit dell'Articolo 14, che hai valutato la vulnerabilità e concluso che non faceva scattare l'obbligo di segnalazione.

## Perché CycloneDX è preferito per la conformità al CRA

L'obbligo di cui all'Articolo 14 CRA è:

1. Monitorare le vulnerabilità attivamente sfruttate nei componenti del tuo prodotto
2. Segnalare a ENISA tramite la piattaforma unica di segnalazione entro 24 ore se una è attivamente sfruttata

Il design di CycloneDX si allinea a questo:

- L'identificazione dei componenti basata su PURL si collega direttamente alle ricerche nei database di vulnerabilità
- Le dichiarazioni VEX ti danno un modo leggibile meccanicamente per documentare le decisioni di monitoraggio
- Strumenti come [[Grype]] consumano nativamente gli SBOM CycloneDX e producono risultati di scansione delle vulnerabilità in CycloneDX
- Il numero di serie BOM di CycloneDX (`serialNumber`) ti consente di tracciare le versioni dell'SBOM nel tempo

SPDX può gestire le vulnerabilità, ma è stato progettato principalmente per la conformità alle licenze. CycloneDX è stato progettato per le operazioni di sicurezza. Se il tuo caso d'uso principale è la conformità all'Articolo 14, CycloneDX è la scelta più naturale.

## Generare un SBOM CycloneDX

[[Syft]] di Anchore produce CycloneDX 1.6 JSON per impostazione predefinita:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` è un'altra opzione, in particolare per le build specifiche di un linguaggio in cui la scansione del filesystem di Syft potrebbe non rilevare le dipendenze applicative:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Entrambi gli strumenti producono un output CycloneDX 1.6 valido che supera la convalida dello schema ed è accettato dagli strumenti a valle, inclusi Grype, Dependency-Track e la maggior parte delle piattaforme di gestione delle vulnerabilità.

## Punti chiave

1. CycloneDX è uno standard OWASP disponibile in JSON e XML. La versione attuale è la 1.6.
2. Le quattro sezioni principali sono: metadati (sull'SBOM), componenti (l'inventario), dipendenze (il grafo) e, facoltativamente, vulnerabilità.
3. Le dichiarazioni VEX ti consentono di documentare formalmente se una [[CVE]] nota è sfruttabile nel contesto specifico del tuo prodotto, fondamentale come prova in un audit dell'Articolo 14.
4. CycloneDX è il formato preferito per la conformità al CRA perché è stato progettato per i flussi di lavoro di gestione delle vulnerabilità, non per la conformità alle licenze.
5. Sia Syft sia cdxgen producono output CycloneDX 1.6. La maggior parte degli strumenti per SBOM punta a CycloneDX come formato di output principale.
