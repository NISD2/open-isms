# Lección 2.1: CycloneDX: el formato SBOM centrado en la seguridad

El CRA exige un formato "de uso común y legible por máquina". Dos formatos cumplen este requisito: [[CycloneDX]] y [[SPDX]]. Esta lección trata de CycloneDX: qué es, qué lo hace centrado en la seguridad y por qué se adapta bien al flujo de trabajo de notificación de vulnerabilidades del artículo 14 del CRA.

## Qué es CycloneDX

CycloneDX es un proyecto de OWASP. El Open Web Application Security Project (OWASP) lo mantiene como norma para casos de uso de seguridad. La versión actual es la 1.6. Está disponible en JSON y XML.

CycloneDX se diseñó para servir a los flujos de trabajo de gestión de vulnerabilidades. Su modelo de datos principal se construye en torno a la pregunta: "Dada esta lista de componentes, ¿cuáles tienen vulnerabilidades conocidas y puedo actuar sobre ellas?". Todas las funciones principales del formato existen para responder a esa pregunta.

## Estructura de un SBOM CycloneDX

Un documento CycloneDX tiene cuatro secciones principales:

### Metadatos

Información sobre el propio documento SBOM y el producto que describe:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

La marca temporal indica al auditor cuándo se generó el SBOM. La herramienta indica cómo se generó. El bloque de componente identifica lo que describe el SBOM.

### Componentes

La lista de componentes de software. Cada componente incluye:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` u `operating-system`
- `name`: el nombre canónico del paquete
- `version`: cadena de versión exacta
- `supplier`: quién lo publica
- `purl`: el identificador único [[PURL]]
- `hashes`: SHA-256 u otro hash del archivo del componente
- `licenses`: expresiones de licencia SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencias

CycloneDX 1.4+ incluye una sección `dependencies` que asigna qué componente depende de cuál. Esta es la representación legible por máquina del grafo de dependencias. Permite a una herramienta distinguir los componentes de nivel superior de los transitivos sin volver a ejecutar la herramienta de compilación.

### Vulnerabilidades

CycloneDX puede incorporar datos de vulnerabilidades directamente en el SBOM. Cada entrada de vulnerabilidad hace referencia a un [[CVE]] y al componente que afecta. Esto resulta útil para la documentación en un momento concreto, pero es menos habitual en la práctica. La mayoría de los equipos mantienen el SBOM y la salida del análisis de vulnerabilidades como artefactos independientes.

## VEX: la función que distingue a CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, es la función más característica de CycloneDX para el cumplimiento del CRA. Una declaración VEX es una declaración legible por máquina que documenta la relación entre una vulnerabilidad conocida y su producto específico.

VEX de CycloneDX admite cuatro valores de estado:

- **not_affected**: el componente está presente, pero la vulnerabilidad no puede explotarse en este producto
- **affected**: la vulnerabilidad puede explotarse y aún no se ha mitigado
- **fixed**: la vulnerabilidad estaba presente y se ha corregido
- **under_investigation**: todavía se está evaluando

Cada declaración `not_affected` requiere una justificación:

- `code_not_present`: la ruta de código vulnerable no existe en la versión que se utiliza
- `code_not_reachable`: el código vulnerable existe, pero no se puede alcanzar en el contexto de ejecución
- `requires_configuration`: la explotación requiere una configuración que no se utiliza en el despliegue
- `requires_environment`: la explotación requiere una condición de entorno que no aplica
- `protected_by_mitigating_control`: se cuenta con un control compensatorio
- `protected_at_perimeter`: el componente afectado no es accesible desde fuera del entorno

Una declaración VEX de `not_affected` con la justificación `code_not_reachable`, fechada y firmada, constituye una prueba sólida en una auditoría del artículo 14 de que se evaluó la vulnerabilidad y se concluyó que no activaba la obligación de notificación.

## Por qué CycloneDX es el formato preferido para el cumplimiento del CRA

La obligación del artículo 14 del CRA consiste en:

1. Supervisar las vulnerabilidades activamente explotadas en los componentes del producto
2. Si una vulnerabilidad está siendo activamente explotada, notificar al CSIRT designado como coordinador y a ENISA a través de la plataforma única de notificación: una alerta temprana en 24 horas, una notificación más completa en 72 horas y un informe final en un plazo de 14 días desde que esté disponible la corrección

El diseño de CycloneDX se alinea con esta obligación:

- La identificación de componentes basada en PURL se asigna directamente a las consultas en las bases de datos de vulnerabilidades
- Las declaraciones VEX proporcionan un medio legible por máquina para documentar las decisiones de supervisión
- Herramientas como [[Grype]] consumen de forma nativa los SBOM CycloneDX y generan resultados de análisis de vulnerabilidades en CycloneDX
- El número de serie del BOM de CycloneDX (`serialNumber`) permite realizar el seguimiento de las versiones del SBOM a lo largo del tiempo

SPDX puede gestionar vulnerabilidades, pero se diseñó principalmente para el cumplimiento de licencias. CycloneDX se diseñó para operaciones de seguridad. Si el caso de uso principal es el cumplimiento del artículo 14, CycloneDX resulta más natural.

## Generación de un SBOM CycloneDX

[[Syft]] de Anchore produce CycloneDX 1.6 JSON de forma predeterminada:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` es otra opción, especialmente para compilaciones específicas de lenguaje donde el análisis del sistema de archivos de Syft puede pasar por alto dependencias de la aplicación:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambas herramientas generan una salida CycloneDX 1.6 válida que supera la validación del esquema y es aceptada por herramientas posteriores como Grype, Dependency-Track y la mayoría de las plataformas de gestión de vulnerabilidades.

## Puntos clave

1. CycloneDX es una norma de OWASP disponible en JSON y XML. La versión actual es la 1.6.
2. Las cuatro secciones principales son: metadatos (sobre el SBOM), componentes (el inventario), dependencias (el grafo) y, opcionalmente, vulnerabilidades.
3. Las declaraciones VEX permiten documentar formalmente si un [[CVE]] conocido es explotable en el contexto específico del producto. Esto resulta fundamental como prueba en auditorías del artículo 14.
4. CycloneDX es el formato preferido para el cumplimiento del CRA porque se diseñó para flujos de trabajo de gestión de vulnerabilidades, no para el cumplimiento de licencias.
5. Syft y cdxgen generan ambos salida CycloneDX 1.6. La mayoría de las herramientas de SBOM utilizan CycloneDX como formato de salida principal.
