# Lección 2.1: CycloneDX: el formato de SBOM centrado en la seguridad

El CRA exige un formato "de uso común y legible por máquina". Dos formatos cumplen: [[CycloneDX]] y [[SPDX]]. Esta lección trata CycloneDX: qué es, qué lo hace centrado en la seguridad, y por qué se ajusta bien al flujo de trabajo de notificación de vulnerabilidades del Artículo 14 CRA.

## Qué es CycloneDX

CycloneDX es un proyecto de OWASP. El Open Web Application Security Project (OWASP) lo mantiene como estándar para casos de uso de seguridad. La versión actual es la 1.6. Está disponible en JSON y XML.

CycloneDX se diseñó para servir a los flujos de trabajo de gestión de vulnerabilidades. Su modelo de datos central se construye en torno a la pregunta: "Dada esta lista de componentes, ¿cuáles tienen vulnerabilidades conocidas y puedo actuar sobre ellas?". Cada característica importante del formato existe para responder a esa pregunta.

## Estructura de un SBOM CycloneDX

Un documento CycloneDX tiene cuatro secciones principales:

### Metadatos

Información sobre el propio documento SBOM y el producto que describe:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

La marca de tiempo le dice al auditor cuándo se generó el SBOM. La herramienta le dice cómo. El bloque del componente identifica qué describe el SBOM.

### Componentes

La lista de componentes de software. Cada componente tiene:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` o `operating-system`
- `name`: el nombre canónico del paquete
- `version`: cadena de versión exacta
- `supplier`: quién lo publica
- `purl`: el identificador unívoco [[PURL]]
- `hashes`: SHA-256 u otro hash del archivo del componente
- `licenses`: expresiones de licencia SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencias

CycloneDX 1.4+ incluye una sección `dependencies` que asigna qué componente depende de cuál. Esta es la representación legible por máquina del grafo de dependencias: es lo que permite a una herramienta distinguir los componentes de nivel superior de los transitivos sin volver a ejecutar la herramienta de compilación.

### Vulnerabilidades

CycloneDX puede incrustar datos de vulnerabilidades directamente en el SBOM. Cada entrada de vulnerabilidad referencia un [[CVE]] y el componente al que afecta. Esto es útil para documentación en un momento dado, pero menos común en la práctica: la mayoría de los equipos mantienen el SBOM y la salida del análisis de vulnerabilidades como artefactos separados.

## VEX: la característica que distingue a CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, es la característica más distintiva de CycloneDX para el cumplimiento del CRA. Una declaración VEX es una declaración legible por máquina que documenta la relación entre una vulnerabilidad conocida y tu producto concreto.

CycloneDX VEX admite cuatro valores de estado:

- **not_affected**: el componente está presente pero la vulnerabilidad no puede explotarse en este producto
- **affected**: la vulnerabilidad puede explotarse y todavía no la has mitigado
- **fixed**: la vulnerabilidad estaba presente y la has corregido
- **under_investigation**: todavía la estás evaluando

Cada declaración `not_affected` requiere una justificación:

- `code_not_present`: la ruta de código vulnerable no existe en la versión que estás usando
- `code_not_reachable`: el código vulnerable existe pero no puede alcanzarse en tu contexto de ejecución
- `requires_configuration`: la explotación requiere una configuración que tu despliegue no usa
- `requires_environment`: la explotación requiere una condición del entorno que no se da
- `protected_by_mitigating_control`: tienes un control compensatorio implantado
- `protected_at_perimeter`: el componente afectado no es alcanzable desde fuera de tu entorno

Una declaración VEX de `not_affected` con una justificación `code_not_reachable`, fechada y firmada, es una prueba sólida en una auditoría del Artículo 14 de que evaluaste la vulnerabilidad y concluiste que no desencadenaba la obligación de notificación.

## Por qué se prefiere CycloneDX para el cumplimiento del CRA

La obligación del Artículo 14 CRA es:

1. Hacer seguimiento de las vulnerabilidades explotadas activamente en los componentes de tu producto
2. Notificar a ENISA a través de la plataforma única de notificación en un plazo de 24 horas si alguna está explotada activamente

El diseño de CycloneDX se alinea con esto:

- La identificación de componentes basada en PURL se corresponde directamente con las búsquedas en bases de datos de vulnerabilidades
- Las declaraciones VEX te dan una forma legible por máquina de documentar las decisiones de seguimiento
- Herramientas como [[Grype]] consumen de forma nativa SBOM CycloneDX y producen resultados de análisis de vulnerabilidades CycloneDX
- El número de serie del BOM de CycloneDX (`serialNumber`) te permite rastrear las versiones del SBOM a lo largo del tiempo

SPDX puede hacer gestión de vulnerabilidades, pero se diseñó principalmente para el cumplimiento de licencias. CycloneDX se diseñó para operaciones de seguridad. Si tu caso de uso principal es el cumplimiento del Artículo 14, CycloneDX es el ajuste más natural.

## Generar un SBOM CycloneDX

[[Syft]] de Anchore produce CycloneDX 1.6 JSON por defecto:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` es otra opción, especialmente para compilaciones específicas de lenguaje donde el análisis del sistema de archivos de Syft puede pasar por alto dependencias de aplicación:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambas herramientas producen una salida CycloneDX 1.6 válida que pasa la validación de esquema y es aceptada por herramientas posteriores, incluidas Grype, Dependency-Track y la mayoría de las plataformas de gestión de vulnerabilidades.

## Puntos clave

1. CycloneDX es un estándar de OWASP disponible en JSON y XML. La versión actual es la 1.6.
2. Las cuatro secciones principales son: metadatos (sobre el SBOM), componentes (el inventario), dependencias (el grafo) y, opcionalmente, vulnerabilidades.
3. Las declaraciones VEX te permiten documentar formalmente si un [[CVE]] conocido es explotable en el contexto concreto de tu producto: crítico como prueba de auditoría para el Artículo 14.
4. CycloneDX es el formato preferido para el cumplimiento del CRA porque se diseñó para flujos de trabajo de gestión de vulnerabilidades, no para el cumplimiento de licencias.
5. Syft y cdxgen producen ambos una salida CycloneDX 1.6. La mayoría de las herramientas de SBOM tienen CycloneDX como su formato de salida principal.
