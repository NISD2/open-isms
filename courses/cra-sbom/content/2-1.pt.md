# Lição 2.1: CycloneDX: O Formato de SBOM Focado em Segurança

O CRA exige um formato "comumente utilizado, legível por máquina". Dois formatos qualificam: [[CycloneDX]] e [[SPDX]]. Esta lição aborda o CycloneDX: o que é, o que o torna focado em segurança e por que se alinha bem ao fluxo de trabalho de notificação de vulnerabilidades do Artigo 14 do CRA.

## O que é o CycloneDX

O CycloneDX é um projeto da OWASP. A Open Web Application Security Project (OWASP) mantém-no como norma para casos de uso de segurança. A versão atual é a 1.6. Está disponível em JSON e XML.

O CycloneDX foi concebido para servir fluxos de trabalho de gestão de vulnerabilidades. O seu modelo de dados principal centra-se na questão: "Dada esta lista de componentes, quais têm vulnerabilidades conhecidas e posso atuar sobre elas?" Todas as funcionalidades principais do formato existem para responder a essa questão.

## Estrutura de um SBOM CycloneDX

Um documento CycloneDX tem quatro secções principais:

### Metadados

Informação sobre o próprio documento SBOM e o produto que descreve:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

O timestamp indica ao auditor quando o SBOM foi gerado. A ferramenta indica como. O bloco de componentes identifica o que o SBOM descreve.

### Componentes

A lista de componentes de software. Cada componente inclui:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` ou `operating-system`
- `name`: o nome canónico do pacote
- `version`: cadeia de versão exata
- `supplier`: quem o publica
- `purl`: o identificador único [[PURL]]
- `hashes`: SHA-256 ou outro hash do ficheiro do componente
- `licenses`: expressões de licença SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependências

O CycloneDX 1.4+ inclui uma secção `dependencies` que mapeia qual componente depende de qual. Trata-se da representação legível por máquina do grafo de dependências. Permite a uma ferramenta distinguir componentes de nível superior dos transitivos sem voltar a executar a ferramenta de compilação.

### Vulnerabilidades

O CycloneDX pode incorporar dados de vulnerabilidades diretamente no SBOM. Cada entrada de vulnerabilidade referencia uma [[CVE]] e o componente que afeta. Isto é útil para documentação pontual, mas menos comum na prática. A maioria das equipas mantém o SBOM e o resultado da análise de vulnerabilidades como artefactos separados.

## VEX: a funcionalidade que distingue o CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, é a funcionalidade mais distintiva do CycloneDX para conformidade com o CRA. Uma declaração VEX é uma declaração legível por máquina que documenta a relação entre uma vulnerabilidade conhecida e o seu produto específico.

O VEX do CycloneDX suporta quatro valores de estado:

- **not_affected**: o componente está presente, mas a vulnerabilidade não pode ser explorada neste produto
- **affected**: a vulnerabilidade pode ser explorada e ainda não foi mitigada
- **fixed**: a vulnerabilidade estava presente e foi corrigida
- **under_investigation**: a avaliação continua

Cada declaração `not_affected` exige uma justificação:

- `code_not_present`: o caminho de código vulnerável não existe na versão utilizada
- `code_not_reachable`: o código vulnerável existe, mas não pode ser alcançado no contexto de execução
- `requires_configuration`: a exploração exige uma configuração que a implementação não utiliza
- `requires_environment`: a exploração exige uma condição de ambiente que não se aplica
- `protected_by_mitigating_control`: existe um controlo compensatório
- `protected_at_perimeter`: o componente afetado não é acessível a partir do exterior do ambiente

Uma declaração VEX de `not_affected` com justificação `code_not_reachable`, datada e assinada, constitui prova sólida numa auditoria do Artigo 14 de que a vulnerabilidade foi avaliada e se concluiu não desencadear a obrigação de notificação.

## Por que o CycloneDX é preferido para conformidade com o CRA

A obrigação do Artigo 14 do CRA consiste em:

1. Monitorizar vulnerabilidades exploradas ativamente nos componentes do produto
2. Se uma for explorada ativamente, notificar o CSIRT designado como coordenador e a ENISA através da plataforma única de notificação: um alerta precoce no prazo de 24 horas, uma notificação mais completa no prazo de 72 horas e um relatório final no prazo de 14 dias após a disponibilização de uma correção

A conceção do CycloneDX alinha-se com isto:

- A identificação de componentes baseada em PURL mapeia diretamente para consultas em bases de dados de vulnerabilidades
- As declarações VEX oferecem um meio legível por máquina para documentar decisões de monitorização
- Ferramentas como [[Grype]] consomem nativamente SBOMs CycloneDX e produzem resultados de análise de vulnerabilidades CycloneDX
- O número de série do BOM CycloneDX (`serialNumber`) permite acompanhar versões de SBOM ao longo do tempo

O SPDX consegue gerir vulnerabilidades, mas foi concebido principalmente para conformidade de licenças. O CycloneDX foi concebido para operações de segurança. Se o caso de uso principal é a conformidade com o Artigo 14, o CycloneDX é a opção mais natural.

## Gerar um SBOM CycloneDX

[[Syft]] da Anchore produz CycloneDX 1.6 JSON por predefinição:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` é outra opção, especialmente para compilações específicas de linguagem onde a análise de sistema de ficheiros do Syft pode não detetar dependências de aplicação:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambas as ferramentas produzem saída CycloneDX 1.6 válida que passa a validação de esquema e é aceite por ferramentas downstream, incluindo Grype, Dependency-Track e a maioria das plataformas de gestão de vulnerabilidades.

## Principais conclusões

1. O CycloneDX é uma norma da OWASP disponível em JSON e XML. A versão atual é a 1.6.
2. As quatro secções principais são: metadados (sobre o SBOM), componentes (o inventário), dependências (o grafo) e, opcionalmente, vulnerabilidades.
3. As declarações VEX permitem documentar formalmente se uma [[CVE]] conhecida é explorável no contexto específico do produto. Isto é essencial para provas em auditorias do Artigo 14.
4. O CycloneDX é o formato preferido para conformidade com o CRA porque foi concebido para fluxos de trabalho de gestão de vulnerabilidades, não para conformidade de licenças.
5. O Syft e o cdxgen produzem ambos saída CycloneDX 1.6. A maioria das ferramentas de SBOM tem o CycloneDX como formato de saída principal.
