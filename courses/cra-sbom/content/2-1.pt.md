# Lição 2.1: CycloneDX: O Formato de SBOM Orientado para a Segurança

O CRA exige um formato "de uso comum e legível por máquina". Dois formatos cumprem este requisito: [[CycloneDX]] e [[SPDX]]. Esta lição aborda o CycloneDX. O que é, o que o torna orientado para a segurança e porque mapeia bem para o fluxo de trabalho de comunicação de vulnerabilidades do Artigo 14 do CRA.

## O que é o CycloneDX

O CycloneDX é um projeto da OWASP. O Open Web Application Security Project (OWASP) mantém-no como uma norma para casos de uso de segurança. A versão atual é a 1.6. Está disponível em JSON e XML.

O CycloneDX foi concebido para servir fluxos de trabalho de gestão de vulnerabilidades. O seu modelo de dados central foi construído em torno da pergunta: "Dada esta lista de componentes, quais têm vulnerabilidades conhecidas e quais posso resolver?" Todas as funcionalidades principais do formato existem para responder a essa pergunta.

## Estrutura de um SBOM CycloneDX

Um documento CycloneDX tem quatro secções principais:

### Metadados

Informação sobre o próprio documento SBOM e sobre o produto que descreve:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

O timestamp indica ao auditor quando o SBOM foi gerado. A ferramenta indica como. O bloco de componente identifica o que o SBOM descreve.

### Componentes

A lista de componentes de software. Cada componente tem:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file`, ou `operating-system`
- `name`: o nome canónico do pacote
- `version`: a string de versão exata
- `supplier`: quem o publica
- `purl`: o identificador único [[PURL]]
- `hashes`: SHA-256 ou outro hash do ficheiro do componente
- `licenses`: expressões de licença SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependências

O CycloneDX 1.4+ inclui uma secção `dependencies` que mapeia qual componente depende de qual. Esta é a representação legível por máquina do grafo de dependências. É o que permite a uma ferramenta distinguir componentes de topo dos transitivos sem voltar a executar a ferramenta de build.

### Vulnerabilidades

O CycloneDX pode incorporar dados de vulnerabilidades diretamente no SBOM. Cada entrada de vulnerabilidade referencia um [[CVE]] e o componente que afeta. Isto é útil para documentação num momento concreto, mas menos comum na prática. A maioria das equipas mantém o SBOM e o resultado da análise de vulnerabilidades como artefactos separados.

## VEX: a funcionalidade que distingue o CycloneDX

O [[VEX]], Vulnerability Exploitability eXchange, é a funcionalidade do CycloneDX mais distintiva para a conformidade com o CRA. Uma declaração VEX é uma declaração legível por máquina que documenta a relação entre uma vulnerabilidade conhecida e o seu produto específico.

O VEX do CycloneDX suporta quatro valores de estado:

- **not_affected**: o componente está presente mas a vulnerabilidade não pode ser explorada neste produto
- **affected**: a vulnerabilidade pode ser explorada e ainda não a mitigou
- **fixed**: a vulnerabilidade estava presente e já a corrigiu
- **under_investigation**: ainda está a avaliar

Cada declaração `not_affected` exige uma justificação:

- `code_not_present`: o caminho de código vulnerável não existe na versão que está a usar
- `code_not_reachable`: o código vulnerável existe mas não pode ser alcançado no seu contexto de execução
- `requires_configuration`: a exploração exige uma configuração que a sua implementação não utiliza
- `requires_environment`: a exploração exige uma condição de ambiente que não se aplica
- `protected_by_mitigating_control`: tem um controlo compensatório em vigor
- `protected_at_perimeter`: o componente afetado não é alcançável a partir do exterior do seu ambiente

Uma declaração VEX de `not_affected` com uma justificação `code_not_reachable`, datada e assinada, constitui prova sólida numa auditoria ao Artigo 14 de que avaliou a vulnerabilidade e concluiu que não acionou a obrigação de comunicação.

## Porque o CycloneDX é preferido para a conformidade com o CRA

A obrigação do Artigo 14 do CRA é:

1. Monitorizar vulnerabilidades ativamente exploradas nos componentes do seu produto
2. Comunicar à ENISA através da Plataforma Única de Comunicação no prazo de 24 horas se uma estiver a ser ativamente explorada

A conceção do CycloneDX alinha-se com isto:

- A identificação de componentes baseada em PURL mapeia diretamente para pesquisas em bases de dados de vulnerabilidades
- As declarações VEX dão-lhe uma forma legível por máquina de documentar decisões de monitorização
- Ferramentas como o [[Grype]] consomem nativamente SBOM CycloneDX e produzem resultados de análise de vulnerabilidades em CycloneDX
- O Número de Série do BOM CycloneDX (`serialNumber`) permite-lhe acompanhar versões do SBOM ao longo do tempo

O SPDX consegue fazer gestão de vulnerabilidades, mas foi concebido principalmente para a conformidade de licenciamento. O CycloneDX foi concebido para operações de segurança. Se o seu caso de uso principal é a conformidade com o Artigo 14, o CycloneDX é a escolha mais natural.

## Gerar um SBOM CycloneDX

O [[Syft]] da Anchore produz CycloneDX 1.6 em JSON por predefinição:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

O `cdxgen` é outra opção, em particular para builds específicas de uma linguagem onde a análise do sistema de ficheiros do Syft pode não detetar dependências da aplicação:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambas as ferramentas produzem saída CycloneDX 1.6 válida, que passa a validação de esquema e é aceite por ferramentas a jusante, incluindo o Grype, o Dependency-Track e a maioria das plataformas de gestão de vulnerabilidades.

## Pontos-chave

1. O CycloneDX é uma norma da OWASP disponível em JSON e XML. A versão atual é a 1.6.
2. As quatro secções principais são: metadados (sobre o SBOM), componentes (o inventário), dependências (o grafo) e, opcionalmente, vulnerabilidades.
3. As declarações VEX permitem-lhe documentar formalmente se um [[CVE]] conhecido é explorável no contexto específico do seu produto. Algo crítico como prova para a auditoria ao Artigo 14.
4. O CycloneDX é o formato preferido para a conformidade com o CRA porque foi concebido para fluxos de trabalho de gestão de vulnerabilidades, não para conformidade de licenciamento.
5. Tanto o Syft como o cdxgen produzem saída CycloneDX 1.6. A maioria das ferramentas de SBOM tem o CycloneDX como formato de saída principal.
