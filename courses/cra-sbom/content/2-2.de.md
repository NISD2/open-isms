# Lektion 2.2: SPDX und Formatwahl

[[SPDX]] ist das andere Format, das die Anforderung von CRA Anhang I Teil II Nummer 1 für ein "häufig verwendetes und maschinenlesbares" SBOM erfüllt. Diese Lektion behandelt, was SPDX ist, worin es sich von CycloneDX unterscheidet und wie Sie entscheiden, welches Format Sie verwenden.

## Was SPDX ist

Software Package Data Exchange (SPDX) wurde 2010 von der Linux Foundation entwickelt. Es wurde 2021 ISO-Standard: ISO/IEC 5962:2021. Version 2.3 gilt derzeit für den ISO-Standard. Version 3.0 erschien 2024 mit einem neuen Datenmodell und Profil-System.

SPDX wurde entwickelt, um das Problem der Lizenz-Compliance bei Open Source zu lösen. Wenn Sie ein Produkt ausliefern, das Open-Source-Komponenten enthält, entstehen rechtliche Pflichten: Nennung, Einbindung des Lizenztextes, Offenlegung des Quellcodes bei Copyleft-Lizenzen. SPDX bietet eine maschinenlesbare Möglichkeit, auszudrücken, welche Lizenzen für welche Komponenten gelten und welche Pflichten Sie übernommen haben.

Es entwickelte sich im Laufe der Zeit zu einem SBOM-Standard und deckt nun auch die für das Schwachstellenmanagement erforderlichen Felder der Komponentenbestandsliste ab. Der ursprüngliche Entwurfszweck (Lizenz-Compliance) bleibt jedoch im Datenmodell erkennbar.

## SPDX-Dokumentstruktur

Ein SPDX-2.3-JSON-Dokument enthält:

- **Dokumenterstellungsinformationen**: entspricht den CycloneDX-Metadaten: Ersteller, Erstellungszeitstempel, Dokumentnamensraum, SPDX-Version
- **Pakete**: die Komponentenbestandsliste. Jedes Paket enthält: `name`, `version`, `supplier`, `downloadLocation`, `filesAnalyzed`, `packageVerificationCode` oder `checksums`, `licenseConcluded`, `licenseDeclared`, `copyrightText`, `externalRefs` (hier steht [[PURL]])
- **Beziehungen**: wie Pakete zueinander stehen. Die Beziehung `DESCRIBES` kennzeichnet das Produkt der obersten Ebene. `DEPENDS_ON` und `DEPENDENCY_OF` bilden den Abhängigkeitsgraphen ab.
- **Dateien** (optional): dateibasierte Bestandsliste mit Hashes, falls Dateiebene erforderlich ist
- **Snippets** (optional): Code-Snippet-Ebene für kopierten Code, der nicht aus einem Paket stammt

Das SPDX-2.3-PURL-Feld liegt innerhalb des Arrays `externalRefs`:

```json
"externalRefs": [
  {
    "referenceCategory": "PACKAGE-MANAGER",
    "referenceType": "purl",
    "referenceLocator": "pkg:pypi/requests@2.31.0"
  }
]
```

Dies ist ausführlicher als das erste-Klasse-Feld `purl` von CycloneDX, bleibt jedoch maschinenlesbar und von Schwachstellenscannern auswertbar.

## Wo SPDX Vorteile bietet

**ISO-Standardisierung.** ISO/IEC 5962:2021 bedeutet, dass SPDX das einzige SBOM-Format ist, das ein internationaler Standard ist. Für Organisationen, die ISO-zertifizierte Formate in Beschaffungs- oder Lieferantenverträgen verlangen, ist dies relevant.

**Lizenz-Compliance-Workflows.** Wenn Ihr primärer SBOM-Anwendungsfall die Open-Source-Lizenz-Compliance ist, die Nachverfolgung von Nennungspflichten, die Identifizierung von GPL-kontaminiertem Code oder die Erzeugung von Drittanbieter-Hinweisen, eignet sich das umfangreiche Lizenzmodell von SPDX besser. SPDX unterstützt SPDX-Lizenzkennungen, `LicenseInfoInFile` für dateibasierte Lizenzerkennung und `licenseComments` für komplexe Fälle.

**GitHub-Dependency-Graph-Integration.** Der Dependency Graph von GitHub exportiert nativ SPDX 2.3 JSON. Befindet sich Ihr Repository auf GitHub, liefert `github.com/your-org/your-repo/dependency-graph/sbom` ein SPDX-SBOM ohne lokale Tools. Für viele Teams ist dies der einfachste Einstieg.

**Mehrere Ausgabeformate.** SPDX unterstützt JSON, YAML, RDF/XML und ein Tag-Value-Textformat. Das Tag-Value-Format ist für Menschen lesbar (im Gegensatz zu JSON oder XML) und kann bei der Prüfung nützlich sein.

## Wo CycloneDX Vorteile bietet

**Schwachstellenmanagement.** CycloneDX bietet native [[VEX]]-Unterstützung. SPDX 3.0 hat ein Sicherheitsprofil mit VEX-Fähigkeiten hinzugefügt, doch die Unterstützung für SPDX-VEX im Ökosystem reift noch. Für Workflows zur Einhaltung von Artikel 14 ist CycloneDX VEX ausgereifter und wird von Tools besser unterstützt.

**Dependency-Track.** Die führende Open-Source-Plattform für SBOM-Management, OWASP Dependency-Track, wurde für CycloneDX entwickelt. Sie akzeptiert SPDX-Eingaben, doch ihre nativen Funktionen (Schwachstellenabgleich, VEX-Management, Richtlinienauswertung) sind für CycloneDX am vollständigsten.

**Tool-Reife.** Die Mehrzahl der SBOM-Tools, Syft, cdxgen, trivy, grype, behandelt CycloneDX als primäres Ausgabeformat und SPDX als sekundäres.

## Beide Formate erfüllen die CRA-Compliance

Die CRA verlangt "häufig verwendet, maschinenlesbar". Sowohl CycloneDX als auch SPDX werden von Hunderten von Organisationen eingesetzt. Beide sind maschinenlesbar. Beide können die von Anhang I Teil II Nummer 1 geforderten Felder der Komponentenbestandsliste tragen. Sie werden bei einer CRA-Prüfung nicht scheitern, weil Sie SPDX statt CycloneDX oder umgekehrt gewählt haben.

Die Leitlinien der Europäischen Kommission und das Dokument von ENISA zu SBOM-Best-Practice-Verfahren verweisen auf beide Formate. Es gibt keine offizielle EU-Leitlinie, die ein Format dem anderen vorzieht.

## Wie Sie wählen

Nutzen Sie diesen Entscheidungsrahmen:

| Frage | CycloneDX | SPDX |
|---|---|---|
| Primärer Anwendungsfall ist Schwachstellenmanagement und Compliance mit Artikel 14 | ✓ | - |
| Primärer Anwendungsfall ist Open-Source-Lizenz-Compliance | - | ✓ |
| Sie nutzen Dependency-Track | ✓ | - |
| Ihre Beschaffung verlangt ISO-zertifizierte Formate | - | ✓ |
| Sie starten mit dem Export des GitHub-Dependency-Graphs | - | ✓ |
| Ihr Team nutzt Syft oder cdxgen | ✓ | - |
| Sie benötigen ausgereifte VEX-Tools | ✓ | - |

Ist Schwachstellenmanagement Ihr Hauptanliegen, wählen Sie CycloneDX. Verfügen Sie bereits über einen SPDX-Workflow für die Lizenz-Compliance, ist dessen Erweiterung auf das Schwachstellenmanagement vertretbar. Beachten Sie jedoch, dass die VEX-Tools weniger ausgereift sind.

Viele Organisationen erzeugen beide Formate: CycloneDX für Sicherheitsoperationen, SPDX für Rechts- und Beschaffungsabteilungen. Die Tools unterstützen dies. Syft kann beide Formate aus demselben Scan ausgeben.

## Wichtige Erkenntnisse

1. SPDX (ISO/IEC 5962:2021) ist das ISO-Standard-SBOM-Format. Die aktuelle Version für den ISO-Standard ist 2.3, für das neue Datenmodell 3.0. Es wurde für die Open-Source-Lizenz-Compliance entwickelt.
2. Sowohl [[CycloneDX]] als auch SPDX erfüllen die Anforderung "häufig verwendet und maschinenlesbar" nach CRA Anhang I Teil II Nummer 1. Keines wird von EU-Leitlinien offiziell bevorzugt.
3. Vorteile von SPDX: ISO-Status, umfangreicheres Lizenzmodell, nativer Export des GitHub-Dependency-Graphs, mehrere Ausgabeformate.
4. Vorteile von CycloneDX: native [[VEX]]-Unterstützung, Dependency-Track-Integration, ausgereifteres Ökosystem für Schwachstellen-Tools.
5. Ist die Meldung von Schwachstellen nach CRA Artikel 14 Ihr Hauptantrieb, ist CycloneDX die natürlichere Wahl. Die Erzeugung beider Formate aus einem einzigen Syft-Scan ist eine zulässige Strategie.
