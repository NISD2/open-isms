# Lecția 2.1: CycloneDX: Formatul SBOM axat pe securitate

CRA impune un format „uzual, lizibil automat”. Două formate îndeplinesc cerința: [[CycloneDX]] și [[SPDX]]. Această lecție prezintă CycloneDX: ce este, ce îl face axat pe securitate și de ce corespunde bine fluxului de raportare a vulnerabilităților din articolul 14 CRA.

## Ce este CycloneDX

CycloneDX este un proiect OWASP. Open Web Application Security Project (OWASP) îl menține ca standard pentru cazuri de utilizare în securitate. Versiunea curentă este 1.6. Este disponibil în JSON și XML.

CycloneDX a fost conceput pentru fluxuri de gestionare a vulnerabilităților. Modelul său de date principal răspunde la întrebarea: „Având această listă de componente, care prezintă vulnerabilități cunoscute și pot acționa asupra lor?” Fiecare funcționalitate majoră a formatului există pentru a răspunde la această întrebare.

## Structura unui SBOM CycloneDX

Un document CycloneDX conține patru secțiuni majore:

### Metadata

Informații despre documentul SBOM în sine și despre produsul descris:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Marcajul temporal indică auditorului când a fost generat SBOM-ul. Instrumentul arată cum a fost creat. Blocul component identifică obiectul descris de SBOM.

### Components

Lista componentelor software. Fiecare componentă include:

- `type`: `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` sau `operating-system`
- `name`: numele canonic al pachetului
- `version`: șirul exact al versiunii
- `supplier`: entitatea care îl publică
- `purl`: identificatorul unic [[PURL]]
- `hashes`: SHA-256 sau alt hash al fișierului componentei
- `licenses`: expresii de licență SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependencies

CycloneDX 1.4+ include o secțiune `dependencies` care cartografiază dependențele dintre componente. Aceasta este reprezentarea lizibilă automat a grafului de dependențe. Permite unui instrument să distingă componentele de nivel superior de cele tranzitive fără a rula din nou instrumentul de construire.

### Vulnerabilities

CycloneDX poate încorpora direct date despre vulnerabilități în SBOM. Fiecare intrare de vulnerabilitate face referire la un [[CVE]] și la componenta afectată. Utilitatea este limitată la documentarea punctuală; în practică, majoritatea echipelor păstrează SBOM-ul și rezultatul scanării de vulnerabilități ca artefacte separate.

## VEX: funcționalitatea care diferențiază CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, este cea mai distinctivă funcționalitate CycloneDX pentru conformitatea cu CRA. O declarație VEX este o declarație lizibilă automat care documentează relația dintre o vulnerabilitate cunoscută și produsul specific.

CycloneDX VEX acceptă patru valori de stare:

- **not_affected**: componenta este prezentă, dar vulnerabilitatea nu poate fi exploatată în acest produs
- **affected**: vulnerabilitatea poate fi exploatată și nu a fost încă atenuată
- **fixed**: vulnerabilitatea a fost prezentă și a fost corectată
- **under_investigation**: evaluarea continuă

Fiecare declarație `not_affected` necesită o justificare:

- `code_not_present`: calea de cod vulnerabilă nu există în versiunea utilizată
- `code_not_reachable`: codul vulnerabil există, dar nu poate fi atins în contextul de execuție
- `requires_configuration`: exploatarea necesită o configurație pe care implementarea nu o utilizează
- `requires_environment`: exploatarea necesită o condiție de mediu care nu se aplică
- `protected_by_mitigating_control`: există un control compensatoriu
- `protected_at_perimeter`: componenta afectată nu este accesibilă din exteriorul mediului

O declarație VEX de tip `not_affected` cu justificarea `code_not_reachable`, datată și semnată, constituie o probă solidă în auditul articolului 14 că vulnerabilitatea a fost evaluată și s-a concluzionat că nu declanșează obligația de raportare.

## De ce CycloneDX este preferat pentru conformitatea cu CRA

Obligația din articolul 14 CRA constă în:

1. Monitorizarea vulnerabilităților exploatate activ în componentele produsului
2. Dacă o vulnerabilitate este exploatată activ, notificarea CSIRT-ului desemnat coordonator și a ENISA prin platforma unică de raportare: o avertizare timpurie în 24 de ore, o notificare completă în 72 de ore și un raport final în 14 zile de la disponibilitatea unei corecții

Proiectarea CycloneDX se aliniază cu aceste cerințe:

- Identificarea componentelor pe bază de PURL corespunde direct interogărilor bazelor de date de vulnerabilități
- Declarațiile VEX oferă o modalitate lizibilă automat de a documenta deciziile de monitorizare
- Instrumente precum [[Grype]] consumă nativ SBOM-uri CycloneDX și produc rezultate de scanare a vulnerabilităților în același format
- Numărul de serie al BOM-ului CycloneDX (`serialNumber`) permite urmărirea versiunilor SBOM în timp

SPDX poate gestiona vulnerabilități, dar a fost conceput în principal pentru conformitatea cu licențele. CycloneDX a fost conceput pentru operațiuni de securitate. Când obiectivul principal este conformitatea cu articolul 14, CycloneDX reprezintă alegerea mai naturală.

## Generarea unui SBOM CycloneDX

[[Syft]] de la Anchore produce implicit CycloneDX 1.6 JSON:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` reprezintă o alternativă, în special pentru construcții specifice limbajelor unde scanarea de sistem de fișiere a lui Syft poate omite dependențe de aplicație:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambele instrumente generează ieșire CycloneDX 1.6 validă, care trece validarea schemei și este acceptată de instrumente ulterioare, inclusiv Grype, Dependency-Track și majoritatea platformelor de gestionare a vulnerabilităților.

## Concluzii cheie

1. CycloneDX este un standard OWASP disponibil în JSON și XML. Versiunea curentă este 1.6.
2. Cele patru secțiuni principale sunt: metadata (despre SBOM), components (inventarul), dependencies (graful) și, opțional, vulnerabilities.
3. Declarațiile VEX permit documentarea formală a faptului dacă un [[CVE]] cunoscut este exploatabil în contextul specific al produsului. Aceasta este esențială pentru probele de audit conform articolului 14.
4. CycloneDX este formatul preferat pentru conformitatea cu CRA deoarece a fost conceput pentru fluxuri de gestionare a vulnerabilităților, nu pentru conformitatea cu licențele.
5. Syft și cdxgen generează ambele ieșire CycloneDX 1.6. Majoritatea instrumentelor SBOM țintesc CycloneDX ca format principal de ieșire.
