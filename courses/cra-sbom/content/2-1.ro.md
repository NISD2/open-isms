# Lecția 2.1: CycloneDX: formatul SBOM orientat pe securitate

CRA cere un format "frecvent utilizat, care poate fi citit automat". Două formate îndeplinesc condiția: [[CycloneDX]] și [[SPDX]]. Această lecție tratează CycloneDX. Ce este, ce îl face orientat pe securitate și de ce se potrivește bine cu fluxul de raportare a vulnerabilităților din Articolul 14 al CRA.

## Ce este CycloneDX

CycloneDX este un proiect OWASP. Open Web Application Security Project (OWASP) îl menține ca standard pentru cazuri de utilizare din zona securității. Versiunea curentă este 1.6. Este disponibil în JSON și XML.

CycloneDX a fost conceput pentru a servi fluxurilor de gestionare a vulnerabilităților. Modelul său de date central este construit în jurul întrebării: "Dată fiind această listă de componente, care dintre ele au vulnerabilități cunoscute și pot acționa asupra lor?" Fiecare funcție importantă a formatului există pentru a răspunde la această întrebare.

## Structura unui SBOM CycloneDX

Un document CycloneDX are patru secțiuni principale:

### Metadate

Informații despre documentul SBOM în sine și despre produsul pe care îl descrie:

```json
"metadata": {
  "timestamp": "2025-03-15T10:30:00Z",
  "tools": [{ "vendor": "Anchore", "name": "Syft", "version": "1.0.0" }],
  "component": {
    "type": "application",
    "name": "MyProduct",
    "version": "2.4.1",
    "purl": "pkg:docker/myproduct@2.4.1"
  }
}
```

Marcajul temporal îi spune auditorului când a fost generat SBOM-ul. Instrumentul îi spune cum. Blocul component identifică ce descrie SBOM-ul.

### Componente

Lista componentelor software. Fiecare componentă are:

- `type`, care este `library`, `framework`, `application`, `container`, `device`, `firmware`, `file` sau `operating-system`
- `name`, numele canonic al pachetului
- `version`, șirul exact al versiunii
- `supplier`, cine îl publică
- `purl`, identificatorul unic [[PURL]]
- `hashes`, SHA-256 sau alt hash al fișierului componentei
- `licenses`, expresii de licență SPDX

```json
{
  "type": "library",
  "name": "requests",
  "version": "2.31.0",
  "supplier": { "name": "Python Software Foundation" },
  "purl": "pkg:pypi/requests@2.31.0",
  "hashes": [{ "alg": "SHA-256", "content": "942c5a758f98..." }],
  "licenses": [{ "expression": "Apache-2.0" }]
}
```

### Dependențe

CycloneDX 1.4+ include o secțiune `dependencies` care indică ce componentă depinde de care. Aceasta este reprezentarea, care poate fi citită automat, a grafului de dependențe. Este ceea ce permite unui instrument să distingă componentele de nivel superior de cele tranzitive fără a rula din nou instrumentul de build.

### Vulnerabilități

CycloneDX poate include datele despre vulnerabilități direct în SBOM. Fiecare intrare de vulnerabilitate face referire la un [[CVE]] și la componenta pe care o afectează. Acest lucru este util pentru documentarea la un moment dat, dar mai puțin frecvent în practică. Majoritatea echipelor păstrează SBOM-ul și rezultatul scanării de vulnerabilități ca artefacte separate.

## VEX: funcția care distinge CycloneDX

[[VEX]], Vulnerability Exploitability eXchange, este cea mai distinctivă funcție CycloneDX pentru conformitatea cu CRA. O declarație VEX este o declarație care poate fi citită automat și care documentează relația dintre o vulnerabilitate cunoscută și produsul dumneavoastră specific.

VEX în CycloneDX acceptă patru valori de status:

- **not_affected**, componenta este prezentă, dar vulnerabilitatea nu poate fi exploatată în acest produs
- **affected**, vulnerabilitatea poate fi exploatată și nu ați atenuat-o încă
- **fixed**, vulnerabilitatea era prezentă și ați remediat-o
- **under_investigation**, încă o evaluați

Fiecare declarație `not_affected` necesită o justificare:

- `code_not_present`, calea de cod vulnerabilă nu există în versiunea pe care o utilizați
- `code_not_reachable`, codul vulnerabil există, dar nu poate fi atins în contextul dumneavoastră de execuție
- `requires_configuration`, exploatarea necesită o configurație pe care implementarea dumneavoastră nu o utilizează
- `requires_environment`, exploatarea necesită o condiție de mediu care nu se aplică
- `protected_by_mitigating_control`, aveți un control compensatoriu instituit
- `protected_at_perimeter`, componenta afectată nu poate fi atinsă din afara mediului dumneavoastră

O declarație VEX de tip `not_affected` cu o justificare `code_not_reachable`, datată și semnată, reprezintă o dovadă solidă, într-un audit conform Articolului 14, că ați evaluat vulnerabilitatea și ați concluzionat că nu a declanșat obligația de raportare.

## De ce este preferat CycloneDX pentru conformitatea cu CRA

Obligația din Articolul 14 al CRA este:

1. Monitorizați vulnerabilitățile exploatate activ din componentele produsului dumneavoastră
2. Raportați către ENISA prin Platforma unică de raportare în termen de 24 de ore dacă una este exploatată activ

Designul CycloneDX se aliniază cu aceasta:

- Identificarea componentelor bazată pe PURL corespunde direct căutărilor în bazele de date de vulnerabilități
- Declarațiile VEX vă oferă o modalitate, care poate fi citită automat, de a documenta deciziile de monitorizare
- Instrumente precum [[Grype]] consumă nativ SBOM-uri CycloneDX și produc rezultate de scanare a vulnerabilităților în CycloneDX
- Numărul de serie al BOM-ului CycloneDX (`serialNumber`) vă permite să urmăriți versiunile SBOM în timp

SPDX poate face gestionarea vulnerabilităților, dar a fost conceput în principal pentru conformitatea cu licențele. CycloneDX a fost conceput pentru operațiuni de securitate. Dacă principalul dumneavoastră caz de utilizare este conformitatea cu Articolul 14, CycloneDX este alegerea mai naturală.

## Generarea unui SBOM CycloneDX

[[Syft]] de la Anchore produce implicit CycloneDX 1.6 JSON:

```bash
syft my-container-image:latest -o cyclonedx-json > sbom.cdx.json
```

`cdxgen` este o altă opțiune, în special pentru build-uri specifice unui limbaj, unde scanarea sistemului de fișiere a Syft poate rata dependențele aplicației:

```bash
cdxgen -t java -o sbom.cdx.json .
```

Ambele instrumente produc o ieșire CycloneDX 1.6 validă, care trece validarea de schemă și este acceptată de instrumentele din aval, inclusiv Grype, Dependency-Track și majoritatea platformelor de gestionare a vulnerabilităților.

## Concluzii cheie

1. CycloneDX este un standard OWASP disponibil în JSON și XML. Versiunea curentă este 1.6.
2. Cele patru secțiuni principale sunt: metadate (despre SBOM), componente (inventarul), dependențe (graful) și, opțional, vulnerabilități.
3. Declarațiile VEX vă permit să documentați formal dacă un [[CVE]] cunoscut este exploatabil în contextul specific al produsului dumneavoastră. Esențial pentru dovezile de audit conform Articolului 14.
4. CycloneDX este formatul preferat pentru conformitatea cu CRA, deoarece a fost conceput pentru fluxuri de gestionare a vulnerabilităților, nu pentru conformitatea cu licențele.
5. Atât Syft, cât și cdxgen produc o ieșire CycloneDX 1.6. Majoritatea instrumentelor SBOM țintesc CycloneDX ca format principal de ieșire.
