# Lección 1.1: Qué entra en un SBOM: componentes, versiones e identificadores

El Artículo 13(5) CRA te dice que crees un SBOM. No te dice cada campo que debes incluir. Los formatos, [[CycloneDX]] y [[SPDX]], cubren ese hueco. Esta lección trata los campos que tu SBOM debe contener para ser útil en la práctica: para un escáner de vulnerabilidades, para un auditor, y para ti cuando algo sale mal a las 2 de la madrugada.

## El mínimo que exige el CRA

El mínimo del CRA es: "los componentes contenidos en los productos con elementos digitales ... como mínimo, las dependencias de nivel superior". En la práctica, eso significa que cada entrada de componente necesita información suficiente para responder a:

- ¿Qué es este componente?
- ¿Quién lo creó?
- ¿Qué versión tiene?
- ¿Cómo lo busco en una base de datos de vulnerabilidades?

Esas cuatro preguntas se corresponden directamente con los campos básicos que tanto CycloneDX como SPDX exigen.

## Los campos básicos

### Nombre

El nombre del componente tal y como lo publica el mantenedor del paquete. No tu alias interno. El nombre exacto tal como aparece en el registro de paquetes. Para npm: `@angular/core`. Para Maven: `org.springframework.boot:spring-boot`. Para Python: `requests`.

Los nombres exactos importan porque las bases de datos de vulnerabilidades indexan por el nombre canónico del paquete. Una pequeña diferencia ortográfica rompe la búsqueda.

### Versión

La cadena de versión exacta. Para paquetes npm: `17.0.0`. Para bibliotecas del sistema: `2.38.1-5+deb12u1`. Los rangos como `>=2.0` no son aceptables: no le dicen a un escáner qué binario se está ejecutando realmente.

La versión importa porque un [[CVE]] suele afectar a un rango de versiones y se corrige en una versión concreta. Sin la versión exacta, no puedes determinar si tu componente está afectado.

### Proveedor

La organización que publica o mantiene el componente. Para paquetes npm: el autor u organización que figura en el manifiesto del paquete. Para paquetes del sistema operativo: el mantenedor de la distribución. Para bibliotecas comerciales: el fabricante.

El proveedor importa para el panorama de riesgo de [[supply chain attack|ataques a la cadena de suministro]]. Si un proveedor se ve comprometido, saber cuáles de tus componentes provienen de ese proveedor te indica dónde mirar primero.

### Identificador unívoco: el PURL

Un [[PURL]] (Package URL) es la forma estándar de identificar un componente de manera unívoca entre registros y bases de datos. El formato es:

```
pkg:type/namespace/name@version
```

Ejemplos:

- `pkg:npm/%40angular/core@17.0.0` — Angular Core 17.0.0 de npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0` — Spring Boot 3.2.0 de Maven Central
- `pkg:pypi/requests@2.31.0` — requests 2.31.0 de PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3` — libc6 de Debian Bookworm

Tanto CycloneDX como SPDX tratan el PURL como el identificador unívoco recomendado. Las bases de datos de vulnerabilidades lo usan para vincular registros CVE con componentes concretos. Cuando tu escáner coteja un SBOM contra un feed de vulnerabilidades, está cotejando PURL.

### Hash

Un [[hash]] es una huella de longitud fija del archivo del componente. SHA-256 es el estándar. Incluir un hash en cada entrada del SBOM te permite verificar que el componente no ha cambiado desde que se generó el SBOM. Es además la única forma de confirmar que dos equipos están hablando del mismo binario, no solo de la misma cadena de versión.

CycloneDX y SPDX admiten ambos hashes por componente. Añádelos siempre que tus herramientas los produzcan.

### Licencia

No es obligatorio según el mínimo del CRA, pero sí lo exigen la mayoría de los flujos de trabajo de SPDX y resulta útil en la práctica. El SPDX License Identifier (p. ej., `Apache-2.0`, `MIT`, `GPL-2.0-only`) enlaza con el texto completo de la licencia.

Si eres una empresa que usa componentes de código abierto, la información de licencia en el SBOM es la base de tu programa de cumplimiento de licencias de código abierto.

## Metadatos del SBOM

Más allá de la lista de componentes, un SBOM válido incluye metadatos sobre el propio documento SBOM:

- **Marca de tiempo**: cuándo se generó el SBOM
- **Versión del SBOM**: una versión o identificador de este documento SBOM concreto
- **Información de la herramienta**: qué herramienta generó el SBOM y en qué versión
- **Describe**: qué producto o componente describe este SBOM (el paquete de nivel superior)

CycloneDX lo llama el objeto `metadata`. SPDX lo llama la sección de información de creación del documento. Los auditores miran aquí primero para verificar la actualidad.

## Qué significa "legible por máquina" en la práctica

El CRA exige un formato "legible por máquina". Esto significa que un escáner de vulnerabilidades debe poder analizar el SBOM sin intervención humana. JSON y XML lo cumplen. Una hoja de cálculo o un PDF no.

Un SBOM legible por máquina te permite automatizar el bucle de seguimiento del Artículo 14: se publica un nuevo CVE → el escáner coteja el SBOM → se genera una alerta → el equipo evalúa → se presenta la notificación si es necesario.

Si tu SBOM es un PDF, nada de esa automatización funciona.

## Puntos clave

1. Cada entrada de componente del SBOM necesita, como mínimo: nombre, versión, proveedor y un identificador unívoco. El [[PURL]] es el identificador unívoco estándar.
2. Las cadenas de versión exactas son obligatorias: los rangos rompen el análisis de vulnerabilidades.
3. Un hash por componente te permite verificar que el SBOM no se ha desviado del binario realmente desplegado.
4. Los metadatos del SBOM (marca de tiempo, herramienta, describe) son lo primero que comprueba un auditor.
5. "Legible por máquina" significa JSON o XML: formatos que un escáner de vulnerabilidades puede analizar automáticamente. Una hoja de cálculo o un PDF no cumplen.
