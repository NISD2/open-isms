# Lección 1.1: Qué incluye un SBOM: Componentes, versiones e identificadores

El anexo I, parte II, punto (1) del CRA exige crear un SBOM. No especifica cada campo que debe incluirse. Los formatos [[CycloneDX]] y [[SPDX]] cubren esa necesidad. Esta lección describe los campos que el SBOM debe contener para resultar útil en la práctica: para un escáner de vulnerabilidades, para un auditor y para usted cuando surge un problema a las 2 de la madrugada.

## El mínimo que exige el CRA

El mínimo del CRA es: «componentes contenidos en los productos con elementos digitales ... al menos las dependencias de nivel superior». En la práctica, esto significa que cada entrada de componente necesita suficiente información para responder a estas preguntas:

- ¿Qué es este componente?
- ¿Quién lo ha creado?
- ¿Qué versión tiene?
- ¿Cómo se puede consultar en una base de datos de vulnerabilidades?

Estas cuatro preguntas se corresponden directamente con los campos principales que exigen tanto CycloneDX como SPDX.

## Los campos principales

### Nombre

El nombre del componente tal como lo publica el responsable del paquete. No se trata del alias interno. El nombre exacto que aparece en el registro de paquetes. Para npm: `@angular/core`. Para Maven: `org.springframework.boot:spring-boot`. Para Python: `requests`.

Los nombres exactos importan porque las bases de datos de vulnerabilidades indexan por el nombre canónico del paquete. Una diferencia menor de ortografía impide la consulta.

### Versión

La cadena de versión exacta. Para paquetes npm: `17.0.0`. Para bibliotecas del sistema: `2.38.1-5+deb12u1`. No se aceptan rangos como `>=2.0`. Estos rangos no indican al escáner qué binario se está ejecutando realmente.

La versión importa porque un [[CVE]] suele afectar a un rango de versiones y se corrige en una versión concreta. Sin la versión exacta, no se puede determinar si el componente está afectado.

### Proveedor

La organización que publica o mantiene el componente. Para paquetes npm: el autor o la organización que figura en el manifiesto del paquete. Para paquetes del sistema operativo: el responsable de la distribución. Para bibliotecas comerciales: el proveedor.

El proveedor importa para la imagen de riesgo de [[supply chain attack|ataque a la cadena de suministro]]. Si un proveedor sufre una vulneración, saber qué componentes proceden de ese proveedor indica dónde buscar primero.

### Identificador único: el PURL

Un [[PURL]] (Package URL) es la forma estándar de identificar un componente de manera única en distintos registros y bases de datos. El formato es:

```
pkg:type/namespace/name@version
```

Ejemplos:

- `pkg:npm/%40angular/core@17.0.0`: Angular Core 17.0.0 de npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0`: Spring Boot 3.2.0 de Maven Central
- `pkg:pypi/requests@2.31.0`: requests 2.31.0 de PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3`: libc6 de Debian Bookworm

Tanto CycloneDX como SPDX tratan el PURL como el identificador único recomendado. Las bases de datos de vulnerabilidades lo utilizan para vincular registros CVE a componentes específicos. Cuando un escáner compara un SBOM con una fuente de vulnerabilidades, está comparando PURLs.

### Hash

Un [[hash|hash]] es una huella digital de longitud fija del archivo del componente. SHA-256 es el estándar. Incluir un hash en cada entrada del SBOM permite verificar que el componente no ha cambiado desde que se generó el SBOM. También es la única forma de confirmar que dos equipos se refieren al mismo binario, y no solo a la misma cadena de versión.

Tanto CycloneDX como SPDX admiten hashes por componente. Añádalos siempre que la herramienta los genere.

### Licencia

No la exige el mínimo del CRA, pero sí la requieren la mayoría de los flujos de trabajo SPDX y resulta útil en la práctica. El identificador de licencia SPDX (por ejemplo, `Apache-2.0`, `MIT`, `GPL-2.0-only`) enlaza con el texto completo de la licencia.

Si una empresa utiliza componentes de código abierto, la información de licencias en el SBOM constituye la base de su programa de cumplimiento de licencias de código abierto.

## Metadatos del SBOM

Además de la lista de componentes, un SBOM válido incluye metadatos sobre el propio documento SBOM:

- **Marca temporal**: momento en que se generó el SBOM
- **Versión del SBOM**: una versión o identificador de este documento SBOM concreto
- **Información de la herramienta**: qué herramienta generó el SBOM y en qué versión
- **Describe**: qué producto o componente describe este SBOM (el paquete de nivel superior)

CycloneDX denomina a esto el objeto `metadata`. SPDX lo denomina sección de información de creación del documento. Los auditores consultan primero esta sección para verificar la actualidad.

## Qué significa «legible por máquina» en la práctica

El CRA exige un formato «legible por máquina». Esto significa que un escáner de vulnerabilidades debe poder analizar el SBOM sin intervención humana. JSON y XML cumplen este requisito. Una hoja de cálculo o un PDF no lo cumple.

Un SBOM legible por máquina permite automatizar el bucle de supervisión del artículo 14: publicación de un nuevo CVE → el escáner compara el SBOM → se genera una alerta → el equipo evalúa → se presenta un informe si es necesario.

Si el SBOM es un PDF, ninguna de esas automatizaciones funciona.

## Conclusiones principales

1. Cada entrada de componente del SBOM necesita como mínimo: nombre, versión, proveedor y un identificador único. El [[PURL]] es el identificador único estándar.
2. Se requieren cadenas de versión exactas. Los rangos impiden el análisis de vulnerabilidades.
3. Un hash por componente permite verificar que el SBOM no ha variado respecto al binario realmente desplegado.
4. Los metadatos del SBOM (marca temporal, herramienta, describe) son lo primero que comprueba un auditor.
5. «Legible por máquina» significa JSON o XML: formatos que un escáner de vulnerabilidades puede analizar automáticamente. Una hoja de cálculo o un PDF no cumple este requisito.
