# Lesson 3.1: Building Your SBOM: Tools and Pipeline Integration

Knowing what an SBOM should contain is one thing. Getting it generated reliably, as part of your build process, for every release, is another. This lesson covers the tools that generate SBOMs and how to integrate SBOM generation into a CI/CD pipeline so the output is always current.

## The two categories of SBOM generation

### Source-time analysis

Source-time tools read your code's dependency manifest files, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, and produce an SBOM from the declared dependencies. These tools understand package manager lock files and can produce complete transitive dependency graphs from them.

**cdxgen** (CycloneDX Generator) is the most capable source-time tool. It supports over 30 language ecosystems: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP, and more. It reads the lock file for the ecosystem and outputs CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Source-time analysis is accurate for application dependencies but misses operating system packages and system libraries that are not in the language-specific manifests.

### Image/filesystem scanning

Image scanners examine a built artifact, a container image, a filesystem directory, a compiled binary, and identify packages from the package databases present. [[Syft]] by Anchore is the leading tool for this.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifies packages by reading:
- OS package databases (dpkg for Debian/Ubuntu, rpm for RHEL/Fedora, apk for Alpine)
- Language-specific package manifests and lock files embedded in the image
- Binary signatures for packages that were compiled and installed without a package manager

The advantage of image scanning: you see exactly what is in the artifact that will be deployed. The disadvantage: if a package was installed without a package manager (common in legacy build systems), Syft may miss it.

## Best practice: combine both approaches

Run cdxgen against your source code for application dependencies, and Syft against your container image for OS and runtime packages. Merge the two SBOMs using a merge tool. CycloneDX provides a merge operation that combines component lists and deduplicates.

The merged SBOM covers:
- Application dependencies (from cdxgen, full transitive graph)
- OS packages (from Syft)
- Runtime dependencies (Node.js runtime, Python interpreter, JVM)

This is the complete picture the CRA and Article 14 monitoring require.

## Integrating SBOM generation into CI/CD

The SBOM should be generated automatically as part of your build pipeline. Manual SBOM generation creates the risk of a stale or missing SBOM when you need it for an audit or incident response.

### GitHub Actions example

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Attach the SBOM to the release artifact. Every release gets an SBOM. The SHA-tagged filename creates the audit trail linking each SBOM to its corresponding build.

### GitLab CI example

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` ensures GitLab does not delete the artifact. Combined with your release tagging, this gives you SBOM history for every release going back as far as you need.

## Validating your SBOM

Before storing or submitting an SBOM, validate it:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

The CycloneDX CLI is available from `@cyclonedx/cyclonedx-cli`. Schema validation catches missing required fields, incorrect types, and malformed PURLs before the SBOM enters your documentation records.

## Signing your SBOM

A signed SBOM is stronger evidence in an audit than an unsigned one. If you can show that the SBOM was generated at a specific point in time and has not been modified since, you have a stronger chain of custody.

Cosign (from the Sigstore project) can sign and verify SBOM files:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

The signature file proves the SBOM was produced by your build system and has not been altered. Store the signature alongside the SBOM.

## Key takeaways

1. Source-time tools (cdxgen) read package manifests and produce complete transitive dependency graphs. Image scanners (Syft) examine built artifacts and find OS and runtime packages.
2. Best practice combines both: cdxgen for application dependencies, Syft for OS and runtime packages, merged into one SBOM.
3. SBOM generation must be integrated into CI/CD. Manual generation creates stale or missing SBOMs under pressure.
4. Attach the SBOM to every release artifact, tagged with the build SHA or version. This creates the audit trail the 10-year retention rule requires.
5. Validate with the CycloneDX CLI before storage. Sign with Cosign to create a chain of custody.
