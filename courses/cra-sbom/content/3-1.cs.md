# Lekce 3.1: Vytváření SBOM: Nástroje a integrace do pipeline

Vědět, co by SBOM měl obsahovat, je jedna věc. Zajistit jeho spolehlivé generování jako součásti procesu sestavení pro každé vydání je věc druhá. Tato lekce se zabývá nástroji, které generují SBOM, a tím, jak integrovat generování SBOM do pipeline CI/CD, aby byl výstup vždy aktuální.

## Dvě kategorie generování SBOM

### Analýza v době zdrojového kódu

Nástroje pro analýzu v době zdrojového kódu čtou soubory manifestů závislostí vašeho kódu, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, a vytvářejí SBOM z deklarovaných závislostí. Tyto nástroje rozumí zamykacím souborům správců balíčků a dokážou z nich vytvořit úplné grafy tranzitivních závislostí.

**cdxgen** (CycloneDX Generator) je nejschopnějším nástrojem pro analýzu v době zdrojového kódu. Podporuje více než 30 jazykových ekosystémů: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP a další. Čte zamykací soubor pro daný ekosystém a vystupuje CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Analýza v době zdrojového kódu je přesná pro aplikační závislosti, ale přehlíží balíčky operačního systému a systémové knihovny, které nejsou uvedeny v jazykově specifických manifestecha.

### Skenování image/souborového systému

Skenovací nástroje pro image zkoumají sestavený artefakt, kontejnerovou image, adresář souborového systému, zkompilovanou binárku a identifikují balíčky z přítomných databází balíčků. [[Syft]] od Anchore je předním nástrojem pro tento účel.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifikuje balíčky čtením:
- databází balíčků operačního systému (dpkg pro Debian/Ubuntu, rpm pro RHEL/Fedora, apk pro Alpine)
- jazykově specifických manifestů balíčků a zamykacích souborů vložených do image
- binárních podpisů pro balíčky, které byly zkompilovány a nainstalovány bez správce balíčků

Výhoda skenování image: vidíte přesně to, co obsahuje artefakt určený k nasazení. Nevýhoda: pokud byl balíček nainstalován bez správce balíčků (běžné v legacy build systémech), může jej Syft přehlédnout.

## Osvědčený postup: kombinace obou přístupů

Spusťte cdxgen proti zdrojovému kódu pro aplikační závislosti a Syft proti kontejnerové image pro balíčky operačního systému a runtime. Sloučte oba SBOM pomocí nástroje pro slučování. CycloneDX poskytuje operaci merge, která kombinuje seznamy komponent a odstraňuje duplicity.

Sloučený SBOM pokrývá:
- aplikační závislosti (z cdxgen, úplný tranzitivní graf)
- balíčky operačního systému (ze Syft)
- runtime závislosti (Node.js runtime, Python interpreter, JVM)

Toto je úplný obraz, který vyžaduje CRA a Article 14 pro monitorování.

## Integrace generování SBOM do CI/CD

SBOM by měl být generován automaticky jako součást build pipeline. Ruční generování SBOM vytváří riziko zastaralého nebo chybějícího SBOM v okamžiku, kdy jej potřebujete pro audit nebo reakci na incident.

### Příklad GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Připojte SBOM k release artifact. Každé vydání obdrží SBOM. Název souboru označený SHA vytváří auditní stopu spojující každý SBOM s odpovídajícím buildem.

### Příklad GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` zajišťuje, že GitLab artefakt neodstraní. Ve spojení s vaším označováním vydání získáte historii SBOM pro každé vydání tak daleko do minulosti, jak potřebujete.

## Validace vašeho SBOM

Před uložením nebo odesláním SBOM jej validujte:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

CycloneDX CLI je dostupný z `@cyclonedx/cyclonedx-cli`. Validace schématu zachytí chybějící povinná pole, nesprávné typy a chybně utvořené PURL dříve, než SBOM vstoupí do vašich dokumentačních záznamů.

## Podepisování vašeho SBOM

Podepsaný SBOM představuje v auditu silnější důkaz než nepodepsaný. Pokud můžete prokázat, že SBOM byl vygenerován v určitém okamžiku a od té doby nebyl změněn, máte silnější řetězec péče o důkazní materiál.

Cosign (z projektu Sigstore) dokáže podepsat a ověřit soubory SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Soubor s podpisem dokazuje, že SBOM byl vytvořen vaším build systémem a nebyl pozměněn. Uložte podpis společně se SBOM.

## Klíčové poznatky

1. Nástroje pro analýzu v době zdrojového kódu (cdxgen) čtou manifesty balíčků a vytvářejí úplné grafy tranzitivních závislostí. Skenovací nástroje pro image (Syft) zkoumají sestavené artefakty a nacházejí balíčky operačního systému a runtime.
2. Osvědčený postup kombinuje oba přístupy: cdxgen pro aplikační závislosti, Syft pro balíčky operačního systému a runtime, sloučené do jednoho SBOM.
3. Generování SBOM musí být integrováno do CI/CD. Ruční generování vytváří zastaralé nebo chybějící SBOM pod tlakem.
4. Připojte SBOM ke každému release artifact, označený build SHA nebo verzí. Tím vzniká auditní stopa, kterou vyžaduje pravidlo 10leté uchovávání.
5. Před uložením validujte pomocí CycloneDX CLI. Podepište pomocí Cosign pro vytvoření řetězce péče o důkazní materiál.
