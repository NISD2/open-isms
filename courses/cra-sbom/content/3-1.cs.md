# Lekce 3.1: Vytváření SBOM: nástroje a integrace do pipeline

Vědět, co má SBOM obsahovat, je jedna věc. Spolehlivě jej generovat jako součást procesu sestavení pro každé vydání je věc druhá. Tato lekce popisuje nástroje, které SBOM generují, a způsob, jak generování SBOM začlenit do CI/CD pipeline tak, aby byl výstup vždy aktuální.

## Dvě kategorie generování SBOM

### Analýza ze zdrojového kódu

Nástroje pracující na úrovni zdrojového kódu čtou soubory s manifestem závislostí vašeho kódu, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, a z deklarovaných závislostí vytvoří SBOM. Tyto nástroje rozumí lock souborům správců balíčků a dokážou z nich sestavit úplné grafy tranzitivních závislostí.

**cdxgen** (CycloneDX Generator) je nejschopnější nástroj tohoto typu. Podporuje přes 30 jazykových ekosystémů: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP a další. Načte lock soubor daného ekosystému a vypíše CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

Analýza ze zdrojového kódu je přesná pro závislosti aplikace, ale nezachytí balíčky operačního systému a systémové knihovny, které nejsou v manifestech specifických pro daný jazyk.

### Skenování image a souborového systému

Skenery image zkoumají sestavený artefakt, image kontejneru, adresář souborového systému, zkompilovaný binární soubor, a identifikují balíčky z přítomných databází balíčků. [[Syft|Syft]] od společnosti Anchore je v této oblasti vedoucím nástrojem.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifikuje balíčky čtením:
- Databází balíčků operačního systému (dpkg pro Debian/Ubuntu, rpm pro RHEL/Fedora, apk pro Alpine)
- Manifestů a lock souborů specifických pro jednotlivé jazyky vložených v image
- Binárních signatur balíčků, které byly zkompilovány a nainstalovány bez správce balíčků

Výhoda skenování image: vidíte přesně to, co je v artefaktu, který se bude nasazovat. Nevýhoda: pokud byl balíček nainstalován bez správce balíčků (běžné u starších systémů sestavení), Syft jej může přehlédnout.

## Doporučený postup: zkombinujte oba přístupy

Spusťte cdxgen nad zdrojovým kódem pro závislosti aplikace a Syft nad image kontejneru pro balíčky operačního systému a běhového prostředí. Oba SBOM sloučte pomocí slučovacího nástroje. CycloneDX nabízí operaci sloučení, která spojí seznamy komponent a odstraní duplicity.

Sloučený SBOM pokrývá:
- Závislosti aplikace (z cdxgen, úplný tranzitivní graf)
- Balíčky operačního systému (ze Syftu)
- Závislosti běhového prostředí (běhové prostředí Node.js, interpret Pythonu, JVM)

To je úplný obraz, který CRA a monitorování podle článku 14 vyžadují.

## Integrace generování SBOM do CI/CD

SBOM by se měl generovat automaticky jako součást vaší pipeline sestavení. Ruční generování SBOM nese riziko zastaralého nebo chybějícího SBOM ve chvíli, kdy jej potřebujete pro audit nebo reakci na incident.

### Příklad pro GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Připojte SBOM k artefaktu vydání. Každé vydání dostane svůj SBOM. Název souboru opatřený SHA vytváří auditní stopu, která propojuje každý SBOM s odpovídajícím sestavením.

### Příklad pro GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` zajistí, že GitLab artefakt nesmaže. Ve spojení s vaším značkováním vydání tak získáte historii SBOM pro každé vydání tak daleko zpět, jak potřebujete.

## Validace vašeho SBOM

Před uložením nebo odesláním SBOM jej zvalidujte:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

CycloneDX CLI je k dispozici z `@cyclonedx/cyclonedx-cli`. Validace schématu odhalí chybějící povinná pole, nesprávné typy a chybně sestavené PURL ještě předtím, než se SBOM dostane do vašich dokumentačních záznamů.

## Podepsání vašeho SBOM

Podepsaný SBOM je při auditu silnějším důkazem než nepodepsaný. Pokud dokážete prokázat, že SBOM byl vygenerován v konkrétním okamžiku a od té doby nebyl změněn, máte silnější řetězec úschovy.

Cosign (z projektu Sigstore) umí soubory SBOM podepsat a ověřit:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

Soubor se signaturou prokazuje, že SBOM vytvořil váš systém sestavení a nebyl pozměněn. Signaturu uložte společně se SBOM.

## Klíčové poznatky

1. Nástroje pracující na úrovni zdrojového kódu (cdxgen) čtou manifesty balíčků a vytvářejí úplné grafy tranzitivních závislostí. Skenery image (Syft) zkoumají sestavené artefakty a nacházejí balíčky operačního systému a běhového prostředí.
2. Doporučený postup kombinuje oba přístupy: cdxgen pro závislosti aplikace, Syft pro balíčky operačního systému a běhového prostředí, sloučené do jednoho SBOM.
3. Generování SBOM musí být integrováno do CI/CD. Ruční generování vede pod tlakem k zastaralým nebo chybějícím SBOM.
4. Připojte SBOM ke každému artefaktu vydání, opatřený značkou SHA sestavení nebo verzí. Tím vzniká auditní stopa, kterou vyžaduje pravidlo o desetiletém uchovávání.
5. Před uložením proveďte validaci pomocí CycloneDX CLI. Podepsáním pomocí Cosignu vytvoříte řetězec úschovy.
