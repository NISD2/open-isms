# Lección 3.1: Crear tu SBOM: herramientas e integración en la cadena de entrega

Saber qué debe contener un SBOM es una cosa. Conseguir que se genere de forma fiable, como parte de tu proceso de compilación, en cada release, es otra. Esta lección trata las herramientas que generan SBOM y cómo integrar la generación del SBOM en una cadena CI/CD para que la salida esté siempre actualizada.

## Las dos categorías de generación de SBOM

### Análisis en tiempo de código fuente

Las herramientas en tiempo de código fuente leen los archivos de manifiesto de dependencias de tu código, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, y producen un SBOM a partir de las dependencias declaradas. Estas herramientas entienden los archivos de bloqueo de los gestores de paquetes y pueden producir grafos completos de dependencias transitivas a partir de ellos.

**cdxgen** (CycloneDX Generator) es la herramienta más capaz en tiempo de código fuente. Admite más de 30 ecosistemas de lenguaje: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP y más. Lee el archivo de bloqueo del ecosistema y produce CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

El análisis en tiempo de código fuente es preciso para las dependencias de aplicación, pero pasa por alto los paquetes del sistema operativo y las bibliotecas del sistema que no figuran en los manifiestos específicos del lenguaje.

### Análisis de imagen/sistema de archivos

Los escáneres de imagen examinan un artefacto compilado, una imagen de contenedor, un directorio del sistema de archivos, un binario compilado, e identifican los paquetes a partir de las bases de datos de paquetes presentes. [[Syft]] de Anchore es la herramienta líder para esto.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifica los paquetes leyendo:
- Bases de datos de paquetes del SO (dpkg para Debian/Ubuntu, rpm para RHEL/Fedora, apk para Alpine)
- Manifiestos y archivos de bloqueo de paquetes específicos del lenguaje incrustados en la imagen
- Firmas binarias de paquetes que se compilaron e instalaron sin un gestor de paquetes

La ventaja del análisis de imagen: ves exactamente qué hay en el artefacto que se va a desplegar. La desventaja: si un paquete se instaló sin un gestor de paquetes (común en sistemas de compilación heredados), Syft puede pasarlo por alto.

## Buena práctica: combinar ambos enfoques

Ejecuta cdxgen contra tu código fuente para las dependencias de aplicación, y Syft contra tu imagen de contenedor para los paquetes del SO y del entorno de ejecución. Fusiona los dos SBOM con una herramienta de fusión. CycloneDX proporciona una operación de fusión que combina las listas de componentes y elimina duplicados.

El SBOM fusionado abarca:
- Dependencias de aplicación (de cdxgen, grafo transitivo completo)
- Paquetes del SO (de Syft)
- Dependencias del entorno de ejecución (entorno de ejecución de Node.js, intérprete de Python, JVM)

Esta es la imagen completa que exigen el CRA y el seguimiento del Artículo 14.

## Integrar la generación del SBOM en CI/CD

El SBOM debe generarse automáticamente como parte de tu cadena de compilación. La generación manual del SBOM crea el riesgo de un SBOM obsoleto o ausente cuando lo necesitas para una auditoría o la respuesta a un incidente.

### Ejemplo con GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Adjunta el SBOM al artefacto de release. Cada release obtiene un SBOM. El nombre de archivo etiquetado con el SHA crea el rastro de auditoría que vincula cada SBOM con su compilación correspondiente.

### Ejemplo con GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantiza que GitLab no borre el artefacto. Combinado con tu etiquetado de releases, esto te da un historial de SBOM para cada release hasta donde lo necesites.

## Validar tu SBOM

Antes de almacenar o presentar un SBOM, valídalo:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

El CLI de CycloneDX está disponible desde `@cyclonedx/cyclonedx-cli`. La validación de esquema detecta campos obligatorios ausentes, tipos incorrectos y PURL malformados antes de que el SBOM entre en tus registros de documentación.

## Firmar tu SBOM

Un SBOM firmado es una prueba más sólida en una auditoría que uno sin firmar. Si puedes demostrar que el SBOM se generó en un momento concreto y no se ha modificado desde entonces, tienes una cadena de custodia más fuerte.

Cosign (del proyecto Sigstore) puede firmar y verificar archivos SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

El archivo de firma demuestra que el SBOM fue producido por tu sistema de compilación y no ha sido alterado. Almacena la firma junto al SBOM.

## Puntos clave

1. Las herramientas en tiempo de código fuente (cdxgen) leen los manifiestos de paquetes y producen grafos completos de dependencias transitivas. Los escáneres de imagen (Syft) examinan artefactos compilados y encuentran paquetes del SO y del entorno de ejecución.
2. La buena práctica combina ambos: cdxgen para las dependencias de aplicación, Syft para los paquetes del SO y del entorno de ejecución, fusionados en un solo SBOM.
3. La generación del SBOM debe integrarse en CI/CD. La generación manual crea SBOM obsoletos o ausentes bajo presión.
4. Adjunta el SBOM a cada artefacto de release, etiquetado con el SHA o la versión de la compilación. Esto crea el rastro de auditoría que exige la regla de conservación de 10 años.
5. Valida con el CLI de CycloneDX antes de almacenar. Firma con Cosign para crear una cadena de custodia.
