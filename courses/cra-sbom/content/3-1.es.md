# Lección 3.1: Construcción de su SBOM: Herramientas e integración en la canalización

Saber qué debe contener un SBOM es una cosa. Generarlo de forma fiable, como parte del proceso de compilación, para cada versión, es otra. Esta lección aborda las herramientas que generan SBOM y cómo integrar la generación de SBOM en una canalización CI/CD para que la salida esté siempre actualizada.

## Las dos categorías de generación de SBOM

### Análisis en tiempo de origen

Las herramientas de tiempo de origen leen los archivos de manifiesto de dependencias del código, `package-lock.json`, `requirements.txt`, `pom.xml`, `Cargo.lock`, `go.sum`, y producen un SBOM a partir de las dependencias declaradas. Estas herramientas entienden los archivos de bloqueo de gestores de paquetes y pueden producir gráficos completos de dependencias transitivas a partir de ellos.

**cdxgen** (CycloneDX Generator) es la herramienta de tiempo de origen más capaz. Admite más de 30 ecosistemas de lenguajes: Node.js, Python, Java, Go, Rust, .NET, Ruby, PHP y otros. Lee el archivo de bloqueo del ecosistema y genera CycloneDX JSON.

```bash
# Node.js project
cdxgen -t npm -o sbom.cdx.json .

# Python project
cdxgen -t python -o sbom.cdx.json .

# Java Maven project
cdxgen -t maven -o sbom.cdx.json .
```

El análisis en tiempo de origen es preciso para las dependencias de la aplicación, pero omite los paquetes del sistema operativo y las bibliotecas del sistema que no figuran en los manifiestos específicos del lenguaje.

### Análisis de imagen o sistema de archivos

Los escáneres de imagen examinan un artefacto compilado, una imagen de contenedor, un directorio del sistema de archivos o un binario compilado, e identifican los paquetes a partir de las bases de datos de paquetes presentes. [[Syft]] de Anchore es la herramienta líder para esta tarea.

```bash
# Scan a container image
syft my-image:1.2.3 -o cyclonedx-json > sbom.cdx.json

# Scan a directory
syft dir:./build -o cyclonedx-json > sbom.cdx.json

# Scan a tarball
syft my-image.tar -o cyclonedx-json > sbom.cdx.json
```

Syft identifica paquetes mediante la lectura de:
- Bases de datos de paquetes del sistema operativo (dpkg para Debian/Ubuntu, rpm para RHEL/Fedora, apk para Alpine)
- Manifiestos y archivos de bloqueo de paquetes específicos del lenguaje incrustados en la imagen
- Firmas binarias de paquetes que se compilaron e instalaron sin gestor de paquetes

La ventaja del análisis de imagen es que se ve exactamente lo que contiene el artefacto que se va a desplegar. La desventaja es que, si un paquete se instaló sin gestor de paquetes (algo habitual en sistemas de compilación heredados), Syft puede omitirlo.

## Práctica recomendada: combinar ambos enfoques

Ejecute cdxgen sobre el código fuente para las dependencias de la aplicación y Syft sobre la imagen de contenedor para los paquetes del sistema operativo y del entorno de ejecución. Combine los dos SBOM con una herramienta de fusión. CycloneDX proporciona una operación de fusión que combina listas de componentes y elimina duplicados.

El SBOM fusionado cubre:
- Dependencias de la aplicación (de cdxgen, gráfico transitivo completo)
- Paquetes del sistema operativo (de Syft)
- Dependencias del entorno de ejecución (entorno de ejecución de Node.js, intérprete de Python, JVM)

Esta es la imagen completa que exige el CRA y el seguimiento del Artículo 14.

## Integración de la generación de SBOM en CI/CD

El SBOM debe generarse automáticamente como parte de la canalización de compilación. La generación manual de SBOM crea el riesgo de obtener un SBOM obsoleto o ausente cuando se necesita para una auditoría o una respuesta a incidentes.

### Ejemplo de GitHub Actions

```yaml
- name: Generate SBOM
  run: |
    syft my-image:${{ github.sha }} -o cyclonedx-json > sbom-${{ github.sha }}.cdx.json

- name: Upload SBOM as release artifact
  uses: actions/upload-release-asset@v1
  with:
    upload_url: ${{ steps.create_release.outputs.upload_url }}
    asset_path: sbom-${{ github.sha }}.cdx.json
    asset_name: sbom.cdx.json
    asset_content_type: application/json
```

Adjunte el SBOM al artefacto de la versión. Cada versión recibe un SBOM. El nombre de archivo con la etiqueta SHA crea la pista de auditoría que vincula cada SBOM con su compilación correspondiente.

### Ejemplo de GitLab CI

```yaml
generate-sbom:
  stage: build
  script:
    - syft $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA -o cyclonedx-json > sbom.cdx.json
  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: never
```

`expire_in: never` garantiza que GitLab no elimine el artefacto. Combinado con el etiquetado de versiones, esto proporciona el historial de SBOM de cada versión durante el tiempo que se necesite.

## Validación del SBOM

Antes de almacenar o enviar un SBOM, valídelo:

```bash
# Validate CycloneDX schema
cyclonedx validate --input-format json --input-version v1_6 --input-file sbom.cdx.json
```

La CLI de CycloneDX está disponible en `@cyclonedx/cyclonedx-cli`. La validación de esquema detecta campos obligatorios ausentes, tipos incorrectos y PURL mal formados antes de que el SBOM entre en los registros de documentación.

## Firma del SBOM

Un SBOM firmado constituye una prueba más sólida en una auditoría que uno sin firma. Si puede demostrar que el SBOM se generó en un momento concreto y que no se ha modificado desde entonces, dispondrá de una cadena de custodia más sólida.

Cosign (del proyecto Sigstore) puede firmar y verificar archivos SBOM:

```bash
cosign sign-blob --key cosign.key sbom.cdx.json > sbom.cdx.json.sig
```

El archivo de firma demuestra que el SBOM lo generó el sistema de compilación y que no se ha alterado. Almacene la firma junto con el SBOM.

## Conclusiones principales

1. Las herramientas de tiempo de origen (cdxgen) leen los manifiestos de paquetes y producen gráficos completos de dependencias transitivas. Los escáneres de imagen (Syft) examinan los artefactos compilados y encuentran los paquetes del sistema operativo y del entorno de ejecución.
2. La práctica recomendada combina ambos enfoques: cdxgen para las dependencias de la aplicación, Syft para los paquetes del sistema operativo y del entorno de ejecución, fusionados en un único SBOM.
3. La generación de SBOM debe integrarse en CI/CD. La generación manual produce SBOM obsoletos o ausentes bajo presión.
4. Adjunte el SBOM a cada artefacto de versión, etiquetado con el SHA de la compilación o la versión. Esto crea la pista de auditoría que exige la regla de retención de 10 años.
5. Valide con la CLI de CycloneDX antes del almacenamiento. Firme con Cosign para crear una cadena de custodia.
