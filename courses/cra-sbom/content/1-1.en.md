# Lesson 1.1: What Goes Into an SBOM: Components, Versions, and Identifiers

Article 13(5) CRA tells you to create an SBOM. It does not tell you every field to include. The formats, [[CycloneDX]] and [[SPDX]], fill that gap. This lesson covers the fields your SBOM must contain to be useful in practice: to a vulnerability scanner, to an auditor, and to you when something goes wrong at 2 a.m.

## The minimum the CRA requires

The CRA minimum is: "components contained in the products with digital elements ... at least the top-level dependencies." In practice, that means each component entry needs enough information to answer:

- What is this component?
- Who made it?
- What version is it?
- How do I look it up in a vulnerability database?

Those four questions map directly to the core fields that both CycloneDX and SPDX require.

## The core fields

### Name

The name of the component as the package maintainer publishes it. Not your internal alias. The exact name as it appears in the package registry. For npm: `@angular/core`. For Maven: `org.springframework.boot:spring-boot`. For Python: `requests`.

Exact names matter because vulnerability databases index by the canonical package name. A minor spelling difference breaks the lookup.

### Version

The exact version string. For npm packages: `17.0.0`. For system libraries: `2.38.1-5+deb12u1`. Ranges like `>=2.0` are not acceptable. They do not tell a scanner which binary is actually running.

Version matters because a [[CVE]] typically affects a range of versions and is fixed in a specific version. Without the exact version, you cannot determine whether your component is affected.

### Supplier

The organisation that publishes or maintains the component. For npm packages: the author or organisation listed in the package manifest. For operating system packages: the distribution maintainer. For commercial libraries: the vendor.

Supplier matters for the [[supply chain attack]] risk picture. If a supplier is compromised, knowing which of your components come from that supplier tells you where to look first.

### Unique identifier: the PURL

A [[PURL]] (Package URL) is the standard way to identify a component uniquely across registries and databases. The format is:

```
pkg:type/namespace/name@version
```

Examples:

- `pkg:npm/%40angular/core@17.0.0`: Angular Core 17.0.0 from npm
- `pkg:maven/org.springframework.boot/spring-boot@3.2.0`: Spring Boot 3.2.0 from Maven Central
- `pkg:pypi/requests@2.31.0`: requests 2.31.0 from PyPI
- `pkg:deb/debian/libc6@2.36-9+deb12u3`: libc6 from Debian Bookworm

Both CycloneDX and SPDX treat the PURL as the recommended unique identifier. Vulnerability databases use it to link CVE records to specific components. When your scanner matches an SBOM against a vulnerability feed, it is matching PURLs.

### Hash

A [[hash]] is a fixed-length fingerprint of the component file. SHA-256 is standard. Including a hash in each SBOM entry lets you verify that the component has not changed since the SBOM was generated. It is also the only way to confirm that two teams are talking about the same binary, not just the same version string.

CycloneDX and SPDX both support hashes per component. Add them whenever your tooling produces them.

### License

Not required by the CRA minimum, but required by most SPDX workflows and useful in practice. The SPDX License Identifier (e.g., `Apache-2.0`, `MIT`, `GPL-2.0-only`) links to the full license text.

If you are an enterprise using open-source components, license information in the SBOM is the foundation of your open-source license compliance program.

## SBOM metadata

Beyond the component list, a valid SBOM includes metadata about the SBOM document itself:

- **Timestamp**: when the SBOM was generated
- **SBOM version**: a version or identifier for this specific SBOM document
- **Tool information**: which tool generated the SBOM and at what version
- **Describes**: which product or component this SBOM describes (the top-level package)

CycloneDX calls this the `metadata` object. SPDX calls it the document creation information section. Auditors look here first to verify freshness.

## What "machine-readable" means in practice

The CRA requires a "machine-readable" format. This means a vulnerability scanner must be able to parse the SBOM without human intervention. JSON and XML satisfy this. A spreadsheet or PDF does not.

A machine-readable SBOM lets you automate the Article 14 monitoring loop: new CVE published → scanner matches SBOM → alert raised → team assesses → report filed if needed.

If your SBOM is a PDF, none of that automation works.

## Key takeaways

1. Each SBOM component entry needs at minimum: name, version, supplier, and a unique identifier. The [[PURL]] is the standard unique identifier.
2. Exact version strings are required. Ranges break vulnerability scanning.
3. A hash per component lets you verify the SBOM has not drifted from the actual deployed binary.
4. SBOM metadata (timestamp, tool, describes) is the first thing an auditor checks.
5. "Machine-readable" means JSON or XML: formats a vulnerability scanner can parse automatically. A spreadsheet or PDF does not qualify.
